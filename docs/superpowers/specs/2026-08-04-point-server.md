# Сервер Point: аккаунт вместо пейринга (#413)

Проработано 04.08.2026 по требованию владельца, записанному в #413. Документ проектный:
кода здесь нет, срезы заведены отдельными задачами. Работа поглощает **#419** (общий секрет
приложения в раздаваемом MSI) и закрывает вторую половину **#465** (пробная квота AI).

## Требование владельца (дословно)

> релей на релизе должен стать сервером, для SSL можно взять Letsencrypt и сабдомен
> point.leerio.app (потом поменяем). Вход и регистрация в приложение и ПК по аккаунту гугл.
> Должно спокойно работать и не пересекаться несколько человек — первые альфа-тестеры.
> У каждого может быть несколько телефонов или ПК.

И решение по миграции: **вход обязателен, старый способ убрать.** Одна модель «человек → его
устройства»; связка по QR-токену исчезает полностью. Гибридов нет.

## Граница, которая не двигается

Сегодня релей физически не может прочитать объект. Корпус владельца — карты, платежи,
переписка, военная ведомость; `CLAUDE.md` называет это границей, которая важнее удобства.
Сервер с аккаунтами обязан сохранить свойство: **аккаунт даёт право положить и забрать, но не
право прочитать.**

Отсюда главный вопрос всей работы, поставленный ещё в #413: чем шифровать, когда токен пары
перестанет существовать. Ответ — раздел «Ключи рождаются у устройств»: ключ не выдаётся
сервером ни в каком виде, сервер раздаёт только **открытые** ключи.

## Что уже построено — на это опираемся, а не строим заново

- **Слепой почтовый ящик работает.** `relay/relay.py` (491 строка): положить / забрать /
  подтвердить, TTL сутки, самолечащийся автозапуск. Через него уже ходят **все** операции
  пары устройств (#415), включая запрос-ответ (`RelayRpcProtocol.kt`).
- **Кадр — один на все дороги.** `encodePcFrame` (`[длина шапки][k=v][байты]`) возит объект и
  по локальной сети, и через релей, и со страницы приёма. Своего формата не заводим.
- **Транспорт уже за швом.** `PcTransport` (`:core:flow`) — контракт; `LanThenRelayTransport`
  выбирает дорогу, `SelfHealingPcTransport` чинит адрес. Смена модели связывания меняет
  реализации, но не форму шва.
- **Цепочка моделей уже умеет OpenAI-совместимого провайдера** (`OpenAiCompatibleClient` +
  `OpenAiProvider`). Пробная квота встанет туда как ещё один адрес, без нового клиента.
- **Приватность уже настройка человека** (`CloudPrivacy.kt`: `PrivacyLevel`, `ReaderPrivacy`,
  `allowedAt`), и куда уходит объект — уже видно (`cloudDestination`). Пробная квота обязана
  жить внутри этой механики, а не мимо неё.

## Решение в одну строку

> **Сервер знает, чьи устройства; устройства знают, что в объекте.**
> Ящик адресуется устройством аккаунта, содержимое запечатано ключом, которого у сервера нет.

## 1. Вход по Google на трёх сторонах

### Один поток на телефоне и на ПК — «как у телевизора»

Развилка была между тремя вариантами: Credential Manager на Android + OAuth-loopback на ПК
(две разные механики), OAuth Authorization Code + PKCE прямо в клиентах (клиентские
идентификаторы уезжают в APK и MSI) — и **поток, посредником в котором служит наш сервер**.

**Выбран третий.** Устройство не участвует в OAuth вовсе:

```
устройство                        сервер point.leerio.app                Google
    │  POST /auth/start ─────────────────►│
    │  ◄──── login_id (256 бит) + код «K7-42Q» + URL входа
    │  открыть браузер ───────────────────►│  /login?d=<login_id>
    │                                      │  ── Authorization Code + PKCE ──►│
    │                                      │  ◄──── id_token (sub, email) ────│
    │                                      │  страница: «Готово. Код K7-42Q»
    │  GET /auth/session/<login_id> (опрос)│
    │  ◄──── device_id + device_token ─────│
```

Почему так:

- **Ни один секрет не попадает в раздаваемый артефакт.** `client_secret` Google живёт только
  на сервере, в файле службы. Это ровно тот инвариант `CLAUDE.md`, который сегодня нарушает
  `RELAY_APP_SECRET`, — и лечится он здесь целиком, а не заменой одного секрета другим.
- **Одна реализация на две платформы.** Compose Desktop и Android открывают браузер одинаково;
  ни `App Links`, ни своей схемы возврата, ни слушателя на `127.0.0.1` (который на Windows
  вызывает запрос брандмауэра при первом же входе).
- **Работает без сервисов Google на телефоне.** Кастомная вкладка — обычный браузер.

Цена, названная вслух: вместо одного тапа — прыжок в браузер и возврат руками. Смягчение:
`login_id` живёт 5 минут и забирается один раз; код на экране и на странице совпадают, чтобы
человек не подтвердил чужой вход. Когда альфа поедет, Credential Manager можно добавить
**поверх того же `/enroll`** как второй вход на Android — это замена реализации, не модели.

### Что Point просит у Google

Только `openid email profile`. Токены доступа Google **не сохраняются**: они нужны ровно один
раз — узнать человека. Значит утечка нашей базы не даёт доступа ни к чьей почте и диску.

### Свой сеанс — непрозрачный токен, а не JWT

Сервер выдаёт `device_id` + `device_token` (256 бит случайности; в базе — только SHA-256 от
него). Устройство шлёт `Authorization: Bearer <device_token>`.

JWT здесь был бы хуже: его нельзя отозвать, не заводя список отозванных, — а отзыв это и есть
свойство, ради которого всё делается («потерял телефон»). Непрозрачный токен проверяется
запросом в базу и умирает в ту же секунду, как человек нажал «Отключить».

**Где живёт токен.** Телефон — `EncryptedSharedPreferences` (сегодня ключ AI лежит в обычных
app-private prefs; для долгоживущего пропуска к своим объектам поднимаем планку). ПК —
`~/.point-pc/account`, права только владельцу. Честно: злоумышленник с правами пользователя на
ПК побеждает в любом случае, шифрование файла здесь ничего не добавляет.

**Отзыв.** Любое устройство круга может отключить любое (`POST /devices/<id>/revoke`).
Отключённое получает `401` на следующем запросе, стирает локальное состояние и показывает вход.
Отзыв доступа на стороне Google **не выкидывает устройства** — Google нужен только чтобы узнать
человека при входе; если владелец захочет иначе, это отдельная периодическая сверка, и в альфу
она не входит.

## 2. Модель данных: человек → устройства

```
users     (id, google_sub, email, created_at)
devices   (id, user_id, kind PHONE|PC, name, key_agree, key_sign, created_at, last_seen, revoked_at)
tokens    (token_sha256, device_id, created_at, last_used_at)
mailbox   (id, device_id, path, size, created_at)          -- шифротекст на диске, TTL 24 ч
drops     (id, user_id, path, size, expires_at)            -- «Дать ссылку»
inboxes   (id, user_id, expires_at, files)                 -- «Принять файл»
ai_usage  (user_id, used, reset_at)                        -- счётчики, без единого байта содержимого
```

- **`google_sub`, а не почта.** Почта у человека меняется, `sub` — нет.
- **Изоляция — не проверка, а форма запроса.** Каждый запрос к данным несёт `user_id` из токена
  в `WHERE`; отдельной «проверки прав» нет, потому что запроса без владельца не существует.
- **Ящик адресуется устройством, а не производной от секрета.** Сегодня адрес
  (`RelayCrypto.mailboxId`) был и адресом, и пропуском. Теперь пропуск — токен аккаунта, и
  адрес освобождается от второй работы.

### Что сервер узнал, чего не знал (называем прямо)

| знает сегодня | добавляется |
|---|---|
| размер блоба, время, непрозрачный адрес | почта и имя человека, список его устройств и их имена, кто кому и когда написал, объём |
| — | какие устройства сейчас на связи |
| **не знает: содержимое** | **по-прежнему не знает содержимое** |

Это цена аккаунта, и она неустранима: «чьи устройства» — и есть то, что аккаунт добавляет.
Метаданные не расширяются сверх необходимого: имя файла и MIME **едут внутри шифротекста**, а не
в заголовке, — сегодня в кадре пары они уже внутри, и так и остаётся.

## 3. Замена пейринга: круг устройств

**Пейринга больше нет как действия.** Есть вход: устройство, вошедшее в аккаунт, само
оказывается в круге и сразу видит остальные.

```
вход → POST /enroll (id_token + открытые ключи устройства + имя) → device_id
     → GET /circle → список устройств аккаунта с их открытыми ключами
```

- Круг кэшируется локально (`FilePcPairings` → `FileCircle` на телефоне, `~/.point-pc/circle`
  на ПК) и обновляется при открытии экрана устройств и после входа — тем же правилом
  «не в каждом шаринге», что сегодня действует для `/caps` (#80).
- Пузырь «На компьютер» перестаёт быть про **пару**: если компьютер один — тап отправляет ему,
  если их несколько — тап открывает выбор из круга. Механика выбора уже есть (device-app-picker
  из #79), заводить свою не нужно.
- Новый телефон подключается из любой точки — ровно то, чего требовал владелец в #413: сеть
  для связывания больше не нужна вообще.

### Локальная сеть остаётся — и авторизуется сама собой

LAN — быстрый путь и единственный, который работает без интернета. Он **остаётся**, но теряет
токен.

Сегодня `PcServer` пускает по `X-Point-Token` (константное сравнение с токеном из QR). Завтра
запрос по локальной сети несёт тот же **запечатанный и подписанный кадр**, что едет через
сервер, плюс заголовок `X-Point-From: <device_id>`. Компьютер пускает, если:

1. `device_id` есть в его кэше круга и не отозван;
2. подпись кадра проверяется открытым ключом этого устройства;
3. кадр открывается его собственным закрытым ключом.

**Умение открыть кадр и есть авторизация.** Ручка `/pair` удаляется целиком; заголовка с
токеном не остаётся ни в одной ручке. Побочный выигрыш: локальная сеть и сервер начинают возить
байт-в-байт одинаковый кадр — сегодня это два разных пути с разными проверками.

**Как находят друг друга в сети.** mDNS остаётся (`Advertiser`, `AndroidPcDiscovery`), но
объявляет `device_id` вместо имени и порта «для пейринга». Телефон сопоставляет объявление с
записью круга — и получает адрес без единого вопроса человеку. Ручной ввод `host:port` уходит
вместе с экраном пейринга.

**Бутстрап.** Круг приезжает с сервера, значит первый запуск требует интернета один раз.
Это не новое ограничение: вход и так требует сети.

## 4. Ключи рождаются у устройств

Требование #413: «ключ должен рождаться у устройств, а не выдаваться сервером, иначе слепота
теряется».

**Каждое устройство при первом запуске генерирует две пары ключей P-256:** одну для
согласования (ECDH), одну для подписи (ECDSA). Закрытые половины не покидают устройство
никогда. Открытые уходят на сервер в `/enroll` и раздаются остальным устройствам круга.

Почему P-256, а не X25519: `XDH` появился в Android только с API 33, а `ECDH`/`ECDSA` по
P-256 есть с ранних версий и в JVM 17. Значит `javax.crypto` хватает — новых зависимостей ноль,
как и у сегодняшнего `RelayCrypto`.

**Кадр v2 (гибридная схема, один вид для одного и для многих получателей):**

```
"P2" | версия | N получателей
     | N × { device_id, эфемерный открытый ключ, nonce, AES-GCM(ключ содержимого) }
     | nonce | AES-GCM(ключ содержимого, encodePcFrame(meta, bytes))
     | подпись отправителя над всем предыдущим
```

- **Отправитель** генерирует случайный ключ содержимого, шифрует им кадр один раз и заворачивает
  этот ключ отдельно под каждого получателя (ECDH с его открытым ключом → HKDF-SHA256 → AES-GCM).
- **Подпись** нужна не для сервера, а для локальной сети: там некому подтвердить, кто пишет.
  Через сервер отправителя подтверждает токен аккаунта, но одна форма кадра на две дороги важнее
  экономии тридцати строк.
- Сервер видит: размер, время, `device_id` получателей. Всё.

### Слабое место, названное вслух

Открытые ключи раздаёт сервер. Значит **злонамеренный сервер может подсунуть свой ключ** и
читать переписку устройств — сегодня этого сделать нельзя, потому что токен рождался в QR,
которого сервер не видел вовсе. Это единственная настоящая потеря во всей работе, и прятать её
нельзя.

Чем смягчается:

1. **Ключ запоминается при первой встрече** (TOFU). Сменился — на экране устройств громкая
   строка «этот компьютер сменил ключ», и до подтверждения человеком через него ничего не едет.
2. **Код устройства** — восемь знаков из отпечатка открытых ключей, показывается на обоих
   экранах. Кто хочет — сверяет глазами; это проверка, а не шаг входа.
3. Сервер свой, на машине владельца. Для альфы этого достаточно; для чужих людей — нет, и когда
   Point выйдет за круг альфа-тестеров, сверка кода должна стать заметнее.

## 5. SSL: домен и Let's Encrypt

Сегодня релей стоит на самоподписанном сертификате с IP в SAN; приложение его пинит
(`RelayTls.kt`), а браузер — нет. Чужой человек, открывший ссылку приёма файла, видит
«подключение не защищено». Для альфы это конец сценария; это записано ценой ещё в `DECISIONS.md`
(#388) и теперь оплачивается.

**Решение: `point.leerio.app`, TLS терминирует Caddy, приложение — за ним на localhost.**

- Caddy получает и **продлевает сам** сертификат Let's Encrypt (ACME встроен, крона не нужно);
  бесплатно, один бинарник, конфиг в пять строк.
- `relay`-приложение перестаёт заниматься TLS вовсе: слушает `127.0.0.1:8080`, снаружи не виден.
- **Пиннинг удаляется** (`RelayTls.kt` целиком). Пинить сертификат Let's Encrypt — ловушка: он
  меняется каждые 90 дней, и первый же автопродлённый ключ положил бы связь у всех сразу.
  Проверка по системному хранилищу — правильная защита для публичного домена, и она же чинит
  предупреждение в чужом браузере.
- Адрес сервера становится константой сборки без секрета (`RELAY_URL` → `POINT_SERVER_URL`),
  переезд на другой домен — правка одной строки, как владелец и просил.

**Действия владельца (без них срез 1 не начинается):**

1. A-запись `point.leerio.app` → `35.185.31.106`;
2. в фаерволе GCP проекта `leerio` открыть `80` (нужен ACME) и `443`;
3. в Google Cloud Console — экран согласия OAuth и клиент типа «Web application» с
   `redirect_uri = https://point.leerio.app/auth/callback`; `client_id`/`client_secret` положить
   на сервер (не в репозиторий).

Порт `8443` после переезда закрывается.

## 6. Квоты и хранение

Чужие данные на одном сервере — значит пределы, сроки и понятная цена. На аккаунт:

| что | предел | срок |
|---|---|---|
| один блоб | 50 МБ (как сегодня) | — |
| почтовые ящики всех устройств | 300 МБ | 24 ч |
| ссылки «Дать ссылку» | 20 активных | 24 ч |
| ящики приёма | 5 активных, по 20 файлов | 24 ч |
| всего на диске | 500 МБ в любой момент | — |

- **Переполнение — честный отказ, а не тихая потеря.** «На сервере кончилось место — заберите
  то, что уже отправлено». Молчаливое вытеснение старого нарушило бы то же правило, что и
  проглоченная ошибка.
- **Цена.** Десять альфа-тестеров × 500 МБ = 5 ГБ пикового диска; на free-tier машине с 30 ГБ
  это влезает с запасом. Сервер остаётся бесплатным — опора на бесплатные ресурсы из `CLAUDE.md`
  не трогается.
- **Уход человека.** «Выйти» стирает устройство и его ящики. «Удалить всё моё» — учётную запись
  и все блобы немедленно, не дожидаясь суток.
- **Логи.** Сегодня `log_message` заглушён нарочно; правило переносится дословно: сервер не
  пишет ни путей, ни имён, ни адресов — только агрегаты без привязки к человеку.

### Чем становится сам сервер

Ручек стало больше десятка, появились аккаунты, проверка чужих подписей (JWT Google) и база.
Ручной разбор HTTP на `http.server` для этого уже не годится — не потому что «мало
возможностей», а потому что своя проверка RS256 была бы худшим кодом в проекте.

**FastAPI + SQLite (WAL) + Caddy.** На той же машине рядом уже живёт uvicorn (`~/icg`, см. #82),
то есть это не новая инфраструктура, а сращивание с существующей. Семантика слепого ящика
переносится дословно: положить / забрать / подтвердить, TTL, сборщик по времени.

## 7. Пробная квота AI (#465, смежно #82)

Вторая половина решения по #465: «квота на пробу + доведение за руку». Сегодня свежепоставленный
Point без ключа не умеет почти ничего — релизная сборка ключей не читает вовсе, и это второй
блокер альфы.

**Прокси-ручка `POST /ai/v1/chat/completions` — OpenAI-совместимая.** Это не изящество, а
экономия: телефон уже умеет такого провайдера (`OpenAiCompatibleClient`), значит нового клиента
писать не нужно. Пробная квота встаёт в цепочку одной строкой:

```
UserKeyLlmClient (свой ключ)  →  TrialLlmClient (квота Point)  →  встроенные ключи (пусто в релизе)
```

Сервер за этой ручкой держит **свои** бесплатные ключи и ротирует их (#82): на 402/429 — следующий
провайдер, никогда в кассу. Это ровно та политика, что записана в `CLAUDE.md`.

**Квота:** 30 действий на аккаунт (не в день), запрос до 5 МБ. Кончилась — `429` с человеческим
телом, которое на экране превращается в «Пробные действия кончились» и ведёт на экран ключа. Это
и есть «доведение за руку»: человек упирается в конец пробы уже понимая, зачем ключ, — а не
узнаёт про ключ из провалившегося действия.

### Эта дорога зрячая, и так и написано

Прокси по построению видит то, что через него идёт: он обязан передать текст и файл чужой
модели. Поэтому:

- **Две службы, а не одна.** Почта (`/mbx`, `/d`, `/u`) слепа и остаётся слепой. `/ai` — другая
  дверь, и слепой её никто не называет.
- Она приходит **за существующий шов** `LlmClient`, как того требует `CLAUDE.md`: сетевое только
  после явного тапа, происхождение видно.
- В `cloudDestination` — своя строка: «пробная квота Point → бесплатная модель». Человек видит,
  что объект уходит не «в Point», а через Point наружу.
- `ReaderPrivacy(where = "сервер Point → бесплатная модель", europe = false, logsRequests = true)`.
  Мы не храним тело запроса; обещать за чужого провайдера не можем и не будем.
- `PrivacyLevel.DEVICE_ONLY` выключает её, как любого облачного читателя. Отдельного
  «выключателя пробы» не заводим — механика уже есть.
- Тела запросов не пишутся на диск и не логируются; считается только число.

Побочный, но крупный выигрыш: пробная квота — это первый настоящий повод убрать бесплатные
ключи провайдеров из раздаваемой сборки насовсем. Проба идёт через сервер, постоянная работа —
через свой ключ; в артефакте не остаётся ни одного.

## 8. Экран входа

Point отвечает на один вопрос — «что я могу сделать с этим объектом». Вход эту границу
переживает: он не заводит своей предметной области и своей навигации. Но экран обязан говорить
языком портала.

**Что на экране:** тёмный портал (`LivingBackground`, как везде), одна строка смысла, одна
кнопка, одна строка про приватность. Ни полей, ни «регистрации», ни второго согласия — согласие
уже живёт в `ConsentScreen`, второго не заводим.

```
                    Point узнаёт ваши устройства по аккаунту

                          [ Войти через Google ]

     Point видит только имя и почту. Что вы пересылаете между своими устройствами,
     сервер прочитать не может.
```

Во время ожидания браузера — «Подтвердите вход в браузере · код K7-42Q» и «Отменить». Не крутящееся
колесо без выхода.

**Где стоит дверь.** Рекомендация:

- **на ПК — при первом запуске.** Компьютер без круга и сегодня ничего не делает: он стартует
  экраном «подключите телефон». Вход просто занимает место пейринга;
- **на телефоне — при первом действии, которое уходит с устройства** («На компьютер», «Дать
  ссылку», «Принять файл», пробный AI). Всё локальное — распаковка, чтение текста, OCR на
  устройстве, QR — работает без входа.

Причина второго пункта: `#465` требует, чтобы первые пять минут Point производили впечатление,
а не спрашивали. Стена на первом запуске отняла бы у поставившего именно этот кусок. **Это
развилка, оставленная владельцу:** если он хочет вход до первого объекта, гейт переезжает в
`FlowHostActivity` — правка одного места, модель от этого не меняется.

**«Мои устройства»** заменяет `PairPcScreen`: список круга (имя, вид, «на связи»/«последний раз
вчера»), код устройства мелким шрифтом, «Отключить» на каждом, «Выйти» внизу. Это не настройки
и не новый раздел — это тот же экран, что был экраном компьютера.

## Развилки, оставленные владельцу

1. **Где стоит дверь входа на телефоне** — при первом запуске или при первом действии, уходящем
   с устройства (рекомендация — второе, раздел 8).
2. **Размер пробной квоты** — предложено 30 действий на аккаунт; число выбрано «чтобы хватило
   распробовать», а не замером.
3. **Сверка кода устройства** — предложена как необязательная проверка. Если владелец считает
   подмену ключа сервером недопустимой даже теоретически, шаг сверки становится обязательным при
   входе нового устройства, и это плюс один экран.

## Что эта работа не делает

- Не трогает ни один инвариант из `CLAUDE.md`: цепочки по-прежнему не строятся сами, сетевое —
  после тапа, происхождение видно, ошибки не глотаются.
- Не заводит подписку и не открывает кассу: сервер бесплатный, ключи бесплатные, на 402/429 —
  следующий провайдер.
- Не делает Point «ещё одним приложением с логином»: единственный новый экран — вход, и он
  заменяет собой экран пейринга, а не добавляется к нему.
