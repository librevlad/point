# Конституция Point

**Статус:** нормативный документ.

Конституция определяет, чем является Point и какие продуктовые законы не могут быть изменены реализацией.

Иерархия:

CONSTITUTION
    ↓
ADR
    ↓
RFC
    ↓
IMPLEMENTATION
    ↓
TESTS

Git history, Issues и текущий код не имеют нормативной силы.

Если код противоречит Конституции — меняется код.
Если ADR противоречит Конституции — пересматривается ADR.
Если RFC противоречит ADR или Конституции — пересматривается RFC.

---

## 1. Point

Point получает чужой объект извне и предлагает действия над ним.

Способ передачи — свойство поверхности:
- системный Share;
- компьютер;
- другие поверхности, если они появятся.

Point отвечает на вопрос:

> Что я могу сделать с этим объектом прямо сейчас?

Point не требует предварительной загрузки объекта в собственное хранилище.

Point не является:
- файловым менеджером;
- AI-чатом;
- OCR-приложением;
- базой знаний;
- постоянным хранилищем файлов;
- облачным диском;
- Dropbox;
- универсальным AI-backend;
- marketplace;
- серверным orchestration-слоем.

Point может помнить, что узнал об объекте, но не обязан владеть байтами объекта.

Рабочая копия может существовать временно. После работы байты могут быть удалены. Память о найденном знании не является хранением исходного файла.

---

## 2. Объект

Object — самостоятельная единица, над которой имеет смысл выполнять действие.

У объекта есть `kind`, но словарь `kind` открыт.

Нельзя заранее предполагать содержание объекта только по его форме.

Например:

IMAGE может оказаться:
- фотографией;
- документом;
- таблицей;
- картой;
- QR;
- перепиской;
- автомобилем;
- котом;
- чем угодно ещё.

Наличие нового типа не требует изменения Конституции.

Point не обязан полностью классифицировать объект перед тем, как начать с ним работать.

---

## 3. Object Graph

Point представляет понимание объекта как граф.

Граф может содержать:
- самостоятельные объекты;
- свойства и факты;
- отношения между объектами;
- локализацию знания;
- происхождение и доказательства;
- вложенность;
- альтернативные и противоречивые результаты;
- результаты преобразований.

Граф не является каталогом мира.

Не требуется вводить runtime-типы `Car`, `Cat`, `Stamp`, `Passport` и тысячи подобных сущностей.

Сущность становится самостоятельным объектом, если с ней имеет смысл отдельно работать пользователю.

Например, на фотографии автомобиля могут одновременно существовать два разных автомобиля. Они не должны сливаться только потому, что принадлежат одному изображению.

Связь между ними и источником выражается графом.

Слияние сущностей, когда оно действительно нужно человеку, может быть выполнено средствами UX.

---

## 4. Знание и обогащение

Enrichment добавляет знание существующему объекту.

Обогащение:
- не уничтожает объект;
- не создаёт его версию;
- не заменяет старое знание;
- увеличивает известное состояние объекта.

Фотография остаётся той же фотографией после того, как Point узнал:
- текст;
- QR;
- номер автомобиля;
- координаты;
- людей;
- даты;
- печати;
- связи;
- другие свойства.

Знание может одновременно существовать:
1. как знание об исходном объекте;
2. как самостоятельный Object Graph node, если с ним можно отдельно работать.

Это одно значение, а не две независимые копии.

---

## 5. Transformation

Transformation создаёт самостоятельный результат, с которым можно работать независимо от исходного объекта.

Например:

ZIP → файлы

Документ → отдельный документ

Документ → таблица

Документ → структурированный текст

Transformation не уничтожает исходный объект или его знания.

Формат сам по себе не является новым semantic object.

Например:

Table
→ XLSX
→ CSV
→ HTML

Это разные representations одного объекта.

---

## 6. Intent

Intent — не пользовательский ввод и не тип объекта.

Intent — семантический смысл действия, которое Point считает уместным для текущего состояния объекта.

Point выводит его по доступному знанию, контексту и пользовательскому Focus.

Intent не должен превращаться в предположение о содержании.

Intent может изменяться по мере получения нового знания.

Конституция не требует одного фиксированного Intent на весь жизненный цикл объекта.

---

## 7. Capability и Realizer

Capability отвечает:

> Что можно сделать?

Realizer отвечает:

> Как это сделать?

У одной Capability может быть несколько Realizer.

Получение знания об объекте — такая же Capability. Отличается результат: знание об объекте, а не новый объект или внешний эффект. Отдельного механизма исследования Point не заводит.

Человек выбирает Capability, а не Realizer.

Конкретный исполнитель скрыт, если его выбор не меняет результат, который получает человек.

Устройство является частью Capability только тогда, когда от него зависит внешний результат.

Вычисление на телефоне и компьютере, дающее человеку один и тот же результат, — одна Capability.

Печать на телефоне и печать на компьютере — разные действия, если результат физически появляется в разных местах.

---

## 8. Planner

Planner определяет доступные и порядок предлагаемых действий для текущего состояния объекта.

Список действий выводится из:
- текущего Object Graph;
- деклараций Capability;
- контекста;
- Intent;
- пользовательского Focus;
- доступности исполнения.

Таблицы вида `ObjectState → Actions` не существует.

Новая Capability автоматически становится кандидатом там, где она применима.

Intent влияет на порядок, но не должен уничтожать потенциально полезные действия.

Порядок действий для человека и выбор следующего исследования — две разные задачи над одним состоянием.

Полезное действие не становится следующим исследованием только потому, что оно уместно. Полезное исследование не показывается человеку действием только потому, что оно выбрано следующим.

---

## 9. Progressive Understanding

Point не обязан понять объект целиком одним проходом.

Понимание развивается:

Object
→ Knowledge
→ новые возможности исследования
→ новое Knowledge
→ новые действия
→ ещё возможности
→ ...

После существенного обогащения пространство действий пересматривается.

Point может продолжать понимать объект столько, сколько это оправдано.

Полное понимание не является обязательной целью.

Цель — сделать следующие полезные действия возможными и вероятными.

---

## 10. Focus

Focus — пользовательское указание на область, часть или аспект объекта.

Focus не является Intent.

Focus не является редактированием значения.

Focus может быть:
- выделенной областью изображения;
- выбранным объектом внутри документа;
- конкретной частью сообщения;
- другим способом указать Point, куда смотреть сильнее.

Отсутствие Focus не блокирует понимание.

UX должен позволять двигаться по лестнице:

Понять
→ Понять сильнее
→ Понять ещё сильнее
→ ...

При этом пользователь может войти внутрь обнаруженного объекта и продолжить понимание уже его.

Например:

переписка
→ фотография
→ автомобиль
→ конкретный автомобиль
→ госномер.

---

## 11. Автоматизм

Point вправе автоматически выполнять внутреннюю работу в пределах разрешённых границ.

Автоматическое понимание не означает автоматическое выполнение внешнего действия.

Граница автоматизма определяется политикой исполнения и приватности.

Объект покидает устройства пользователя только с явного согласия человека.

Согласие может быть дано заранее — выбранным режимом работы, — но никогда не подразумевается по умолчанию и не выводится из того, что снаружи получится качественнее.

Автоматизм действует внутри устройств пользователя. Граница устройств не пересекается автоматически.

Конституция не требует полностью понимать объект до первого экрана и не запрещает внутреннее Progressive Understanding.

---

## 12. Local / Computer / Remote и продолжение на другом устройстве

Исполнение может использовать:
- устройство пользователя;
- компьютер пользователя;
- внешний сервис;
- несколько исполнителей.

Выбор конкретного исполнителя — внутреннее решение Point, если результат для человека одинаков.

Внешний сервис не становится скрытым исполнителем.

Пользователь знает, что объект покидает его устройства, и куда он направляется. Это знание не зависит от того, насколько Point считает отправку полезной.

Качество результата является главным критерием внутри разрешённого пространства исполнения.

### Продолжение на другом устройстве

Работа над объектом может быть продолжена на другом устройстве пользователя.

При этом:
- это тот же объект, а не его копия и не новый объект;
- уже полученное знание не теряется при передаче;
- полученный результат возвращается в состояние исходного объекта.

Point не обязан держать единый синхронный Graph на всех устройствах пользователя.

Между устройствами передаётся то, что нужно для продолжения работы: объект, его известное состояние и результат.

Отсутствие синхронизации не является основанием потерять знание.

---

## 13. Неопределённость

Point не превращает отсутствие найденного знания в утверждение об отсутствии сущности.

Например:

QR не найден ≠ QR отсутствует.

Телефон не распознан ≠ телефона нет.

Состояние знания должно позволять отличать:
- обнаружено;
- не обнаружено;
- не исследовано;
- исследовано недостаточно;
- противоречивые результаты.

Противоречивые знания не уничтожаются молча.

Состояние знания и состояние операции — разные вещи.

Идёт ли сейчас исследование, завершилось ли оно и не сорвалось ли — свойства операции, а не знания об объекте.

Сорвавшееся или прерванное исследование не превращается в «не обнаружено». Знание остаётся неисследованным или исследованным недостаточно, а неудача сообщается человеку как неудача.

---

## 14. Provenance

Point может хранить происхождение, доказательства и альтернативы.

Происхождение не является обязательной частью пользовательского представления.

Человеку не требуется видеть:
- какой Realizer дал результат;
- какую модель использовали;
- внутреннюю confidence;
- внутреннюю цепочку доказательств.

Point отвечает за качество результата сам.

---

## 15. UX

Пользователь должен сразу увидеть:
1. объект;
2. доступные действия.

Получение дополнительного знания может происходить после появления первого экрана.

Новые действия могут появляться по мере понимания.

UX не обязан раскрывать внутреннюю архитектуру.

Пользователь видит человеческие формулировки действий:
- «Прочитать»;
- «Найти номер»;
- «Определить место»;
- «Понять сильнее»;
- и т. п.

Не показываются внутренние названия:
`Capability`, `Realizer`, `Planner`, `Resolver` и т. п.

---

## 16. Настройки

Настройки являются конфигурацией Point, а не предметной областью работы с объектами.

Они могут иметь собственную полноценную навигацию.

Правило «Point не создаёт собственные предметные области» к настройкам не применяется.

---

## 17. Память

Point может сохранять память о:
- объектах, с которыми работал;
- действиях;
- найденном знании.

Память не должна превращаться в копию исходных файлов.

Память может быть забывчивой и управляемой пользователем.

Память не превращает Point в файловое хранилище.

---

## 18. Инварианты

Нарушение любого из следующих правил является дефектом:

1. Point начинается с внешнего объекта.
2. Нельзя считать содержание известным без исследования.
3. Разные намерения не сводятся в одно ради удобства реализации.
4. Действия выводятся, а не хранятся таблицей переходов.
5. Capability отвечает «что», Realizer — «как».
6. Enrichment не создаёт новую версию объекта.
7. Новый самостоятельный объект появляется только при действительно самостоятельном результате.
8. Отказ не скрывается.
9. Объект не покидает устройства пользователя без явного согласия человека.
10. Внутренние архитектурные понятия не становятся пользовательским интерфейсом.
11. Отложенная возможность не становится частью продукта только потому, что код уже существует.
12. Реализация не определяет продуктовую семантику.
13. Неудача исследования не превращается в знание об отсутствии.
14. Продолжение работы на другом устройстве не теряет уже полученное знание.

---

## 19. Что Point не обязан делать

Point не обязан:
- полностью классифицировать каждый вход;
- строить полный semantic graph;
- заранее знать все типы объектов;
- запускать весь AI на каждом входе;
- полностью понимать объект до показа действий;
- превращать каждую обнаруженную сущность в Object;
- иметь отдельный pipeline для каждого типа мира.

---

## 20. Изменение Конституции

Конституция меняется только явным продуктовым решением владельца.

ADR, RFC, код, тесты, Issues и Git history не могут изменить Конституцию сами по себе.
