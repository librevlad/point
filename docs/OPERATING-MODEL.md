# Point — операционная модель разработки

Как здесь организована работа: три «кресла», их права решений, петля одного среза и
где живёт контекст. Инженерные инварианты — в `CLAUDE.md`; направление — в
`ROADMAP.md`; спорные развилки — в `DECISIONS.md`. Тут — *ритм*, а не бюрократия
(документ намеренно ≈ на один экран).

## Три кресла

| Кресло | Владеет | Решает | Пишет | Никогда |
|---|---|---|---|---|
| **ChatGPT — ко-фаундер / продукт** | ЧТО и ЗАЧЕМ | Скоуп, приоритет, ship/no-ship по Северной звезде | **Issues** (скоуп + acceptance + чем уменьшает переключения); порядок «Up next» | Прод-код; открывать/мёржить PR; менять `compileSdk`/зависимости |
| **Claude Code — CTO / dev** | КАК | Архитектура, реализация, инвариантные развилки | **Ветка + PR** (self-review, чеклист инвариантов, результат гейта); записи `DECISIONS.md`; коммиты | Решать приоритет; **начинать срез без «go»**; self-merge без зелёного CI |
| **Человек (librevlad) — founder/owner** | ВКУС + ГЕЙТ | «go», финальный approve, **merge**, тег релиза | Сигнал «go»; approve/merge PR; ратификация спорных DECISIONS | Микроменеджить «как» |

**Граница в одну строку:** ChatGPT — *что стоит делать и зачем*; Claude — *как это
построено, и строит*; человек — *go / не сейчас* и *merge / держим*.

## Права решений: что / как / делать

- **Что и зачем** — ChatGPT. Превращает `ROADMAP.md` в скоупнутые issues, держит
  порядок «Up next», защищает Северную звезду («каждый релиз уменьшает переключения
  между приложениями»).
- **Как** — Claude Code. Реализация за контрактами, инварианты `CLAUDE.md`, спорные
  развилки → `DECISIONS.md`.
- **Делать / не сейчас** — человек. Единственный, кто даёт «go» и мёржит.

## Петля одного среза

1. **Направление → задача.** ChatGPT читает `ROADMAP.md` → пишет **Issue** (acceptance
   + одна строка про Северную звезду) → Backlog/Up next.
2. **Приоритет + «go».** ChatGPT упорядочивает «Up next». Человек даёт **«go»** на
   верхний issue (`roadmap #N` — это *идентичность*, не приоритет).
3. **Сборка.** Claude: issue → In progress; ветка `feat/N-slug`; реализация; инварианты;
   при спорной развилке — `DECISIONS.md`; гейт `./gradlew test assembleDebug`; независимое
   AI-ревью `bash scripts/gemini-review.sh`; **PR** (Conventional-title, `Closes #N`,
   чеклист) → In review.
4. **Суд.** Человек смотрит diff (вкус + Северная звезда), ждёт **зелёный CI**,
   **squash-merge**. Issue авто-закрыт → Done.
5. **Релиз (периодически).** Прошёл milestone по Северной звезде → человек режет тег.

**«go» = переход доски `Up next → In progress`.** Это конкретный триггер правила
`CLAUDE.md` «не начинай следующий срез без явного го». ChatGPT, заскоупивший issue, —
это НЕ «go»; «go» даёт только человек.

## Где живёт контекст (без двойного учёта)

| Артефакт | Что держит | Кто пишет / читает |
|---|---|---|
| `docs/ROADMAP.md` | Стратегия/нарратив: Северная звезда, фазы, швы (не статус задач) | ChatGPT/человек пишут; Claude читает |
| **GitHub Issues** | Исполняемые задачи: скоуп, acceptance, статус, обсуждение | ChatGPT пишет; Claude ссылается; закрывает merge |
| **Projects-доска** | Текущее состояние (какой issue где) | авто (workflow «closed → Done») |
| **PR-описание** | «Как в полёте»: self-review, инварианты, гейт | Claude пишет; человек читает для approve |
| `docs/DECISIONS.md` | Долговечные спорные решения | Claude добавляет; человек ратифицирует |

Новые гранулярные задачи **рождаются как Issues** (#7+), не дописываются в `ROADMAP.md`.

## Ветки и PR

- Ветка: `<type>/<issue#>-<slug>` (напр. `feat/5-floating-bubble`), type = Conventional-тип.
- **PR** на существенное (новый Capability/Realizer, архитектура, всё, что трогает
  инвариант, мультифайловое); **прямо в `main`** на тривиальное (`docs:`/`chore:` вне
  `src/main`). Сомневаешься → ветка. CI гоняется и на прямых пушах.
- **Squash-merge** только при зелёном CI (`gh pr merge --squash --delete-branch`) —
  держит историю линейной. PR-title = Conventional-Commit subject + `Closes #N`.
- Жёсткая branch protection отложена (блокирует соло self-merge); включить с приходом
  2-го контрибьютора.

## CI

Один workflow `.github/workflows/ci.yml`: `./gradlew test assembleDebug` на каждый push
в `main` и на PR. Билд keyless (без секретов) — гард в `data/build.gradle.kts`.

## Ревьювер (Gemini CLI)

Независимый AI-ревьювер — второе мнение помимо CTO/dev, локально и read-only.
`bash scripts/gemini-review.sh [base]` (база по умолчанию `origin/main`) берёт дифф
ветки и шлёт в **Gemini CLI** (`--approval-mode plan` — только чтение; модель
`gemini-flash-latest`, т.к. дефолтная `gemini-2.5-pro` недоступна на free-tier), печатает
ревью с упором на инварианты проекта. Ключ — из `local.properties` (`GEMINI_API_KEY`),
в репозиторий не попадает. Claude прогоняет его перед PR; вывод **информативный, не гейт**
(гейт — зелёный CI + вкус человека).

## Релизы

Ручной тег-на-milestone под Северную звезду: `git tag -a vX.Y.Z` + опц. `gh release
create --generate-notes`. В том же коммите — синхро `versionName`/`versionCode`
(`app/build.gradle.kts`). CHANGELOG не ведём (Conventional Commits + generated notes).

## Инварианты

Не дублирую — единственный источник правды по инженерным инвариантам (Capability ≠
Realizer, Android-free ядро, side-effect за контрактом, ≤300 мс первый экран, …) —
`CLAUDE.md`, раздел «Инварианты, которые легко нарушить».

## Планирование: спринты (метод принят из #113, 2026-07-29)

Уровни: **Vision → Epic → Milestone → Sprint → Task.** Живой план — `docs/SPRINTS.md`.

**Правило спринта.** Спринт заканчивается **демонстрируемым артефактом**, который можно
показать человеку за 30 секунд.

**Оговорка (обязательная).** Исходная формулировка #113 требовала именно *фичи* — «не
рефакторинг, не подготовка, только демонстрируемая ценность». Буквально применённое, это
правило отвергает весь релизный спринт: «вынести ключи из сборки» за 30 секунд не покажешь.
Поэтому критерий смягчён с *фичи* до *артефакта*:

- Годится: «релизная сборка стоит на телефоне и проходит смоук» · «`strings` по APK даёт ноль
  ключей, а возврат ключа роняет тест» · «черновик релиза в Play Console, все проверки зелёные».
- Не годится: «отрефакторили» · «подготовили основу» · «покрыли тестами» без внешнего эффекта.

Спринт без записанного демо не начинается. Демо пишется **до** работы, а не после.

## Inbox → Backlog: сырьё отделено от работы (04.08.2026)

На доске появилась колонка **Inbox**. Правило одно:

- **Inbox** — сырой поток мыслей владельца. Мысль на ходу, идея из десяти строк, «а вот бы».
  Ловится, чтобы не потеряться, и НЕ является работой. `/todo` пишет сюда.
- **Backlog** — то, что прошло **разбор**: понятно, зачем это человеку, за какие швы делается и
  как судить результат. Из Inbox в Backlog переводит брейншторм с владельцем, а не команда.

Зачем разделение: до него бэклог смешивал сорок задач разной природы — от «поправить кнопку» до
манифеста платформы, и верхний issue доски ничего не значил. Приоритет («Up next») ставит только
человек, и ставить его можно лишь тому, что уже разобрано.

**Разобранная идейная issue, в которой не осталось полезного, удаляется.** Не закрывается «на
всякий случай», а удаляется: смысл из неё уже переехал в конкретные задачи, а пустая оболочка
только засоряет поиск. Решение владельца.

**Идентификаторы колонок меняются при любой правке набора** — 04.08.2026 добавили Inbox, и
сменились все шесть. Скрипты и скиллы, где они зашиты (`/todo`), после такой правки надо чинить,
иначе задача ляжет на доску без статуса и потеряется молча.

## Система разработки Point (05.08.2026)

Это рабочий процесс, а не разовая уборка доски. Ему следуют все — и человек, и Claude.

### Цикл задачи

```
INBOX → SHAPED → READY → IN PROGRESS → REVIEW → VERIFY → DONE
```

| Стадия | Что означает |
|---|---|
| **Inbox** | Сырьё: идея, наблюдение, гипотеза, «а вот бы». Ещё **не** обязательство продукта. |
| **Shaped** | Задача сформулирована: проблема · ценность для человека · ожидаемое поведение · границы · критерий готовности. |
| **Ready** | Понятна, невелика, зависимости известны, нерешённых продуктовых развилок нет. |
| **In progress** | Работа идёт прямо сейчас. |
| **Review** | Реализация закончена: сверяем с задачей, ищем расползание рамок, регрессии, качество тестов. |
| **Verify** | Проверка на живом продукте — телефон, компьютер, сервер, Drop, настоящие пути человека. |
| **Done** | Проверенный результат. |

### Четыре правила, которые не обсуждаются

1. **Claude берёт работу сам только из `Ready`.** Ни из Inbox, ни из Shaped, ни «по смыслу».
2. **Claude не принимает продуктовых решений.** Встретил развилку — остановил зависимую часть,
   назвал её решением владельца, продолжил независимое.
3. **`Done` — это проверенный результат, а не «исполнитель сказал, что готово».** Написанный код
   не равен работающему продукту, и разница между ними стоит ровно одного разочарованного человека.
4. **Новая идея не становится задачей автоматически.** Превратить Inbox в Shaped Claude может
   помочь; превратить идею в обязательство продукта — нет.

### Продуктовые решения — отдельный поток

```
OPEN → DISCUSS → DECIDED
```

Живёт в поле `Decision` и в отдельном виде доски. Сюда идёт то, что нельзя безопасно угадать:
продуктовая модель, равноправные варианты поведения, границы продукта, UX-решения с
последствиями. Угаданное продуктовое решение дороже несделанной задачи: задачу видно, а
угаданную волю владельца — нет, пока она не разошлась по десяти местам.

### Незавершённое держим малым

`Ready → In progress` — только когда работа действительно начинается. Один исполнитель — одна
задача; несколько независимых исполнителей — несколько действительно параллельных. Количество
открытых issues прогрессом не является.

### Чем меряется движение

```
ясная проблема → ясное решение → маленькая реализация → проверка → эффект у человека
```

Не «больше issues → больше коммитов → больше возможностей».

### Устройство доски

- **Поля:** `Status` (семь стадий выше) · `Priority` (P0/P1/P2/POST) · `Area` (Core, UX, AI,
  Phone, Computer, Drop, Server, Privacy, Release) · `Type` (Feature, Bug, UX, Product, Tech Debt,
  Research) · `Size` (XS…XL) · `Decision` (Open/Discuss/Decided) · веха · родительская задача.
- **Виды:** `Execution` — доска работы без сырья и сделанного · `Product Backlog` — всё
  сформированное таблицей · `Inbox` — только сырьё · `Release` — текущая веха · `Decisions` —
  продуктовые развилки.
- **Эпик — это родитель, а не чек-лист в теле issue.** Прогресс считает доска
  (`Sub-issues progress`); список галочек руками расходится с действительностью на второй день.
- **Статус выводится, а не вводится**, везде, где это возможно: правила доски сами ставят Inbox
  новой карточке, Done — закрытой задаче и смерженному PR. Ручной остаётся ровно та часть, где
  решает человек: «нужно ли это» и «делаем ли это следующим».

### Цена ошибки при правке полей

Опции поля обновляются **вместе с идентификаторами**: передашь список без `id` — GitHub
пересоздаст опции, и все проставленные значения слетят молча. Проверено 05.08.2026 на `Priority`:
двадцать пять приоритетов исчезли и восстанавливались из снимка, снятого перед правкой. Снимок
доски перед изменением полей — обязателен.
