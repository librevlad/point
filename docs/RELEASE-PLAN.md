# Point — путь к 1.0 (CTO release plan)

Живой документ. Цель: первая **публичная** версия Point — надёжная, приватная, с
замкнутым killer-циклом. Принцип: **не выдумываем новую архитектуру** — доводим
существующую (Capability ≠ Realizer, граф-из-контрактов, Android-free ядро). Северная
звезда: *каждый релиз уменьшает переключения между приложениями*.

Связанные доки: `ARCHITECTURE.md` (карта), `DECISIONS.md` (почему), `ROADMAP.md`
(фазы платформы), `OPERATING-MODEL.md` (как ведём работу). Задачи — GitHub issues
(`roadmap #N == issue #N`), сгруппированы в майлстоуны M1–M3.

---

## 1. Аудит-дельта (Этап 1)

**Реализовано полностью:** core-loop (Share→граф→действие→объект→история); вывод Flow
Graph из `accepts()`; Resolver + мульти-realizer шов (OCR device→cloud, доказан);
офлайн-OCR (Tesseract); AI-фолбэк Gemini→Claude→OpenAI; коллекции (архив/PDF-страницы,
merge/save-all/share-all); история + launcher-home; избранные цепочки; бренд + adaptive
icon; светлая **и тёмная** темы.

**Реализовано частично:** история (пишет **только исходный объект**, не флоу-журнал);
scan (только Ч/Б-фильтр, не авто-геометрия); office (только извлечение текста, не
редактирование); мульти-объект (share **out** есть, receive **in** — нет).

**Осталось заглушкой:** paywall (`DefaultEntitlements=true` → AI/Excel бесплатны);
OpenCV-скан-пак (спроектирован в `design-opencv-scan-pack.md`, не построен, gated на
пробе); `RealizerKind.REMOTE` (зарезервирован под ICG).

**Можно удалить / разрешить:** фичи `HAS_TEXT` и `IS_IMAGE_PDF` объявлены, но **никто не
производит и не читает** (мёртвые) → `IS_IMAGE_PDF` **оживить** энричером (маршрут
скан-PDF в OCR), `HAS_TEXT` — оживить или удалить. `DefaultBubblePolicy` не забинжен —
**оставить** (детерминированные тесты). `HistoryStore.clearAll` есть, но не вызывается —
**подключить**, не удалять.

**Удачные решения:** Capability ≠ Realizer (единственный шов для cloud/ICG/паков);
граф-из-контрактов (нет рассинхрона UI↔граф); Android-free ядро (`ScratchRef`, не `Uri`)
→ Desktop/Web почти бесплатны; HTTP без SDK (вес APK); output-based fallback-цепочка;
файловая персистенция без Room (просто, JVM-тестируемо).

**Стали техническим долгом:** история без ретенции (утечка диска); флоу in-memory →
теряется на process-death; конфиг только compile-time (блокирует BYOK/смену модели);
`:app` / HTTP-клиенты / Android-адаптеры / `FlowViewModel` — 0 тестов; release-minify off.

**Архитектурные риски:**
- **R1 — нет persist состояния** → потеря середины флоу на фоновом kill (продукт-«путешествие» рвётся).
- **R2 — нет runtime-конфига** → BYOK и смена модели заблокированы (вшитый ключ/квота).
- **R3 — приватность** → документы уходят в облачные LLM без consent (store-review + доверие).
- **R4 — release-minify off + вес 24.5 МБ** → большой релиз-APK, нет R8/shrink.
- **R5 — `FlowViewModel` без тестов** → «мозг» флоу хрупок при любой доработке.

**Доки vs код:** исправлено этим ходом — `CLAUDE.md` (устаревшее «нет иконки в лаунчере»
→ HomeActivity=лаунчер), ранее `ROADMAP.md` #2–#4 (помечены ✅). Остаток — историческая
секция `ARCHITECTURE.md` «Executor'ы MVP» (терминологический сдвиг задокументирован) —
не трогаю намеренно.

## 2. Roadmap до 1.0 (Этап 3 — настоящий путь; каждый этап самоценен и опирается на предыдущий)

### M1 — «Trust» (0.3): надёжная, приватная база
*Ценность:* приложение, которое **можно опубликовать** и которому доверяешь.
*Опирается на:* существующий core-loop. *Разблокирует:* всё остальное (без доверия нет релиза).
- Persist флоу-стека (R1) — переживает process-death.
- История: ретенция (cap/TTL) + подключить `clearAll` (утечка).
- `FlowViewModel` → тестируемая оркестрация + покрытие (R5).
- Privacy/consent-поверхность для облачной загрузки (R3) — блокер стора.
- Release-hardening: R8/`shrinkResources` + signing config + crash-репортинг-шов (R4).
- Полировка error/empty-состояний (доверие).

### M2 — «Killer loop» (0.4): замкнуть коллекцию + документный сценарий
*Ценность:* «сфоткал N страниц → один чистый PDF / текст, не выходя из Point» — момент
«теперь всегда буду пользоваться». *Опирается на:* M1 (стабильность) + существующие
collection/merge/scan/OCR. *Разблокирует:* документо-центричный use-case (главный липкий).
- Входящий `ACTION_SEND_MULTIPLE` → COLLECTION (последняя миля к merge/save-all).
- `IS_IMAGE_PDF` энричер → маршрут скан-PDF в OCR/Страницы (убить тупиковый «Извлечь текст»).
- Разрешить `HAS_TEXT` (оживить или удалить).
- Мультистраничный скан → merge (фото → Ч/Б → один PDF).

### M3 — «Control & measure» (0.5): runtime-конфиг + телеметрия
*Ценность:* пользователь владеет ключами/моделью; команда **измеряет** Северную звезду.
*Опирается на:* M1/M2. *Разблокирует:* публичную раздачу без «нашего» ключа + iteration по данным.
- Settings-подсистема (runtime-конфиг + secure storage) → **BYOK** + смена модели (R2).
- Телеметрия / event-log шов → измерять минус-переключения; питает learning-policy.
- HTTP-transport шов + тесты LLM-клиентов.
- Structured LLM output (tool/JSON) → обобщить Excel/таблицы вместо TSV-хака.

> **1.0 = M1 + M2 + M3.** Надёжный, приватный, замкнутый killer-цикл, конфигурируемый и измеримый.

### Post-1.0 (те же швы — фазы `ROADMAP.md`)
Capability Packs (OpenCV-пак — первый DLC, gated; carve-up `:executors`) · ICG Resolver
(REMOTE-routing) · Floating Bubble / Accessibility (policy-риск, валидировать до вложений)
· Marketplace / Plugin SDK / Desktop / Web / Enterprise — на существующих контрактах.

## 3. Максимум пользы при минимуме сложности (Этап 4)

Не эффектные — **липкие**. Для каждой: зачем · стоимость · риск · почему сейчас.

1. **Входящий мульти-шаринг → PDF** (M2). *Зачем:* закрывает killer-сценарий, который
   уже построен (merge/collection), но недостижим на входе. *Стоимость:* S–M. *Риск:*
   низкий. *Почему сейчас:* последняя миля к готовому механизму.
2. **Persist флоу** (M1). *Зачем:* без него «путешествие» рвётся на любом фоновом kill —
   тихо теряет доверие. *Стоимость:* M. *Риск:* средний (сериализация scratch). *Почему
   сейчас:* ретрофит дорожает со временем; фундамент доверия.
3. **Скан-PDF → OCR-маршрут** (`IS_IMAGE_PDF`, M2). *Зачем:* сейчас скан-PDF ведёт в
   тупиковый Failure. *Стоимость:* S. *Риск:* низкий. *Почему сейчас:* мёртвая фича +
   живая боль, дешёвый шов, +ребро графа.
4. **BYOK / смена модели** (M3). *Зачем:* снимает зависимость от вшитого ключа — юзеры
   приносят свой. *Стоимость:* M. *Риск:* средний. *Почему сейчас:* разблокирует
   публичную раздачу без нашей квоты.

## 4. Технический долг (Этап 5)

**Критично** (блокирует релиз/доверие):
- CI-гейт (`gradlew` exec-бит) — ✅ **починено**. *Иначе:* «squash при зелёном CI» неисполним.
- Флоу теряется на process-death (R1). *Иначе:* продукт ненадёжен при фоновых kill.
- История без ретенции. *Иначе:* утечка диска, деградация, риск полного хранилища.
- Приватность облачной загрузки без consent (R3). *Иначе:* отказ/бан Play + репутация.

**Важно:**
- `FlowViewModel` без тестов (R5). *Иначе:* регрессии в мозге флоу проходят молча.
- HTTP-клиенты без тестов + дублирование. *Иначе:* хрупко к смене API провайдеров.
- release-minify off + APK 24.5 МБ (R4). *Иначе:* тяжёлый релиз-APK, медленнее установка.

**Можно позже:**
- Мёртвые `HAS_TEXT`/`IS_IMAGE_PDF` (частично снимается M2). *Иначе:* путаница + упущенный роут.
- Единый `:executors` (carve-up с приходом паков). *Иначе:* неудобство модуляризации позже.
- OpenAI без PDF/`max_tokens`; нет retry/учёта стоимости. *Иначе:* асимметрия провайдеров, слепота по деньгам.

## 5. Производительность (Этап 6)

- **Первый экран** — zero-I/O, ≤300 мс, держится. *Улучшение:* измерять реальный TTID телеметрией (M3).
- **Память** — bounded-peek везде; риск — полный decode больших Bitmap (Image/Scan/Merge).
  *Улучшение:* `inSampleSize`/downscale для крупных изображений; гарантировать `recycle`.
- **Размер APK** — включить **R8 + `shrinkResources`** (release), ожидаемо −30–40%. PdfBox-шрифты
  (+~9 МБ) и Tesseract (+~14 МБ) доминируют → OCR-движок/модели — кандидат в **on-demand** (как OpenCV).
- **Холодный старт** — Hilt-граф + `FileCapabilityUsage` load из Properties; дёшево, но не тянуть
  тяжёлые синглтоны на критический путь; мерить.
- **Большие PDF** — извлечение/растеризация постранично; риск OOM на 100+ стр. *Улучшение:*
  страничный стриминг + лимит/предупреждение на очень больших.
- **Архивы** — energ-peek 200 записей; распаковка полная. *Улучшение:* лимит размера/числа при
  extract (zip-slip защита уже есть).
- **OCR** — on-device первый; холодная инициализация движка. *Улучшение:* ленивая init + кеш.
- **AI** — без streaming/retry: долгие ответы «висят» в спиннере. *Улучшение:* streaming (UX) +
  retry/backoff на 5xx + учёт токенов (M3).
- **История** — unbounded (см. долг) → ретенция (M1).
- **Scratch** — чистится в `endFlow`/`onShared`; риск утечки при abnormal kill смягчён clear-на-старте.

## 6. Архитектура под будущее (Этап 7)

Проверка «готова ли текущая архитектура», и нужен ли **небольшой рефактор сейчас**.

| Возможность | Готовность | Рефактор сейчас? |
|---|---|---|
| Floating Bubble | флоу переиспользуется; вход+сервис net-new + policy-риск | Нет (шов флоу готов) |
| ICG | `RealizerKind.REMOTE` + Resolver + `produces`-advisory готовы | Нет |
| Capability Packs | шов доказан (OCR); контракты уже в независимом `:core:flow` | Нет — carve-up только с 1-м паком |
| Marketplace / Plugin SDK | контракты = SDK-поверхность (`:core:flow`+`:core:model`) | Нет — реестр/песочница net-new (Security) |
| Desktop / Web | ядро чистый Kotlin → переиспользуемо | Нет (возможный KMP-вынос — post-1.0) |
| Enterprise | политики/аудит на `Entitlements`/`HistoryStore` | Нет |

**Вывод:** срочного архитектурного рефактора под будущие возможности **нет** — швы
существуют, преждевременный carve-up = выдумывание архитектуры (против принципа). Реальная
now-работа — это долг M1 (persist / история / тесты), а не «будущие» рефакторы; она
идёт задачами M1, а не мелкими правками. Единственный отложенный структурный шаг —
carve-up `:executors` под паки — имеет явный **триггер** (первый Capability Pack), зафиксирован issue.

## 7. UX (Этап 8 — глазами обычного пользователя)

- **Непонимание:** пузырьки-иконки без ясной модели «что произойдёт»; «Done» vs новый объект
  неочевиден; после действия непонятно, «куда делся результат».
- **Слишком много мыслей:** выбор из N пузырьков без видимой подсказки «частое/рекомендованное»
  (learning-policy работает, но невидима); пустой AI-промпт «что сделать?» пугает.
- **«Набор функций» vs система:** цепочки есть (избранное), но не предлагаются проактивно; нет
  «продолжить» после Done/Share; коллекция и одиночный объект — разные экраны без единого нарратива.
- **Улучшения (MVP):** (a) подпись под пузырём «→ станет TEXT/PDF» из `expectedNextState`; (b) после
  терминального Done — предложить следующий разумный шаг вместо тупика; (c) первый запуск — 1 экран
  «что такое Point» (share-target невидим без объяснения — это и GTM); (d) видимый маркер «часто
  используемое» на топ-пузыре.

## 8. Правило графа (Этап 9 — фильтр каждой фичи)

Каждый предложенный Executor/Capability проверяется: **добавляет ли он рёбра в граф**
(новые цепочки)?
- Мульти-приём → COLLECTION: +рёбра (N объектов → merge/save-all/OCR-all) ✅
- `IS_IMAGE_PDF`-маршрут: +ребро (скан-PDF → OCR/Страницы) ✅
- Structured LLM output: усиливает Excel/AI-выходы → +рёбра (таблица → OFFICE → …) ✅
- Persist / telemetry / settings: **не рёбра**, а фундамент доверия/измеримости — осознанное
  исключение уровня MVP-хардненинга, не «фича-в-граф».

Фичи, НЕ усиливающие граф → вне MVP (косметика, эффектные one-off без нового состояния).
