# RFC — Progressive Object Understanding

Status: Proposed
Date: 2026-08-07

## 1. Summary

Progressive Object Understanding (POU) — алгоритм, посредством которого Point постепенно увеличивает полезное понимание произвольного входа.

Главный принцип:

> Point не пытается понять объект целиком.
> Point ищет следующее знание, которое с наибольшей вероятностью расширит пространство полезных действий.

После получения знания алгоритм пересматривает состояние Graph и может выбрать следующий шаг.

Поэтому понимание является циклическим и потенциально неограниченным:

    State
      ↓
    Discover
      ↓
    Merge
      ↓
    Re-evaluate
      ↓
    Discover
      ↓
    ...

Пользователь может останавливать или продолжать этот процесс через UI:

    Понять
    Понять сильнее
    Понять ещё сильнее
    ...

---

## 2. Не является целью

POU не пытается:

- полностью классифицировать вход;
- построить исчерпывающую модель мира;
- заранее найти все сущности;
- выполнить все возможные анализы;
- выбрать единственный правильный тип объекта;
- автоматически пройти бесконечную цепочку действий.

Цель — максимально полезно расширять состояние понимания при разумной цене.

---

## 3. State

На каждом шаге алгоритм получает:

    State =
        Objects
        + Facts
        + Relations
        + Evidence
        + Focus
        + Context
        + Investigation State

State представляет текущую модель того, что Point уже знает и что ещё не исследовано.

---

## 4. Candidate Discovery

На основании State генерируется множество потенциальных Discovery.

Discovery может быть направлен на:

- исходный Object;
- дочерний Object;
- область;
- Representation;
- Relation;
- группу объектов;
- конкретное неизвестное свойство.

Discovery не привязан жёстко к типу исходного объекта.

Пример:

    Photo

может породить разные кандидаты:

    QR detection
    OCR
    document geometry
    region detection
    visual understanding

Если после OCR найден номер:

    Text("AA1234")

то новое состояние может породить уже другие кандидаты:

    interpret as plate
    locate related vehicle
    search document context
    extract surrounding fields

Никакой список таких кандидатов не является глобальным исчерпывающим справочником.

---

## 5. Candidate generation is contextual

Один и тот же Discovery может быть бессмысленным в одном состоянии и очень полезным в другом.

Например:

    Photo
        → generic OCR

после обнаружения:

    Map
        → coordinate localization

а после Focus на конкретной области:

    Map
        → locate selected marker

Следовательно, Candidate Discovery строится из текущего состояния Graph, а не только из исходного MIME/type.

---

## 6. Ranking

Candidate Discovery оценивается по ожидаемой полезности.

Минимально учитываются:

- вероятность получить новое знание;
- вероятность, что знание изменит доступные действия;
- стоимость;
- latency;
- privacy;
- необходимость внешнего сервиса;
- наличие Focus;
- уже проведённые исследования;
- качество имеющегося Evidence.

Точная формула ранжирования не является частью Конституции.

RFC допускает несколько реализаций ranking, если они сохраняют эти свойства.

---

## 7. Cheapest useful first

При сопоставимой ожидаемой пользе предпочтение получает более дешёвый и менее рискованный способ.

Например:

    local CV
        ↓
    local OCR
        ↓
    local model
        ↓
    computer
        ↓
    remote model

Но это не фиксированная лестница исполнения.

Если состояние показывает, что дешёвый метод почти наверняка ничего не добавит, более дорогой метод может стать лучшим кандидатом.

---

## 8. External boundary

Discovery не должен автоматически пересекать границу внешнего сервиса только потому, что это повысило бы качество результата.

Внешнее выполнение должно быть отдельно видимым и разрешённым в соответствии с Конституцией и ADR.

Это правило является частью Candidate Ranking и Execution Policy.

---

## 9. Execute

Выбранный Discovery выполняется.

Результат может быть:

- новым знанием;
- новым Graph Object;
- новым Relation;
- Evidence;
- изменением статуса исследования;
- отсутствием найденного;
- противоречием;
- отказом.

Не каждый результат обязан становиться пользовательским результатом.

---

## 10. Merge

Результат не заменяет существующее знание автоматически.

Он добавляется в Graph с соответствующим Evidence.

Если два источника дают разные результаты:

    A = "AA1234"
    B = "AA1284"

они не должны молча превращаться в один факт.

Graph сохраняет конфликт и позволяет следующему Discovery или пользователю разрешить его.

---

## 11. Recursive expansion

После Merge Graph пересматривается целиком.

Любой новый Object может стать новым центром исследования.

Например:

    Conversation
       ↓
    Photo
       ↓
    Region
       ↓
    Vehicle-like interpretation
       ↓
    Plate
       ↓
    Text
       ↓
    Coordinates / identification / other actions

При этом не требуется иметь специальные runtime-типы:

    ConversationPhoto
    Car
    Cat
    LicensePlate

если существующих примитивов Graph достаточно.

---

## 12. Focus

Focus резко уменьшает пространство Candidate Discovery.

Без Focus:

    Photo
      → исследовать наиболее перспективные области

С Focus:

    Photo
      → исследовать именно указанную область

Focus может быть:

- region;
- crop;
- selected object;
- selected representation;
- другим указателем на часть состояния.

Focus не означает редактирование факта.

---

## 13. Progressive depth

Каждый пользовательский запрос «Понять сильнее» запускает новый виток оценки State.

Point не хранит заранее:

    depth = 1 / 2 / 3 / ...

Глубина — это фактическое количество итераций над состоянием.

Новый виток может выбрать совершенно другой механизм, чем предыдущий.

Например:

    Понять
      → OCR

    Понять сильнее
      → layout understanding

    Понять ещё сильнее
      → relation extraction

    Понять ещё сильнее
      → targeted external analysis

Это не обязано быть последовательностью заранее известных стадий.

---

## 14. Stop conditions

Остановка не определяется полнотой классификации.

Очередной Discovery может не запускаться, если:

- ожидаемая польза слишком мала;
- стоимость слишком высока;
- результат не изменит пространство действий;
- требуется согласие пользователя;
- отсутствует подходящий исполнитель;
- пользователь не запросил дальнейшее углубление.

Невозможность продолжить не означает, что объект «полностью понят».

---

## 15. Action discovery

После каждого Merge Planner пересматривает доступные Actions.

Поэтому:

    новое знание
        ↓
    новый Graph State
        ↓
    новые Actions

не является отдельным pipeline.

Например:

    Photo
      → обнаружен QR
      → QR открывает URL
      → URL открывает действия URL

или:

    Screenshot
      → обнаружена область карты
      → обнаружена координата
      → координата открывает действия Location.

---

## 16. Example: complex nested input

Input:

    Screenshot of conversation
        ↓
    message contains photo
        ↓
    photo contains vehicle
        ↓
    vehicle contains visible plate
        ↓
    plate contains text

POU не обязан выполнить всё это при первом открытии.

Он может сначала понять Conversation.

Пользователь может войти в Photo.

Затем:

    Понять

может обнаружить наиболее полезную структуру фотографии.

Следующий:

    Понять сильнее

может исследовать выбранную область автомобиля.

Следующий:

    Понять ещё сильнее

может найти номер.

То есть каждый объект внутри Graph становится потенциальной точкой продолжения.

---

## 17. Example: handwritten document

Input:

    distorted photo of handwritten document
    + stamps
    + signatures
    + tables
    + multiple semantic regions

POU не должен заранее решать:

    "это Excel"

Сначала могут появиться:

    Document
    Regions
    Text
    Dates
    Persons
    Numbers
    Stamps
    Signatures
    structural relations

После этого разные Actions могут использовать одно и то же состояние:

    export to Excel
    export to Word
    extract dates
    extract persons
    inspect stamp
    correct geometry
    etc.

Таким образом конечный пользовательский результат определяется не исходным MIME/type и не первым классификатором, а накопленным пониманием и выбранным действием.

---

## 18. Core invariant

POU должен сохранять следующий инвариант:

> Каждый новый шаг должен либо добавлять новое полезное знание, либо давать честное объяснение, почему дальнейшее исследование сейчас невозможно или нецелесообразно.

POU не должен уничтожать ранее полученное знание только потому, что новый метод дал другой результат.

---

## 19. Relationship to ADR-0001

ADR-0001 определяет Object Graph Runtime.

Этот RFC определяет только механизм Progressive Object Understanding внутри него:

    Graph State
        → Candidate Discovery
        → Ranking
        → Execute
        → Merge
        → Re-evaluate

RFC не переопределяет:

- смысл Object;
- Graph;
- Enrichment;
- Transformation;
- Object identity;
- пользовательские законы Point.

Изменение этих понятий требует изменения ADR.

---

## 20. Open implementation questions

Открытыми остаются:

- конкретная формула ranking;
- конкретный механизм генерации Candidate Discovery;
- конкретный набор фундаментальных Object primitives;
- структура Evidence;
- конкретная модель investigation state;
- оптимальный баланс local / computer / remote execution;
- конкретная визуализация прогрессивного понимания.

Эти вопросы не должны решаться добавлением новых мировых сущностей в Graph.

---

## 21. Success criterion

POU считается успешным, если один и тот же механизм способен работать с:

- текстом;
- фотографией;
- визиткой;
- картой;
- документом;
- рукописью;
- PDF;
- архивом;
- голосом;
- музыкой;
- перепиской;
- вложенным объектом;
- комбинацией объектов;

не имея отдельного алгоритма верхнего уровня для каждого класса входа.

Главный тест:

> Может ли результат одного шага стать входом следующего шага без заранее известного предела глубины?

Если да — механизм сохраняет универсальность Point.
