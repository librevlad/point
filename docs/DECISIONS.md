# Point v0.2 — Принятые решения

ТЗ (`../point-v0.2-spec.md`) оставляет 4 вопроса «нужен твой выбор до старта» и
просит предлагать улучшения с компромиссами. Ниже — решения, принятые автономно
(взяты рекомендованные варианты, где ТЗ их отмечает), с обоснованием. Любое можно
пересмотреть — фактуру для этого я и выкладываю.

---

## Открытые вопросы ТЗ

### 1. Flow Graph: вывод из контрактов Executor'ов ✅ (рекомендация ТЗ)
**Решение:** графа как хранимой сущности нет; `bubblesFor(state)` фильтрует
Executor'ы по `accepts(state)`.
**Компромисс:** теряем «глобальную карту переходов» одним взглядом (её можно
восстановить обходом registry). Взамен убираем целый класс багов «граф и
executors рассинхронены» и получаем требование «заменить Executor цепочкой
capability без правок UI» бесплатно.

### 2. Модули: единый `:executors` на MVP ✅ (рекомендация ТЗ)
**Решение:** все Executor'ы — пакетами внутри одного `:executors`, строгие
интерфейсы дают заменяемость.
**Компромисс:** per-executor multi-module даёт максимум изоляции, но плодит
Gradle-оверхед и замедляет сборку. Пакеты + интерфейсы = та же заменяемость
дешевле; дробить на модули позже тривиально (граница уже есть).

### 3. Process death в середине флоу: терять флоу ✅ (рекомендация ТЗ для MVP)
**Решение:** флоу не персистим; при смерти процесса теряется.
**Обязательное условие:** `ObjectStore.clear()` всё равно должен отработать
(scratch не должен утекать). Персист стека `FlowFrame` — задача пост-MVP.

### 4. AiExecutor — типы вывода в v0.1: минимум text/markdown → файл ✅
**Решение:** материализуем markdown-ответ модели в `.md` файл в scratch и
возвращаем как `ResultObject(type = TEXT)`.
**Компромисс:** богатые выводы (таблицы → xlsx, image-gen и т.п.) откладываем;
единый путь «ответ → файл в scratch → снова объект в графе» проверяется на самом
дешёвом случае.

## Улучшение сверх ТЗ (с компромиссом)

### Ядро полностью без Android — `ScratchRef` и `ingest(String)`
ТЗ пишет `PointObject(uri /* в scratch */)` и `ObjectStore.ingest(uri: Uri)`, но
одновременно требует, чтобы `:core:model` был «без Android API» и чтобы ядро было
юнит-тестируемо fakes.

`android.net.Uri` в сигнатуре контракта затянул бы Android (и Robolectric) в
«чистый» слой. Поэтому:
- в `:core:model` ссылка на scratch — `ScratchRef(String)`, а не `Uri`;
- `ObjectStore.ingest(sourceUri: String)` принимает строку; `android.net.Uri`
  превращается в строку на границе `:app`/`ShareActivity`, а `:data` парсит её
  обратно через `Uri.parse`.

**Выигрыш:** весь `:core` (model + flow) компилируется и тестируется как обычный
Kotlin, без Android runtime — ровно то, чего требует принцип «max interfaces».
**Компромисс:** одно строковое преобразование Uri↔String на границе. Считаю
оправданным.

### Ещё две правки контрактов (при реализации среза 1)
1. **`Executor` несёт своё представление** — `val icon` и `fun title(state)`.
   Иначе реестру пришлось бы держать отдельную карту `executorId → (icon, title)`,
   а это тот самый анти-паттерн «отдельная таблица», от которого мы уходим. Теперь
   `bubblesFor` собирает `Bubble` целиком из самого Executor'а. Компромисс: немного
   презентации протекает в доменный контракт — но `Bubble` в модели и так несёт
   `icon/title`, так что граница уже была признана.
2. **`ObjectStore.ingest(sourceUri, mime)`** — добавлен `mime`. Store не должен
   угадывать тип; MIME известен из Share-интента, и на нём store сразу считает
   начальное состояние через инжектированный `ObjectClassifier`. Это и есть
   «первая отрисовка по нулевым сигналам».

## Решения среза 2

### `ExecutorResult.Done(message)` — терминальные действия
Share/Save не создают новый объект. Втискивать их в `Success(ResultObject)` =
дублировать текущий объект в стеке. Добавил случай `Done`: действие завершено,
нового фрейма нет, UI показывает подтверждение. Sealed-контракт остаётся честным.

### Share/Save — без Activity-контекста
Наивно executors нужен Activity, чтобы запустить share sheet / SAF. Решение: оба
работают через `@ApplicationContext`:
- **Share** — `startActivity(chooser)` с `FLAG_ACTIVITY_NEW_TASK`; scratch-файл
  отдаётся как `content://` через `FileProvider` (raw `file://` кинул бы
  `FileUriExposedException`).
- **Save** — MediaStore Downloads (API 29+, без permission по scoped storage); на
  API<29 — app-external Downloads (тоже без permission).
Executors инжектируют контракты `Sharer`/`Exporter` (в `:core:flow`), реализация в
`:data`. Никакой Activity в executors — независимость сохранена.
**Компромисс:** Save на API<29 пишет в app-scoped Downloads (менее «публично»), но
без грязного дэнса с `WRITE_EXTERNAL_STORAGE`.

### Gemini — HttpURLConnection, без SDK
Взял `HttpURLConnection` + встроенный `org.json` вместо Gemini SDK/OkHttp: ноль
новых зависимостей, полный контроль над inline-data (лимит 15 МБ на вложение).
Модель — `gemini-2.0-flash` (константа в `GeminiLlmClient`). Ключ пустой → падение
с понятным сообщением до сети.

### TranslateExecutor через `LlmClient`
Отдельный движок перевода (ML Kit + скачивание модели) — лишний вес. Перевод текста
идёт через тот же Gemini с промптом. Executor остаётся независимым — просто
использует контракт `LlmClient`.

### PDF→текст — реализовано (срез A) через PdfBox-Android
В Android нет встроенного извлечения текста из PDF (`PdfRenderer` даёт только
растровые страницы). Взял **PdfBox-Android** (`com.tom-roush`) за контрактом
`PdfTextExtractor` (в стиле прочих side-effect'ов): `PdfExecutor` для PDF извлекает
текст, `TranslateExecutor` — извлекает и переводит. Скан без текста → `Failure(
recoverable)` с подсказкой про OCR.
**Компромисс:** PdfBox бандлит шрифтовые ресурсы → debug-APK вырос ~15.8 → 24.5 МБ.
Приемлемо; при желании ужать R8/shrinkResources в release или сузить набор
ресурсов. iText не взял из-за AGPL.

## Решения среза 3 (progressive disclosure)

### Обогащение — отдельные `Enricher` + рантаймер, а не в классификаторе
Нулевые сигналы (`ObjectClassifier`) и дорогой peek — разные фазы (спека: первый
экран ≤300 мс без I/O, затем async). Поэтому обогащение вынесено в контракт
`Enricher(appliesTo, enrich)` + `Enrichment`, запускается VM **после** первого
кадра. Enricher только добавляет `Feature` (никогда не убирает) — состояние
монотонно обогащается.

### Пузырьки уточняются через `accepts` по фичам, не отдельной картой
`OpenUrlExecutor.accepts = kind==URL || has(HAS_URL)`. Появление пузырька после
обогащения — это тот же вывод графа из контрактов: обновили состояние →
`bubblesFor` вернул больше. Никакой отдельной логики «когда показать» нет.

### VM обновляет фрейм in-place и только если объект ещё на вершине
`enrichInBackground` пересобирает верхний `FlowFrame`, но лишь когда `top.obj.id`
совпадает — если пользователь уже ушёл вперёд по стеку, результат обогащения
игнорируется (без гонок). Bounded-peek (64 КБ текста / 200 записей zip) держит
обогащение дешёвым.

### Enrichers cheap-peek, но лежат в `:data`
Технически `TextUrlEnricher`/`ZipImagesEnricher` — чистый JVM (java.io + zip) и
тестируются на JVM. Оставил их в `:data` как «работа с содержимым файла» (side-
effect-адъяцент), чтобы `:core` остался про контракты и модель.

## Решения среза «полировка + расширения»

### Порядок пузылков — `Executor.order`, а не сортировка снаружи
Порядок был недетерминирован (итерация Hilt-`Set`). Дал каждому Executor'у `order`
(по умолч. 50), реестр сортирует по `(order, id)` — тай-брейк по id гарантирует
стабильность даже при равных order. Логика остаётся в самих Executor'ах
(распределённо), а не в отдельной карте.

### 7z/rar — по магическим байтам, не по имени
7z (`SevenZFile` + tukaani-xz) и rar (junrar) не поточные, поэтому вынесены из
общего commons-compress-пайплайна; формат определяется сигнатурой файла, а не
расширением (надёжнее). rar5 у junrar — best-effort.

### office→PDF — переиспользование рендера текста
`PdfExecutor` для OFFICE извлекает текст (тем же `OfficeTextExtractor`) и гонит
через общий `renderTextToPdf`. Форматирование теряется (текст-only PDF), но без
тяжёлого office-рендер-движка это разумный компромисс.

### Альтернативный ИИ — фолбэк-цепочка, не переключатель
`LlmClient` = `FallbackLlmClient(listOf(gemini, openai))`: пробуем по порядку,
первый успех выигрывает. Прямо лечит пойманный на устройстве **429**: если Gemini
исчерпал квоту, запрос уходит в OpenAI-совместимый провайдер. `OpenAiLlmClient`
берёт base URL/модель из конфига — работает с OpenAI, OpenRouter и локальным
сервером. Пустой ключ провайдера → он пропускается; если все упали — показываем
объединённую ошибку.

## Решения среза «платформа: Capability ≠ Realizer»

> Терминологический сдвиг: то, что в разделах выше называется `Executor`, теперь
> разрезано на **`Capability`** (что можно) + **`Realizer`** (как это сделать).
> Старые записи не переписываю — они фиксируют решения в терминах своего времени.

### Разрез Executor → Capability + Realizer + Resolver + BubblePolicy
**Решение:** `Capability` = декларация (id, icon, meta, accepts/produces) — её
видят UI, Flow Graph, Bubble Policy. `Realizer` = поведение (`perform`) за
`Resolver`'ом. UI/граф **никогда** не зависят от реализации.
**Зачем (CTO-видение):** завтра у одной capability будет несколько realizer'ов
(local / AI / cloud / Internet Capability Graph) — их выберет `Resolver`, и ничто
выше него не изменится. `BubblePolicy` вынесена отдельной чистой функцией
(сегодня детерминированная сортировка, завтра ML/LLM — без правок реестра/UI).
**Компромисс:** больше файлов (каждое действие = пара классов) и один лишний слой
косвенности. Окупается тем, что это единственный шов, куда встают cloud/ICG.

### `produces()` — подсказка, а не истина
`produces(state)` теперь nullable и **необязателен**: истинное следующее состояние
переклассифицируется из реального выходного объекта. Закрывает непредсказуемый
выход AI (`AiCapability.produces == null`) без спец-кейсов в графе.

### `CapabilityMeta` — одни поля для четырёх задач
`priority/cost/latency/network/auth` читают сразу ранжирование (BubblePolicy),
выбор реализации (Resolver), будущий paywall (Pro-capability) и бюджет первого
экрана (`network=true` держит действие вне ≤300 мс). Один seam — четыре
потребителя, ни один не меняется, когда завтра его прочитает ICG.

## Решения среза «История + Избранное» (метрика: меньше переключений)

Северная звезда (задана заказчиком): *каждый релиз должен уменьшать число
переключений между приложениями*. Оба решения ниже прошли этот фильтр.

### История — «журнал потока», файловый, без Room
**Решение:** `HistoryStore` (контракт в `:core:flow`) + `FileHistoryStore`
(`:data`): персистентная копия каждого принятого объекта + append-only
`index.jsonl`. Point получил **launcher-домашний экран** (`HomeActivity`) со
списком недавних — объект можно переоткрыть и продолжить работу **без повторного
шаринга из приложения-источника**.
**Зачем:** прямой минус переключений; и этот журнал — субстрат сразу для
Избранного, Analytics и обучающих данных для ML-BubblePolicy (четыре пункта одним
примитивом).
**Компромисс:** без Room (проще, юнит-тестируемо через инжектируемый `@HistoryDir`;
`org.json` в тестовый classpath). Хранит копии → растёт диск; чистка — задача
пост-MVP. Point эволюционировал из «только share-target» в «место, которое
открывают» — отсюда и launcher-иконка.

### Избранные цепочки — реплей последовательности capability
**Решение:** `FavoritesStore` + провенанс во `FlowFrame` (`viaCapability/viaTitle`)
= журнал того, какая capability произвела кадр. Сохранил последовательность
(авто-имя из подписей) — применяешь к новому объекту в один тап; реплей идёт по
`Resolver`'у, останавливается на `Done/Failure/NeedsInput`.
**Зачем:** повтор частой цепочки в один тап = минус шаги/переключения.
**Компромисс:** цепочка со `NeedsInput` (AI) прерывается — осознанно, без «тихой»
автоматики с вводом.

## Решения среза «офлайн + Claude»

### Claude как фолбэк после Gemini — нативный API, без SDK
**Решение:** цепочка провайдеров стала `Gemini → Claude → OpenAI`.
`ClaudeLlmClient` говорит на **нативном Anthropic Messages API** через
`HttpURLConnection`+`org.json` (не OpenAI-шим, не SDK — как Gemini/OpenAI-клиенты,
чтобы не раздувать APK). Картинки/PDF — base64-блоками (OCR/vision работают и через
Claude). Модель конфигурируема (`CLAUDE_MODEL`, по умолч. `claude-opus-4-8`).
**Компромисс:** HTTP-клиент нельзя юнит-тестировать (как Gemini/OpenAI); покрыта
логика фолбэка и realizer'ов, сам вызов — тонкая обвязка.

### Офлайн-OCR первым, облако — фолбэком («и то, и то»)
**Решение:** «Распознать текст» развязан от облака. `TextRecognizer` (контракт) +
on-device Tesseract (`rus+eng`, модели в assets → filesDir при первом запуске).
`OcrRealizer` пробует **устройство** первым (бесплатно, офлайн, без квот); только
если распознал пусто — уходит в облачный `LlmClient` (таблицы → Markdown).
**Зачем:** прямое лечение «Gemini 429 → приложение бесполезно» — ключевая фича
перестаёт зависеть от квоты/сети/ключа. `OcrCapability` стала `FREE`/без network.
**Компромисс:** APK +~14 МБ (нативный движок + модели); ограничил ABI до
`arm64-v8a`+`armeabi-v7a`. Качество распознавания проверяется на устройстве
(нативный вызов — тонкая обвязка; логика офлайн→облако покрыта фейками).

### Движок OCR: tess-two → tesseract4android (Tesseract 5)
**Решение:** сначала взял `com.rmtheis:tess-two:9.1.0` (на Maven Central), но на
устройстве его движок (Tesseract 4.1.1, 2019) **не инициализировал** LSTM-модели
`tessdata_fast` — подтверждено `run-as` (модели на месте, полного размера) и
logcat (`Could not initialize Tesseract API`). Перешёл на живой
**tesseract4android** (Tesseract 5, jitpack) — тот же пакет
`com.googlecode.tesseract.android` (только `recycle()` вместо `end()`), читает
текущие модели.
**Компромисс:** зависимость с jitpack (добавлен репозиторий) — не Maven Central,
но это поддерживаемый форк с нужным движком.

### Фото → скан — чистый `ScanFilter`, realizer тонкий
**Решение:** «Скан» = grayscale + **Otsu-бинаризация** в чистом `ScanFilter`
(ARGB int[], без Android) — юнит-тестируется напрямую; `ScanRealizer` — тонкая
Bitmap-обвязка. Выход — IMAGE, чтобы дальше уходил в «В PDF»/Save/Share.
**Зачем:** и полезная фича, и чистый вход для Tesseract (ч/б повышает точность).

### Распакованный архив — объект-коллекция (`ObjectKind.COLLECTION`)
**Решение:** «Распаковать» больше не терминальна: `ArchiveRealizer` отдаёт
`Success(ResultObject(COLLECTION, "inode/directory", <scratch-dir>))`, и флоу
продолжается на самой коллекции. Над ней работает первое коллекционное действие
`SaveAll` («Сохранить всё»); одиночные Share/Save/AI для COLLECTION скрыты
(`accepts(state.kind != COLLECTION)`). `ArchiveExtractor.extract` теперь
возвращает каталог (`ScratchRef`), а не число файлов.
**Развилка:** как сохранить kind COLLECTION через `ObjectStore.put`, который
переклассифицирует результат из **реального выхода**, а не из `ResultObject.type`
(инвариант «состояние выводится, не хранится»). Научил **классификатор** маппить
`inode/directory → COLLECTION` — источник истины о kind остаётся один, инвариант
цел. Альтернативу «`put` уважает `ResultObject.type`» отверг: раздваивает источник
истины и ломает переклассификацию.
**Зачем:** коллекция — объект первого класса, поэтому «сохранить всё / поделиться
всем / OCR по всем» подключаются как обычные Capability — граф расширяется сам.

### «Открыть» — внешнее приложение (ACTION_VIEW), не встроенный просмотрщик
**Решение:** «Открыть» = отдать объект системе через `ACTION_VIEW` (FileProvider
content-Uri + read-grant, `startActivity(NEW_TASK)`) за контрактом `Viewer`
(`:core:flow`) → `AndroidViewer` (`:data`, зеркалит `AndroidSharer`: VIEW вместо
SEND). Терминальное `Done`. Показывается на всех файловых объектах, кроме `URL`
(своё «Открыть ссылку») и `COLLECTION` (каталог внешне не открыть). `priority=65` —
среди «стоков» (open/save/share/ai), после трансформаций типа.
**Развилка:** встроенный просмотрщик текста (в духе «не выходим из приложения») vs.
системный intent. Выбрал системный — по решению владельца: меньше кода, работает для
любого типа, привычный жест «Открыть в…». Компромисс: для плейн-текста внешние
вьюеры слабые — встроенный просмотр может вернуться позже отдельным действием.
**Мелочь:** чтобы TEXT с URL (`HAS_URL`) не показывал два «Открыть», старое `OpenUrl`
переименовано в «Открыть ссылку», новое — «Открыть».

### Коллекция: просмотр содержимого + вход в элемент (роадмап #2)
**Решение:** COLLECTION перестала быть тупиком с одним «Сохранить всё» —
`FirstScreen` рисует список её элементов, тап уводит в обычный флоу на выбранном
файле. Перечисление — `ObjectStore.children(collection)` (файлы scratch-каталога,
уже материализованы → оборачиваем без копии, mime по расширению). Элементы грузятся
async и живут на `FlowFrame.items`; вход = `pushFrame(item)` (навигация, `via=null`,
в цепочку не попадает).
**Развилки:** (1) `children` — на `ObjectStore`, а не отдельный `CollectionReader`:
scratch-IO уже там (`ingest`/`put`), лишний контракт не нужен. (2) items — на
`FlowFrame` (едут с фреймом в `AnimatedContent`), а не в общем `FlowUiState`. (3)
Вход в элемент — переиспользуем стек фреймов, отдельного «экрана коллекции» нет.
**Зачем:** прямое попадание в «Северную звезду» — содержимое архива обрабатывается
внутри Point (открыть/OCR/сохранить поштучно), без файлового менеджера. Только что
добавленное «Открыть» становится полезным именно здесь.

### Встроенный просмотр текста — инлайн-панель, не действие/экран
**Решение:** TEXT-объект показывает своё содержимое прямо на `FirstScreen` —
прокручиваемая панель с родным выделением/копированием (`SelectionContainer`),
пузырьки остаются снизу. Симметрично просмотру коллекции: контент грузится async и
живёт на `FlowFrame.textPreview`; чтение — `ObjectStore.readText(obj, limit)`,
bounded (100k символов, не тянем большой файл в память).
**Развилки:** (1) инлайн-панель, а не отдельное действие «Читать» с новым
`ActionResult`/экраном — текст виден сразу, без лишнего тапа, и не трогаем sealed-
иерархию результата. (2) `readText` — на `ObjectStore` (там уже scratch-IO), не новый
контракт. (3) Копирование — родным Android-выделением, без своей кнопки.
**Зачем:** закрывает исходную боль «неудобно работать с плейн текстом» и «Северную
звезду»: результат OCR/извлечения/AI/перевода и .txt из архива читаются в Point, без
внешнего вьюера. Внешнее «Открыть» остаётся тем, кому нужен другой редактор.

### PDF-страницы как коллекция (роадмап #2, закрытие)
**Решение:** «Страницы» (`PagesCapability`, accepts PDF) рендерит каждую страницу в
JPEG (нативный `PdfRenderer`, ~144 DPI, белый фон) в свежий scratch-каталог и
оборачивает его в `COLLECTION` — тот же шов, что распаковка архива
(`Success(ResultObject(COLLECTION, "inode/directory", dir))`). Дальше — существующий
просмотр коллекции: страницы как IMAGE-элементы, поштучно Открыть/OCR/Сохранить.
**Зачем:** завершает Collection-as-Object (#2) — коллекция теперь и из PDF, не только
из архива; переиспользует весь UI/флоу. `PdfRenderer` — платформенный, без новой
зависимости (в отличие от PdfBox для текста).

### Paywall — это Realizer, выбираемый Resolver'ом (роадмап #3)
**Решение:** гейт Pro-функций (`CapabilityMeta.cost == PAID`) реализован как выбор
реализации: `DefaultResolver` для PAID-capability, если пользователь не entitled,
возвращает `PaywallRealizer` (recoverable-апселл) вместо настоящего realizer'а.
Контракт `Entitlements` (`:core:flow`); дефолт `DefaultEntitlements` — всё разрешено
(пока ничего не продаём). Capability/Flow Graph/пузырьки не трогаем — Pro-действие
остаётся видимым, тап объясняет, что оно Pro.
**Развилки:** (1) гейт в `Resolver` («как» выбирается), а не фильтр в `BubblePolicy`
(«что» показывается) — сохраняем discovery Pro-функций. (2) Признак Pro — существующий
`cost == PAID` (уже на `AiCapability`), без нового поля в meta.
**Зачем:** первый монетизационный шов, ядро не тронуто; включается заменой
`DefaultEntitlements` на реальную проверку подписки (Play Billing / серверный чек).

### Обучаемая BubblePolicy — приоритет минус частота использования (роадмап #4)
**Решение:** `LearningBubblePolicy` заменяет детерминированную сортировку: эффективный
приоритет = `meta.priority − min(использований, 25)`, поэтому часто используемые
пузырьки уходят вперёд (в т.ч. через тир). При нуле использований — байт-в-байт старый
порядок (`priority, id`), деградация мягкая. Сигнал — `CapabilityUsage` (счётчики в
памяти + Properties-персист, `FileCapabilityUsage`, `@Singleton`); VM пишет
`usage.record` при каждом применении capability. `DefaultBubblePolicy` оставлен
(детерминированные тесты); в приложении биндится Learning.
**Развилки:** (1) формула `priority − boost(cap 25)`, а не «сортировка по частоте» —
приоритет остаётся смыслом, частота лишь подталкивает. (2) счётчики в памяти
(volatile-снимок), чтобы `rank` не делал IO на render-пути; персист — off-path в
`record`. (3) сигнал — простой счётчик применений, не полный ML (журнал истории —
следующий источник, когда понадобится).
**Зачем:** роадмап #4; ранжирование учится на реальном использовании, контракт
`BubblePolicy` крошечный — ML/LLM-политика встанет на тот же шов без изменений UI.

### Парсинг в Excel — LLM извлекает таблицу как TSV, пишем свой .xlsx
**Решение:** «В Excel» (IMAGE/PDF/TEXT → OFFICE) отдаёт документ в LLM с просьбой
вернуть таблицу как **TSV**, парсит строки и пишет **настоящий `.xlsx`** минимальным
OOXML-zip'ом без зависимостей (`OoxmlSpreadsheetWriter`, зеркалит OOXML-ридер).
Действие PAID/сеть → Pro под paywall-шов.
**Развилки:** (1) движок — **LLM**, а не классический CV/OCR: понимание структуры
таблицы у модели радикально лучше, а картинка/PDF уже инлайнятся в `LlmClient.run`.
(2) формат обмена — **TSV**, не CSV: табы/переносы надёжнее кавычек и не зависят от
локального разделителя (в ru-локали CSV — это `;`). (3) вывод — свой `.xlsx` без
Apache POI (как OOXML-ридер), а не `.csv`: корректно и без раздувания APK.
**Зачем:** «фото приказа/таблицы → Excel за одно действие», и результат — OFFICE-объект,
с которым флоу продолжается. Killer-часть — «продолжить работать», а не просто распознать.

### Сканер как фоллбек-цепочка Realizer'ов; тяжёлое — Capability Pack (DLC)
**Решение:** «варианты с фоллбеком» ложатся на существующий шов «несколько Realizer
на одну Capability»: `ScanCapability` получает фильтр-realizer (Ч/Б, всегда доступен,
`priority=90` — фоллбек) и, позже, предпочтительный OpenCV-realizer (авто-границы +
перспектива, `isAvailable()`-гейт, низкий priority) — `Resolver` берёт лучший
доступный, падая на фильтр, если OpenCV-пак отсутствует/не загрузился. OpenCV
выносится в отдельный модуль-**Capability Pack** (первый «DLC», пока встроенный).
Многостраничность («объединить страницы») — отдельное `MergePdf` (COLLECTION
изображений → один PDF), без тяжёлых зависимостей.
**Развилки:** (1) фоллбек — это `Resolver`/`RealizerMeta`, а не новый механизм. (2)
OpenCV — тяжёлый нативный DLC (+~40 МБ, качество детекции проверяется только на
устройстве), поэтому заводится отдельным сфокусированным шагом; фоллбек гарантирует
мягкую деградацию. (3) ML Kit Document Scanner отвергнут: это флоу с камерой, не
обрабатывает уже расшаренное фото.
**Зачем:** «фото → чистый документ» без жёсткой зависимости от одного движка; и это
первый реальный Capability Pack — валидирует роадмап-фазу 3.

### OCR — два реализатора через фолбэк-цепочку Resolver'а (роадмап #1 в проде)
**Решение:** device-first/cloud-fallback OCR вынесен из нутра одного `OcrRealizer` в
**два независимых реализатора** одной `OcrCapability`, выбираемых `Resolver`'ом:
`DeviceOcrRealizer` (Tesseract, `priority=10`, LOCAL) и `CloudOcrRealizer` (LLM-vision,
`priority=90`, CLOUD). Первое продовое воплощение пункта #1 роадмапа — «readied» шов
«несколько Realizer на одну Capability» стал нагруженным.
**Развилка (суть):** прежний фолбэк OCR — **output-based** («устройство распознало
пусто → облако»), а `Resolver` выбирал **один** реализатор *до* запуска по
`isAvailable()`. Наивный сплит потерял бы путь «трудный скан → облако» (устройство
доступно, но вернуло пусто — до облака бы не дошли). Поэтому шов обобщён:
`DefaultResolver` для capability с несколькими доступными реализаторами возвращает
`FallbackRealizer` — **цепочку**, где каждый передаёт следующему **только на
`Failure(recoverable=true)`**; первый не-defer результат (Success/Done/NeedsInput/
hard-Failure) выигрывает, все defer → последний. `DeviceOcrRealizer` на пустом
распознавании/сбое движка отдаёт recoverable-Failure → запускается `CloudOcrRealizer`.
Три исходных сценария сохранены (юнит-тесты обоих реализаторов + интеграционный
`OcrChainTest` через реальный `Resolver`).
**Почему recoverable-Failure как сигнал «дальше», а не новый тип:** он уже значит «шаг
не дал результата, можно иначе» — точное прочтение «пусть попробует следующий», без
расширения sealed-иерархии `ActionResult`. Действие с одним реализатором (share/save/…)
имеет цепочку длины 1 — ретрая нет, побочных эффектов не задваивает.
**Побочный выигрыш:** цепочка **строго улучшает scan-шов** — рантайм-сбой
предпочтительного OpenCV-realizer'а теперь падает на фильтр (раньше `isAvailable`-гейт
ловил только его отсутствие/незагрузку до запуска). Capability с одним реализатором
(20+ действий) возвращаются напрямую, без обёртки — поведение не изменилось.
**Компромисс:** `CloudOcrRealizer.isAvailable()` оставлен `true` — наличие ключа дёшево
здесь не узнать (`FallbackLlmClient` прячет провайдеров); отсутствие ключа всплывает
recoverable-Failure'ом из `perform`, как и во всём приложении. Прятать облако без ключа
до запуска — `LlmClient.isAvailable()` позже, когда понадобится (YAGNI).

## Решения фазы A — Point как объектно-ориентированная среда

Инвариант проекта (см. `ARCHITECTURE.md`): *Point не выполняет действия — изменяет
объекты в соответствии с намерением пользователя.* Незаменимы **Object · Intent ·
Flow**; всё ниже Intent (Capability/Executor/Resolver/ICG/модели) — сменяемо.

### ObjectRef — абстракция ссылки на объект (не привязанная к схеме)
**Решение:** ссылка объекта на его байты — `interface ObjectRef { val value: String }`
(`:core:model`); `ScratchRef` стал его сегодняшней (и единственной) реализацией. Поля
`PointObject.uri` / `ResultObject.uri` / `HistoryEntry.ref` перетипированы на `ObjectRef`.
**Зачем:** Point — среда, где объекты путешествуют между Capability и, со временем, между
устройствами и бэкендами исполнения; ссылка должна пережить любую конкретную схему.
Сегодня — локальный scratch-путь; завтра `content://` / `point://object/…` / `icg://…`
как **новые реализации `ObjectRef`**, а не костыли поверх ScratchRef.
**Почему дёшево:** интерфейс объявляет `val value: String`, поэтому все ~46 мест
`File(ref.value)` (16 файлов `:data` + 14 `*Action.kt`) скомпилировались **без единой
правки** (читают `value` через супертип); `newScratchFile()` по-прежнему отдаёт
конкретный `ScratchRef`. Проверено: `./gradlew test assembleDebug` зелёная, 69 тестов.
**Интерфейс, не `sealed`:** будущие реализации (напр. `ContentRef`) могут жить в других
модулях (`:data`), что sealed-иерархия запретила бы.
**Компромисс / будущий гейт:** пока все refs — scratch (локальные пути), доступ к данным —
`File(value)`. Как только появится нелокальная реализация, доступ к байтам пойдёт **через
`ObjectStore`**, а не дереференсом `value` как пути. Полный резолвер схем сейчас НЕ строим
(YAGNI) — введён только шов.

### Intent — средний член модели (пользователь выбирает намерение, не механизм)
**Решение:** введён `enum Intent { UNDERSTAND, PREPARE, SEND }` (`:core:model`) — «Понять /
Подготовить / Отправить». `Capability.intents(state)` объявляет обслуживаемые намерения,
`CapabilityRegistry.intentsFor(state)` даёт применимые. UI стал **intent-first**: экран
показывает 2–3 намерения; тап → одна capability запускается сразу, несколько — раскрываются
тем же bubble-UI. Путь: `Object → Intent → Resolver → Capability → Object`.
**Умный дефолт вместо 17 правок:** `intents(state)` выводится из уже объявленного
`produces(state)` — терминал (`produces===state` — возвращает **тот же** объект `state`,
напр. Share/Save) → SEND; TEXT/неизвестный-AI выход → UNDERSTAND; иначе → PREPARE. Поэтому
17 классов capability **не тронуты**; `pdf` корректно идёт в UNDERSTAND на PDF (извлечь
текст) и в PREPARE на картинке (в PDF) — через свой state-зависимый `produces`.
**Фикс #33 (терминал vs трансформация — по идентичности, не значению):** различие берётся
по **ссылке** (`===`), а не по значению (`==`). Причина: трансформация того же типа
(скан/сжатие: картинка → **новая** картинка) структурно равна входу, и наивный `==`
кидал «Скан»/«Сжать» в SEND — под «Подготовить» их не было видно («не предлагает из фото
сделать скан»). Терминал возвращает тот же `state` по ссылке → `===` их разделяет.
**Зачем (стабильность UX под ICG):** Intent — контракт того, что видит пользователь; всё
ниже (Capability/Realizer/Resolver/ICG/модели) сменяемо без изменения экрана. Это и есть
инвариант проекта (см. `ARCHITECTURE.md`).
**Компромисс:** `translate` по дефолту попадает в UNDERSTAND (produces TEXT); осознанно
оставлено (перевести = понять на своём языке), переопределяемо одной строкой при желании.

## Решения фазы B (Document Scan)

### Один жест: пачка фото → чистый PDF (#17)
**Решение:** отдельная capability `ScanPdfCapability` (COLLECTION → PDF,
«Сканировать в PDF»): чистит каждую страницу `ScanFilter` (grayscale + Otsu) и
собирает один PDF. Это killer-loop сканера **в один тап**, а не двухшаговая цепочка
«Скан всех → Объединить».
**Почему отдельная, а не чистка внутри MergePdf:** «Объединить в PDF» осознанно
остаётся «как есть» (цветные фото в PDF) — иногда чистка не нужна; сканирование —
явный отдельный выбор. Сборку страниц оба делят через общий
`imagesToPdf(store, dir, clean?)`; чистка — единственное различие (без дублирования).
**Чистка — fallback-тир:** `ScanFilter` (Otsu) всегда доступен; преимущественный
OpenCV-реализатор (авто-контур + перспектива) встанет позже как on-demand Capability
Pack (решение office-hours), Resolver предпочтёт его — UI не меняется.

## Решения по AI-провайдерам

### «Все бесплатные по максимуму» — самоактивирующаяся цепочка (#32)
**Проблема:** Gemini постоянно 429-ит и «ни разу не отработал»; падать было не на что.
**Решение:** один `OpenAiCompatibleClient` (config-driven: label + baseUrl + key + model)
размножен на бесплатных OpenAI-совместимых провайдеров — OpenRouter, Groq, Mistral,
Cerebras (+ generic OpenAI). `FallbackLlmClient` перебирает их по порядку. Каждый
включается сам, когда его ключ появляется в `local.properties` (`configured()` отбрасывает
безключевые). Порядок: vision-способные free первыми (для «Понять» по фото), Gemini —
последним (он и есть источник 429). Добавить провайдера = строка в `openAiProviders()` +
поля BuildConfig; новый код не нужен.
**Тест:** `configured()` — чистая, покрыта (безключевые выпадают, порядок сохраняется);
fallback-логика уже покрыта `FallbackLlmClientTest` (first-success / 429-fallback / all-fail).

### AI-сеть за одним тестируемым интерфейсом (#21)
**Решение:** HTTP вынесен за `HttpJson` (единственный реальный `UrlConnectionHttpJson`,
фейки в тестах). Три провайдера — `OpenAiCompatibleClient`, `GeminiLlmClient`,
`ClaudeLlmClient` — строят запрос и разбирают ответ поверх шва; сетевой boilerplate
больше не копируется в каждом. `Gemini` и `OpenAiCompatible` — config-injected
(ключ/модели через конструктор, не `BuildConfig`), поэтому unit-тестируемы
детерминированно даже на CI без ключей.
**Покрыто тестами:** разбор ответа, `4xx/5xx → ошибка`, пустой/битый JSON, таймаут
(пробрасывается, чтобы fallback продолжил), переключение моделей (`GeminiLlmClientTest`)
и провайдеров (`FallbackLlmClientTest`).

### «Открыть» — отдельное намерение, не «Отправить» (#42)
**Решение:** `Intent` расширен до `UNDERSTAND · PREPARE · OPEN · SEND`. «Открыть»/«Открыть
ссылку» (терминальные, `produces === state`) по общему дефолту падали в SEND, но открыть
= посмотреть/использовать здесь, а отправить = поделиться/сохранить наружу — разные цели.
`OpenCapability`/`OpenUrlCapability` переопределяют `intents()` → `{OPEN}`. Цвет — синий
(как их пузырь), иконка — OpenInNew.

### Свой AI-ключ (BYO) — по требованию, без постоянного меню (#19)
**Решение:** ключ/модель пользователя хранятся на устройстве (`UserKeyStore` → app-private
SharedPreferences, песочница; шифрование — харднинг позже). `UserKeyLlmClient` встаёт
**первым** в fallback-цепочку и читает ключ в рантайме: задан — его квота выигрывает; не
задан — отходит в сторону, работают встроенные dev-ключи. Экран (`KeyScreen`) вызывается
**по требованию** (AI без ключа → экран сам, через сообщение «задайте свой ключ») и с
**шестерёнки на Home** — не постоянное меню (в духе «без настроек»).
**Почему первым в цепочке, а не вместо BuildConfig:** одна сборка годна и для раздачи
(юзер-ключ), и для разработки (dev-ключи) — без флагов сборки.

### Метрика Северной звезды — приватный журнал по согласию (#20)
**Решение:** `UsageJournal` (app-private: JSONL + маркер-файл согласия) пишет **обезличенные**
события — SHARED (пришёл объект), ACTION (действие), COMPLETED (доведено до terminal в Point).
Метрика «меньше прыжков» = действий-на-объект (глубина цепочки) + доля COMPLETED (задача
закрыта в Point, а не уходом в другое приложение). **Только по согласию** (opt-in, дефолт off;
выключение стирает данные) и **только на устройстве** — ничего не отправляется. Тумблер и
сводка — на экране ключа. Ранжирование подсказок уже питает `CapabilityUsage`; журнал — про
измерение Северной звезды, не дублирует.

### Надёжные таблицы через структурированный JSON (#22)
**Решение:** «В Excel» просит модель вернуть **JSON-массив массивов** (структурированный
ответ, который модели дают надёжно), а не TSV-текст «на честном слове». `parseTable`
разбирает JSON, с **TSV-фолбэком** (старый формат тоже работает) и терпит ```-ограждение.
Чистая функция, покрыта тестом. Полный API json-mode (`response_format`) — дальнейшее усиление.

### Согласие перед отправкой в облако (#10)
**Решение:** ни один объект не уходит на облачный сервис без одноразового согласия. Гейт —
на уровне capability: `CapabilityMeta.network=true` («AI», «Перевести», «В Excel») перед
первым запуском показывает `ConsentScreen` («Отправить в облако?» + что/куда уходит), а не
диспатчит realizer. Согласие хранится на устройстве (`PrivacyConsent` → app-private флаг),
кэшируется в `FlowViewModel` (без I/O на каждый тап), после «Разрешить» повторно не
спрашивается. **Почему на уровне capability, а не realizer:** `network` — уже объявленный шов
(его читают BubblePolicy/paywall/first-screen), UI знает «облачность» без залезания в
реализацию; облачный OCR-фолбэк (device-first, `network=false`) сюда не попадает — отдельный
след для #23. В духе «без меню»: одно контекстное решение в момент, когда оно важно.

### История ограничена по объёму + ручная очистка (#8)
**Решение:** `FileHistoryStore` держит последние **50** объектов (больше, чем 30, что
показывает Home, — недавнее не теряется). После каждой записи `pruneToLimit` удаляет копии
вытесненных и **переписывает журнал** одной компактной строкой на выжившего (заодно
схлопывая дубликаты пере-записей). Раньше каждый расшаренный объект оставлял файл навсегда —
тихо забивая диск. Плюс кнопка «Очистить недавнее» на Home (`clearAll`, уже был в контракте).
**Почему @Singleton + Mutex:** prune — это read-rewrite журнала, две параллельные записи могли
бы его побить (тот же урок, что в #20); сериализуем записи мьютексом, стор — app-scoped.

### Убран мёртвый признак HAS_TEXT (#16)
**Решение:** `Feature.HAS_TEXT` удалён — его не выставлял ни один enricher и не читала ни
одна capability (жил только в `ObjectStateTest` как обобщённый образец `with/has`; тест
переведён на `HAS_URL`). Текстовость объекта выражается через `ObjectKind.TEXT` +
`ObjectStore.readText`, отдельный флаг лишь дублировал бы это. Точно по критерию issue
(«никто не выставляет и не читает»).
**След на будущее:** `ZIP_OF_IMAGES` — обратный случай: enricher его выставляет, но ни одна
capability пока не читает (потребителя нет). Под #16 не подпадает («выставляется»), оставлен;
это отдельный вопрос — либо задействовать в «сохранить все картинки из архива», либо чистить.

### Живые превью картинок в истории на главном (#56)
**Решение:** строка «Недавнего» показывает реальную миниатюру для картинок (`kind==IMAGE`
или `mime image/*`), иначе — иконку типа. Декод downsampled (`Bitmaps.decodeThumbnail`:
`inJustDecodeBounds` → степенной `inSampleSize` до ≤96px по длинной стороне) и EXIF-upright,
off-main (`Dispatchers.IO` внутри `LaunchedEffect(entry.id)`); иконка типа — плейсхолдер, пока
грузится / для не-картинок / при ошибке. Так 12MP-фото стоит сотни КБ, а не десятки МБ — без
OOM и без тормозов списка (перекликается с #18). `Bitmaps` остаётся в :executors (его видят и
:app, и :executors); чистая `sampleSize` покрыта юнит-тестом. Первая страница PDF — возможное
продолжение (нужен `PdfRenderer`, тяжелее), пока не делаем.

### Не падать по памяти на больших фото и толстых PDF (#18)
**Решение:** декод в путях обработки ограничен по размеру. `Bitmaps.decodeUpright` теперь по
умолчанию subsampled до `PROCESS_MAX_PX=1600` по длинной стороне (степенной `inSampleSize`,
результат <2×кэпа): 48MP-фото декодится как ~2000px, а не целиком — без OOM на слабых
устройствах. Затрагивает scan / compress / image→PDF / photos→PDF (все зовут `decodeUpright`).
OCR (Tesseract в :data, который не видит :executors) — со своим локальным bounded-декодом (кэп
2048, текст остаётся читаемым). PDF-растеризатор уже клампил размер страницы (2400px); добавлен
лимит числа страниц (`MAX_PAGES=100`) с логом усечения — толстый PDF не разносит память/диск.
Чистая `sampleSize` покрыта тестом (12MP→/2, 48MP→/4).
**След:** усечение страниц пока только в logcat; показать пользователю «первые 100 страниц» —
возможное продолжение (нужен канал сообщения из растеризатора).

### AI не отправляет вложение — vision-маршрутизация + строгий формат (#60)
**Симптом:** AI/Перевести/В Excel на картинке отвечали «вы не приложили изображение».
**Причина:** `FallbackLlmClient` берёт первый *успешный* ответ; бесплатные vision-модели
(gemma/pixtral, OpenRouter 50/сут) быстро вычерпываются → запрос проваливается в текстовые
модели (Groq llama-3.3, gpt-oss, cerebras), которым уходит `image_url`, но они его не видят и
«успешно» отвечают «нет вложения» — цепочка на этом останавливается.
**Решение:** (1) `LlmClient.canHandle(obj)` — image-объект идёт только в vision-провайдеры;
`OpenAiProvider.vision` выводится из имени модели (`isVisionModel`), OpenAI-совместимые не берут
и PDF (нет inline-PDF → к Gemini/Claude). (2) **Строгий контракт вместо ловли фраз** (по
требованию владельца): image-промпт содержит escape — «не видишь изображение → ответь ровно
`NO_IMAGE`», клиент проверяет маркер и трактует как провал → цепочка идёт к настоящей vision-
модели. (3) Если ни один провайдер не подходит — понятная ошибка, а не ложный ответ.
**Почему маркер, а не эвристика по фразам:** детерминированно и не даёт ложных срабатываний на
коротком легит-ответе (см. память prefer-strict-format-over-output-matching).

### OpenCV-скан как preferred-реализатор с fallback (#45)
**Решение:** «Скан» получил CamScanner-пайплайн на OpenCV (`OpenCvScan`: детект документа →
коррекция перспективы → адаптивный порог), обёрнутый в `OpenCvScanRealizer` (`priority=20`,
`isAvailable()=OpenCV загружен`). Делит capability `scan` с чистым `ScanRealizer` (90); Resolver
предпочитает OpenCV, а на recoverable-провал/недоступность падает на Otsu-фильтр — так пак
никогда не тупикует. Чистая геометрия углов (`orderCorners`) покрыта JVM-тестом.
**Грабли KSP (важно):** `@Binds @IntoSet fun(r: OpenCvScanRealizer)` рушил ВЕСЬ Hilt-модуль
(`error.NonExistentClass` на всех биндингах) — Dagger при аггрегации не может резолвить типы
нативного OpenCV-AAR, хотя kotlinc их видит. Обход: **`@Provides @IntoSet` в companion** —
конкретный тип только в теле метода, вне сигнатуры биндинга. См. память
[[ksp-provides-for-native-aar-types]].
**Осталось (следующий срез):** визуальная проверка качества **на эмуляторе** (картинки из
сети) + тюнинг порога/детекции; размер APK (OpenCV тащит нативные .so под все ABI) — вынести в
on-demand pack / ограничить `abiFilters` (созвучно #23).

### Живой busy-экран вместо статичного колеса (#62)
**Решение:** busy-экран показывает тикающий счётчик времени (доказательство «не завис») плюс
стадии, которые для облачного/AI-вызова (`busyNetwork`) честно сменяются: «Отправляю в облако…»
→ «Модель обрабатывает запрос…» → «Собираю ответ…». Без фейковых процентов — только то, что
реально знаем. `busyNetwork` берётся из `CapabilityMeta.network` там, где реально идёт сетевой
вызов: одиночное действие (`runOnObject`) и resume после `NeedsInput` (`submitAmendment`) —
именно там AI и отрабатывает.

### Сильная vision-модель первой для картинок (#22 follow-up)
**Решение:** для image-объектов `FallbackLlmClient` ведёт цепочку сильными vision-моделями
(Gemini/Claude/свой ключ, `strongVision=true`), а не бесплатными gemma/pixtral — те коверкают
плотные/рукописные/повёрнутые таблицы (печатные наименования путались с соседними колонками).
Для текста порядок прежний (бесплатные первыми, бережём квоту Gemini — #32). Сортировка
стабильная, внутри групп порядок сохраняется. **Компромисс:** облачная квота Gemini тратится на
картинки — оправдано: качество извлечения из фото критично, а объём image-запросов невелик.
Ортогонально: качество ещё сильно зависит от ориентации фото (повёрнутый плотный документ тяжёл
даже сильной модели) и от собственного топ-ключа пользователя.

### Триггер по выделению текста — PROCESS_TEXT (#72, Slice 1)
**Решение:** Point регистрирует `ACTION_PROCESS_TEXT` → появляется в системном меню выделения
текста в ЛЮБОМ приложении («правая кнопка по тексту»). `ProcessTextActivity` читает
`EXTRA_PROCESS_TEXT` (или READONLY-вариант) и вливает текст в поток тем же путём
`onShared(fileUri, "text/plain")`, что и Share (общий хелпер `cacheTextFile`). Ноль разрешений,
API 23+. Это **invocation-триггер** (по вызову пользователя), не слежка — первый срез плана
«правая кнопка для всего, без слежки».

### Сущности on-device → действия (#64/#66, Slice 2a)
**Решение:** TEXT-объект обогащается on-device детектом сущностей (ML Kit Entity Extraction за
Android-free контрактом `EntityExtractor`; `@Provides` — обход KSP-затыка с нативным AAR, как с
OpenCV). Найден телефон → пузырьки «Позвонить»/«Сообщение» (`tel:`/`smsto:`), email → «Написать
письмо» (`mailto:`) через существующий `UrlOpener` (ACTION_VIEW на схеме). Ровно шаблон
`TextUrlEnricher → Feature → OpenUrlCapability`. Работает и на OCR-скриншотах даром (OCR даёт
TEXT). Адрес/дата/карта — следующий срез. Без облака, без слежки.

### Действия из установленных приложений — inline app-picker (#66, Slice 3)
**Решение:** capability «Открыть в…» показывает **реальные установленные приложения**, которые
умеют открыть объект (из `PackageManager.queryIntentActivities` за контрактом `AppLauncher`),
**inline в Point** (не системный диалог), и запускает выбранное (явный компонент + FileProvider-
grant, как `Viewer`). VM перехватывает тап «Открыть в…» (как cloud-consent) → грузит обработчиков →
экран `appPicker` → выбор → `launch`. `<queries>` (VIEW/SEND) в data-манифесте — иначе Android 11+
вернёт пусто. Realizer — фолбэк (первое приложение) для не-интерактивных путей (реплей цепочки).
Дифференциатор #66: список из живого устройства, не выдумка LLM; работает на любом объекте.

### Буфер при открытии — триггер для мессенджеров (#72, Slice 4)
**Решение:** при открытии Point (`HomeActivity.onResume`, **foreground-only** — правило Android 10+)
читается буфер; если текст похож на действие (телефон/email/url) и новый — на Home показывается
**отклоняемый** баннер «Действие из буфера» → тап → текст-объект с действиями по сущностям. Это
триггер, который **достаёт мессенджеры** (там `PROCESS_TEXT` не работает / авто-линковка):
скопировал в приложении → открыл Point → действие. Никакого фонового слежения за буфером (его и
нельзя с Android 10); отклонённый текст не переспрашивается. Завершает набор invocation-триггеров
из брейншторма #72 (PROCESS_TEXT #74 + буфер).

### Синтез совместимости — bridged app-targets через одну трансформу (#79.1)
**Решение:** «Открыть в…» показывает не только прямые обработчики объекта, но и приложения,
достижимые через **одну трансформу** (`AppTarget.via`): для каждой capability, превращающей объект
в другой открываемый тип (image→PDF, image→текст…), — приложения для этого типа, помеченные
«<App> · PDF». Тап по такому: VM запускает трансформу (`resolver.realizerFor(via).perform` →
`store.put`), затем `AppLauncher.launch` уже конвертированного объекта — один жест. Ограничено
глубиной 1, on-device, без бэкенда. Первый proof вижена «Point синтезирует совместимость там, где
разработчики её не заложили» (#79). Мосты `File→localhost→URL` (Cast) и headless-исполнение —
отдельно/позже (дороже: foreground-service / узкий охват экспортированных компонентов).

### Брендовые шрифты — Manrope + Unbounded (#13)
**Решение:** текст/UI — **Manrope**, дисплей/бренд-моменты (вордмарк «Point», заголовки экранов,
consent/пикер приложений) — **Unbounded**. Оба вариативные `.ttf` в `core/ui/.../res/font/`,
грузятся по весам через `FontVariation` (API 26+, `@OptIn(ExperimentalTextApi)`). Шов `Brand`/
`Display` в `Type.kt` был заранее заготовлен — включение без правок остальных экранов. Убирает
«дефолтный системный шрифт» — единственную slop-метку из дизайн-ревью. Тёмная тема уже была
off-white (#E6E9F0), правка не нужна.

### Фиксы с живой WiFi-проверки (краш пикера, буфер, OCR-мусор)
Живая проверка на устройстве вскрыла три бага, которые юнит-тесты не ловили:
- **Краш «Открыть в…»:** одно приложение попадало и в прямые, и в bridged-хендлеры → дубль ключа
  в `LazyColumn` → `IllegalArgumentException`. Фикс: `distinctBy { packageName }` на объединённом
  списке (прямой обработчик выигрывает).
- **Буфер «ничего»:** чтение в `onResume` — до фокуса окна, а Android 10+ отдаёт буфер только при
  фокусе → null. Фикс: читаем в `onWindowFocusChanged(hasFocus)`. Плюс ослаблен гейт — предлагаем
  **любой** новый непустой текст (не только телефон/email/url), как ждёт пользователь.
- **OCR-мусор:** Tesseract на фото документа выдаёт gibberish (символы, 1-2 символьные фрагменты),
  а не пусто → fallback не срабатывал. Фикс: `looksLikeOcrGarbage` (мало букв / почти нет 4+
  буквенных слов) → recoverable Failure → облачный vision-OCR (читает фото куда лучше).

### Объекты-трансформеры (#85) + Capability Preview (#97) — рамка и Slice 1 (Text→QR)
**Рамка:** Point меняет **тип** объекта по явному действию («превратить в…»), открывая весь набор
действий нового типа. Архитектурно нового нет: трансформа = Capability, чей Realizer `produces`
объект другого kind; движок переклассифицирует реальный выход и выводит его пузырьки. Держим
инварианты: on-device, без слежки, Play-safe, LLM только по явному действию, и **Point остаётся
меню-глаголом** (не браузером/CRM/заметками — фильтр из #95).
**Slice 1 — Text/URL → QR-код:** контракт `QrEncoder` (:core:flow) → `ZxingQrEncoder` (:data:
ZXing pure-Java → BitMatrix → PNG, UTF-8 для кириллицы, ECC M, поля 2). `QrCapability`/`QrRealizer`
(:executors) `produces` IMAGE → открывается весь image-набор (сохранить/поделиться/открыть). ZXing —
обычный JAR (не native AAR), поэтому `@Binds` безопасен (в отличие от OpenCV/ML Kit — KSP не давится).
Длина ограничена (~1000 симв.) с понятной ошибкой вместо переполнения ZXing.

### Slice 2 — Address → Карта, Date → Событие (entity-действия как трансформы, #85)
Достроены отложенные сущности из плана «правой кнопки»: `Feature.HAS_ADDRESS`/`HAS_DATE`, маппинг в
`EntityEnricher`. **Открыть на карте** — `geo:0,0?q=<url-encoded>` через существующий `UrlOpener`
(как tel/mailto). **Создать событие** — `ACTION_INSERT` календаря не URI-схема, поэтому новый
контракт `CalendarInserter` + `AndroidCalendarInserter` (:data); заголовок = первая непустая строка
(ML Kit даёт факт даты, не распарсенный timestamp — время ставит пользователь; авто-время — позже,
вместе с Preview #97). **Язык модели:** `MlKitEntityExtractor` теперь выбирает модель по скрипту
(кириллица → RUSSIAN, иначе ENGLISH), клиент на язык кэшируется — иначе адреса/даты (и часть
телефонов) на русском тексте просто не детектились. Приоритеты пузырьков: map 15, event 16 (после
call/email/sms 12–14).

### Slice 3 — Capability Preview (#97)

### #97 — Capability Negotiation («почти доступно»)
Показываем не только доступные действия, но и **почти доступные** — с тем, чего не хватает. Шов:
`Capability.missing(state): String?` (дефолт null) — капабилити САМА объявляет короткую причину, когда
она в одном сигнале от применимости к state; возвращает null, чтобы не шуметь (не для каждого чужого
объекта). Registry: `latentBubblesFor(state)` = не-принимающие капабилити с `missing != null`,
сортировка по приоритету, cap = 2 (информирует, не захламляет). UI — тусклая секция «Почти доступно»
под пузырьками (иконка + «Действие · чего не хватает»), информационная (пока без one-tap-моста).
Первые честные near-miss: фото → «Перевести»/«Открыть ссылку» (нужно «сначала распознать текст» —
OCR раскрывает текст/ссылку). Набор растёт вместе с семантическими фичами (#89) — тогда появятся
«Создать контакт — нужен телефон» и подобные.

### «Убрать фон» — фото → прозрачный PNG (шаг 1 замены фона)
On-device вырезание объекта через ML Kit **Subject Segmentation** (`play-services-mlkit-subject-
segmentation`, едет через Play Services; модель качается при первом использовании — сбой деградирует
в recoverable Failure). Контракт `BackgroundRemover.cutout(path): ScratchRef` (:core:flow) →
`MlKitBackgroundRemover` (:data, `@Provides` в companion — держим ML Kit AAR вне KSP-агрегации, как
у entity/OpenCV). `CutoutCapability`/`CutoutRealizer` (:executors) `produces` IMAGE (PNG — **не JPEG**,
иначе теряется альфа). Edge cases: большое фото — bounded decode; поворот — EXIF-upright
(`decodeBoundedUpright`, общий с уроком OCR); нет объекта — почти-прозрачный foreground → понятная
ошибка «Объект на фото не найден». **Замена** фона на произвольную сцену = AI-редактирование, чего
бесплатные модели надёжно не умеют; честный путь — вырезать + подставить фон, который даёт
пользователь (свой снимок / цвет / размытие) — отдельный срез.

### «Размыть фон» — портретный эффект (самодостаточная замена фона)
Резкий объект поверх размытого оригинала — «заменить фон» без второй картинки. Общий контракт
`ImageCompositor` (:core:flow): `composite(subject, bg)` (рисует прозрачный вырез над фоном,
center-crop до кадра объекта) + `blur(image)` (дешёвый down→up-scale, без RenderScript). Реализация
`AndroidImageCompositor` (:data, чистый `android.graphics` → `@Binds` ок, не native AAR). `BlurBg*`
(:executors): cutout(remover) + blur(оригинал) + composite. Выход — PNG (альфа). `ImageCompositor`
переиспользуется для «Заменить фон» (со снимком-фоном) — следующий срез (нужен пикер второй картинки).
Проверено на эмуляторе: сборка+тесты зелёные, ставится и запускается, Negotiation-хинты рендерятся
живьём.

### «Заменить фон» — фон из снимка пользователя (пикер + композит)
Вырезать объект и положить на фон, который выбирает пользователь. Новый канал ввода **картинки**:
`ActionResult.NeedsImage(prompt)` → хост открывает системный фото-пикер. Пикер зарегистрирован через
`rememberLauncherForActivityResult(PickVisualMedia)` **прямо в `PointHost`** — ни одна Activity не
меняется; выбранный URI возвращается через существующий `submitAmendment(uri)` (переиспользуем канал
NeedsInput). `ReplaceBgRealizer`: `amendment==null` → NeedsImage; иначе `store.ingest(uri)` (пикер
даёт read-grant) → `cutout` объекта → `composite` на фон. VM чистит `needsImage` в
submit/cancel/pushFrame/back; replay цепочки не может авто-выбрать картинку → прерывается как
NeedsInput. Генерация произвольной сцены (AI) — вне охвата, бесплатные модели не тянут.

### #61 — PDF/текст → Word (.docx)
Редактируемый `.docx` из PDF (или текста). Контракт `DocxWriter.write(paragraphs): ScratchRef`
(:core:flow) → `OoxmlDocxWriter` (:data): руками собранный OOXML-ZIP из трёх частей
(`[Content_Types].xml`, `_rels/.rels`, `word/document.xml`), один `<w:p>` на строку — без Apache POI,
как у `OoxmlSpreadsheetWriter`. `Word*` (:executors): PDF → `PdfTextExtractor`, TEXT → файл; пусто
(скан без текст-слоя) → recoverable Failure с подсказкой распознать. Результат — OFFICE-объект
(docx-mime), дальше share/save/open/в-PDF. Валидность OOXML покрыта JVM-тестом (ZIP-части + экранизация).

### «Скопировать» в буфер + «Скопировать карту»
Терминальное копирование в системный буфер. Контракт `Clipboard.copy(text, label)` (:core:flow) →
`AndroidClipboard` (:data, `ClipboardManager`, запись только на переднем плане — Android 10+ гейт не
мешает). `CopyCapability` (TEXT/URL → весь текст), `CopyCardCapability` (`HAS_CARD` → только цифры
номера, через `EntityExtractor`). Добавлен `Feature.HAS_CARD` + маппинг `PAYMENT_CARD` в

### «Собрать данные» — все сущности текста в чистый список (#97)
Скрытая сила «собрать все телефоны/ссылки»: из текста с сущностями — сгруппированный, дедуп-нутый
список (Телефоны/Почты/Ссылки/Адреса) новым TEXT-объектом → копировать/поделиться. `formatEntities`
(pure, тестируемо) + `ExtractAll*` (:executors, `EntityExtractor` + `ObjectStore`). Зажигается на
TEXT с ≥1 сущностью (HAS_PHONE/EMAIL/URL/ADDRESS).

### «Считать QR» — декод QR с картинки (реверс генерации)
Скрин/фото с QR → его текст (обычно ссылка) → «Открыть ссылку». Переиспользуем ZXing (уже есть для
генерации): контракт `QrReader.decode(path): String?` → `ZxingQrReader` (:data, RGBLuminanceSource +
HybridBinarizer + TRY_HARDER; bounded+EXIF-upright). Пузырёк показываем **только если QR есть** —
async `QrEnricher` (:data) декодит и ставит `Feature.HAS_QR`, `ReadQrCapability.accepts(HAS_QR)`.
Результат — TEXT → дальше URL-enricher зажигает «Открыть ссылку». Двойной декод (enricher+realizer)
— осознанный размен на простоту.

### Прогрессивное обогащение с ценами + «скриншот оживает» (#64, ядро среза)
Понимание объекта теперь **планируется, а не просто запускается всё сразу**. У `Enricher` появилась
`EnricherMeta(cost: INSTANT/FAST/SLOW, mayYield, label)`; `Enrichment.enrich` возвращает
`Flow<EnrichmentUpdate>` (кумулятивные фичи+metadata + `running`-метки). `DefaultEnrichment` гонит
волны по возрастанию цены, внутри волны — параллельно, **эмитит после каждого завершения** — пузырьки
дорастают по одному, а не одним поздним батчем. SLOW-энричер запускается только если его `mayYield`
может открыть хотя бы одно новое действие на уже обогащённом дешёвыми волнами состоянии
(`CapabilityRegistry`-гейт): дорогое знание покупаем, только если оно меняет экран. Это минимальный
шов идеи «Planner/цена получения знаний» — без гипотез и байеса, пока энричеров мало.

Ядро ценности — `OcrEnricher` (:data, SLOW, «Распознаю текст…»): расшаренный скриншот **сам**
проходит on-device Tesseract → `EntityExtractor` → `HAS_PHONE/EMAIL/ADDRESS/DATE/CARD/URL` прямо на
IMAGE, без ручного «Распознать текст». Распознанный текст пишется в scratch один раз и живёт в
`metadata[META_OCR_TEXT_REF]` (sidecar): entity-реализаторы берут текст оттуда
(`entitySourceText`), `DeviceOcrRealizer` при явном «Распознать текст» отдаёт кэш мгновенно, без
второго прогона движка. Мусор отсеивает общий `looksLikeOcrGarbage` (переехал в :core:flow) — фото
еды остаётся фото. `ExtractAllCapability` отвязана от TEXT (гейт только по фичам). Скриншот-эвристики
нет сознательно: «мусорный» OCR на не-текстовых фото сам гасит результат, а гейт цен решает, когда
вообще запускать. LLM в авто-пути не участвует никогда (инвариант «LLM не на первом экране» цел;
облачный OCR — только явными пузырьками).

Фидбэк фоновой работы: `FlowFrame.enriching` (метки running) → строка-индикатор под объектом
(«Распознаю текст…» + мини-спиннер, AnimatedVisibility). `FlowViewModel` собирает Flow прогрессивно,
применяет апдейты **к фрейму по id, а не только к вершине** (поздний OCR доезжает в нижний фрейм — к
возвращению пользователя всё уже найдено), отменяет джобы при новом share/endFlow. Развилка «ML Kit
OCR вместо Tesseract» из текста #64 закрыта проверкой: ML Kit Text Recognition v2 **не поддерживает
кириллицу** (только Latin/CJK/Devanagari) — база остаётся Tesseract rus+eng, ML Kit годится лишь как
возможный ускоритель латиницы позже.

### #68 — 16 КБ страницы: выравнивание нативных библиотек (Play-блокер снят)
Все восемь `.so` (tesseract/leptonica/pngx/jpeg, opencv_java4, libc++_shared,
androidx.graphics.path, textclassifier3 из ML Kit) выровнены поднятием версий:
**tesseract4android 4.9.0** (NDK r27c; наша 4.8.0 с JitPack была собрана старым NDK),
**OpenCV 4.14.0** (официальный AAR с выровненными сегментами; 4.11 был «old NDK»),

Проверка — не вера в ченджлоги, а факт: свой Python-парсер ELF program headers по каждой
`.so` внутри APK (все PT_LOAD p_align == 16384) + проверка zip-оффсетов несжатых библиотек
(кратны 16 КБ). Прогон на эмуляторе: Tesseract 4.9 распознаёт (image → TEXT). Финальное
подтверждение — открыть Point на Android 16 (SM-A346E): системный диалог совместимости
больше не должен появляться.

### Захват экрана = только скриншот (решение владельца, #64)
Путь «прочитать текущий экран» (MediaProjection, `AccessibilityService.takeScreenshot`, роль
ассистента) закрыт навсегда: policy-риск Google Play и трение согласий не окупают выгоды.
Канонический вход — системный скриншот, расшаренный в Point: работает с первого дня, а после
прогрессивного обогащения скриншот «оживает» сам (OCR → сущности → действия прямо на картинке),
т.е. UX-разница с «настоящим» захватом почти исчезла при нулевом policy-риске. Floating-вход из
ROADMAP — отдельная тема со своей валидацией, к захвату экрана не относится. Оставшийся хвост
#64 — только структурный LLM-резерв для неклассифицированных фрагментов.

### Первый экран = «Point понял» (#114, срез 1)
Главный герой экрана — объект и его понимание, а не пузырьки. Под объектом — **карточка
понимания**: факты со значениями («✓ Нашёл телефон · +380…», «✓ Нашёл ссылку · github.com»),
выведенные чисто из состояния (`understoodFacts(obj)` в :core:ui, JVM-тест): entity-фичи берут
значения из `metadata[entity.*]` (энричеры теперь сохраняют первое значение каждого типа — раньше
выбрасывали), контентные фичи получают человеческую фразу («Это скан — текст не выделяется»).
Номер карты в карточке маскируется до «•• 5678». Running-метки #64 («Распознаю текст…») живут
**внутри той же карточки** со спиннером — «думает» и «понял» читаются одним монологом, и по мере
прогрессивного обогащения карточка растёт построчно на глазах.

Действия: сверху **топ-3 «Самые вероятные»** (ранжирует существующая обучаемая `LearningBubblePolicy`
— экран лишь уважает порядок; при ≤5 действиях показываются все), остальное — свёрнутое
**«Все действия (N)»**, раскрывающееся группами по уровням. Уровень — новое поле `Bubble.tier`
(`INSTANT`/`SMART`/`AI`), **выводится из `CapabilityMeta`** (network → AI; latency INSTANT → INSTANT;
иначе SMART), не назначается руками. AI-пузыри носят тихое tertiary-кольцо — «действие покидает
устройство» видно до тапа.

**Intent-first слой снят с экрана** (кнопки Понять/Подготовить/Открыть/Отправить и
`selectedIntent`-drill): новый экран отвечает на тот же вопрос информативнее — фактами и
ранжированными действиями, без лишнего тапа. Контракты `Capability.intents()`/`intentsFor` остаются
(классификация целей полезна графу); убран только UI-путь (`FlowUiState.intents/selectedIntent/
intentBubbles`, `onIntent`). `:core:ui` получил зависимость на `:core:flow` (разрешена модульным
правилом) ради `META_ENTITY_PREFIX` — бизнес-логики в UI по-прежнему ноль.

### Object Timeline + история типами (#114, срез 2)
Путешествие объекта стало видимым: над объектом — полоса-таймлайн «🖼 → 📄 → PDF» (`TimelineStrip`,
:app — узлы из стека `FlowFrame`, который и есть журнал пути). Тап по раннему узлу — `jumpTo(index)`
— мгновенный прыжок назад по флоу (мульти-pop одним движением). Полоса появляется только после
первой трансформации (≥2 шагов) и живёт вне `AnimatedContent`, поэтому при переходах стоит на месте,
пока объект под ней анимируется. `FlowUiState.path: List<PathStep(kind, via)>` пересчитывается из
стека в pushFrame/onBack/jumpTo. Философия «объект движется по состояниям» теперь буквально
нарисована на экране — лучший онбординг без единого слова. В Home вторая строка карточки начинается
с типа объекта («Изображение · 2 ч назад») — человек вспоминает объект, а не время (#114).

### История помнит понятое (#114, срез 3)
`HistoryStore.update(obj)`: когда обогащение корневого объекта завершилось, его понимание
(features + значения `entity.*` без префикса) доливается в существующую запись журнала — append
новой строки с тем же id (формат «последняя строка выигрывает» делает update бесплатным, копия
объекта и timestamp не трогаются). Старые строки журнала без новых полей парсятся с дефолтами.
Карточка Home показывает третью строку — «+380 67… · завтра 18:00» цветом бренда: объект
вспоминается по содержимому, не по имени файла. Деривация та же, что на первом экране
(`understoodFacts` поверх восстановленного PointObject) — одна логика, два экрана.

### Discover: «💡 Попробуйте…» (#114, срез 4)
Одна свёрнутая, ни разу не использованная возможность предлагается как открытие: чип
«💡 Попробуйте: Создать событие» между вероятными действиями и «Все действия (N)». Кандидаты — только
скрытая часть графа (за пределами `likelyCount`, теперь общего для экрана и VM) и только не-INSTANT
(мгновенные терминалы — слишком очевидны для «открытия»). Сигнал — существующий `CapabilityUsage`
(тот же, что кормит `LearningBubblePolicy`): использовал — счётчик стал ненулевым — подсказка сама
ушла, её место займёт следующая. Ноль новой инфраструктуры: Discover = проекция уже имеющихся
ранжирования и статистики. Тап по чипу запускает действие как обычный пузырёк.

### Motion M1 — живой объект и аура (MOTION.md, принципы №2/3/6/10)
Первый срез сенсорного языка. `AliveSurface` (:core:ui, Motion.kt) — живая рамка превью:
**дыхание** с физикой по типу (`breathSpecFor(kind)` — фото мягкое 1.008/4.2с, документ строгий
1.003/6с; чистая функция, JVM-тест), **кольцо-импульс** пока идёт обогащение (расширяется от
объекта и тает — принцип «не крутилка»), **аура** при первом понятом факте (тень плавно теплеет
из чёрной в брендовую — «Point понял» без текста). Спиннер в карточке «Понял» заменён на
пульс-точку бренда (`ThinkingDot`). Reduced motion (`ANIMATOR_DURATION_SCALE == 0`) статизирует
всю динамику (`rememberMotionEnabled`); infinite-анимации живут только в активной композиции.
Ноль новых зависимостей — Compose `InfiniteTransition`. Проверено видеозаписью с эмулятора:
пульс во время OCR, построчные факты, тёплая аура после понимания.

### Motion M2 — пузыри-частицы (MOTION.md, принцип №4)
Пузырь — частица, не кнопка. **Рождение**: вектор «центр объекта → слот» замеряется через
`onGloballyPositioned` (Compose-координаты layout'а, без гимнастик), пузырь вылетает из объекта
spring'ом со stagger'ом — «объект нашёл возможность». **Невесомость**: каждый пузырь дрейфует
±1.4–2.2dp со своим периодом и фазой (`driftSpecFor(index)` — чистая функция, JVM-тест: поле
никогда не движется единой решёткой). **Запуск**: тап утягивает пузырь обратно в объект
(`BUBBLE_DEPART_MS = 180`) и только затем диспатчит действие — осознанная цена правила
«микрорадость»; reduced motion (и превью, где якорь неизвестен) снимает и веер, и задержку —
всё мгновенно. Ноль новых зависимостей.

### Motion M3 — перетекание вместо разрыва (MOTION.md, принципы №8/9)
Быстрая локальная работа больше не выбивает полноэкранный BusyScreen: `quietWork(meta)`
(не network и не SLOW — чистая функция, JVM-тест) → `FlowUiState.busyQuiet` → объект остаётся
на экране и «работает» (то же кольцо-импульс M1), поле действий приглушается и блокируется от
повторных тапов. Облако и SLOW сохраняют полноэкранный busy с его staged-подбадриванием (#62).
Морф перехода: новый объект вырастает из старого — spring-scale от 0.80 + fade 340 мс, старый
уходит с лёгким увеличением (300–500 мс «видимого превращения», принцип №9). Пер-типовая
хореография (image складывается в страницу, буквы проступают при OCR) — отложена как M3.5.

### Первый экран: объект показывает себя (#114, «нет превью»)
Хедер первого экрана для IMAGE показывает реальную миниатюру (Bitmaps.decodeThumbnail, 640px,
EXIF-upright, off-main как textPreview/children), а не пиктограмму типа — в той же живой рамке
M1 (дыхание/кольцо/аура), крупнее (132dp). `FlowFrame.preview: ImageBitmap?` грузится асинхронно
и доезжает в фрейм по id. PDF-превью отложено: `PdfRasterizer` рендерит все страницы — дорого для
хедера; нужен лёгкий контракт «первая страница» (отдельный срез).

### PDF-превью первой страницы (#114, хвост «нет превью»)
`PdfRasterizer.rasterizeFirstPage(obj): ScratchRef?` — дешёвый рендер только первой страницы
(полный `rasterize` рендерит все — для хедера расточительно). Маршрутизация превью —
чистая `previewSource(obj, rasterizer)` (IMAGE → свой файл, PDF → первая страница, прочее →
null; JVM-тест): ошибки дают null — превью подарок, не обязанность.

### Motion M4 — хаптика: действие отвечает в руке (MOTION.md, принцип №7)
Контракт `SensoryFeedback` (:core:flow): ровно три момента — `tap` (выбор действия, сухой клик),
`success` (Done-терминал ИЛИ новая трансформация — подтверждающий тик), `failure` (короткий
двойной стук, никогда не злой длинный). Реализация `VibratorSensoryFeedback` (:data):
предопределённые эффекты системного Vibrator c `USAGE_TOUCH` — системная настройка «отклик
касаний» управляет всем, свой тумблер не нужен; любой сбой/отсутствие вибратора — тихий no-op
(отклик никогда не ломает флоу). VM зовёт в dispatch/handleResult (JVM-тесты: tap→success,
tap→failure, tap→success на Success). Фирменный **звук** — отдельный срез: нужны сэмплы
(тик/вууш/пульс) со вкусом владельца; шов уже готов — звук встанет в ту же реализацию.

### Motion M5 — живой фон (MOTION.md, принцип №5)
`Modifier.livingBackground()` (:core:ui): AGSL `RuntimeShader` (API 33+) — mesh двух брендовых
тонов (primary/tertiary, амплитуды 3.5–4.5%) поверх фоновой базы, период — минуты. «Дорого» =
едва заметно. Униформа времени обновляется ~8 раз/сек (`delay(125)`) — дёшево по батарее; ниже
API 33 или при reduced motion — статичный градиент той же гаммы. Подключено к корню `PointHost`
(экран флоу); композиция останавливается вне активного окна вместе с остальным Compose.

### «Понять глубже» — структурный LLM-резерв (#64, финальный срез)
Явный пузырёк (никогда не автоматически): TEXT или IMAGE с OCR-sidecar (вернулся `Feature.HAS_TEXT`
— теперь с настоящим потребителем: гейт текст-голодных действий на картинке; в облако уходит
ТОЛЬКО распознанный текст, никогда пиксели). Сеть → согласие #10 гейтит VM сам. Ответ — строгий
контракт `KEY=VALUE` (PHONE/EMAIL/URL/ADDRESS/DATE/CARD, `NONE` если пусто): детект по формату,
не по прозе (см. память prefer-strict-format). Находки мержатся в `entity.*` metadata тем же
объектом (тот же файл, шаг «понимание» в таймлайне), а новый `MetadataEntityEnricher`
(INSTANT, любой kind) зажигает от них фичи — «Позвонить»/«Создать событие» появляются для того,
что ML Kit пропустил; заодно переоткрытия из истории сохраняют свои действия без пересканов.

### Motion M3.5 + звук M4 (MOTION.md, принципы №7/9 — завершение)
**Хореография знаковых переходов**: transitionSpec различает пары состояний — «что-то → PDF»:
старый объект складывается в лист (scaleOut→0.06), страница разворачивается (expandVertically);
IMAGE→TEXT (распознавание): долгое спокойное проступание (fade 520мс). Остальные — общий M3-морф.
**Фирменный звук**: три синтезированных сэмпла (res/raw, 1–8 КБ) — tick 15мс/1.9кГц (сухой клик),
success 55мс (подъём 1150→1550Гц), failure 90мс (два низких бампа 210Гц). Сгенерированы кодом —
владелец может заменить файлы своим вкусом, не трогая код. SoundPool (USAGE_ASSISTANCE_SONIFICATION),
громкость 0.6; настройка «Звук действий» (default ON — узнаваемая ассоциация) в KeyScreen через
`SensorySettings` (prefs); хаптика тумблера не имеет — ей управляет системная настройка касаний.

### #7 — флоу переживает process death (p0-блокер снят)
`FlowSnapshotStore` (:core:flow) → `FileFlowSnapshotStore` (:data): один маленький JSON вне
scratch (инжектированный файл, JVM-тесты: round-trip / порча / clear). VM журналирует путь после
каждого шага (push/back/jump) И после находок обогащения — понимание переживает смерть вместе с
шагом; `endFlow` стирает снапшот вместе со scratch. Восстановление — в init VM: мёртвые файлы
отфильтровываются, фрейм собирается из (kind, mime, ref, metadata, via), фичи передерайвливаются
обогащением мгновенно (`entity.*`/sidecar в metadata уже есть). Гонка со свежим share решена
синхронным флагом до корутин: новый интент всегда побеждает вчерашний снапшот. Проверено настоящим
убийством процесса на эмуляторе: force-stop → холодный старт → тот же объект, тот же шаг, пузыри
и таймлайн на месте. DoD исполнен дословно.

### #66 срез 3 — пользовательские правила: закреплённое действие
Правило v1 = «для такого типа объекта — сначала вот это»: долгий тап по пузырьку закрепляет его
capability для текущего `ObjectKind` (повторный — открепляет). Контракт `PinnedActions`
(:core:flow, sync-чтение как `CapabilityUsage.counts`) → `PrefsPinnedActions` (:data).

usage (JVM-тест). Закреплённый пузырёк подписан «★» брендовым цветом; подтверждение — словами
(«Закреплено: X»/«Откреплено»). Богаче правила (по фиче/источнику) — за тем же швом. Ранжирование
внешних приложений внутри общего графа (срез 4 issue) — отдельно.

### #117 — метрики: стандартные и графовые, локально и по согласию
Расширен существующий privacy-first `UsageJournal` (события анонимны, только по opt-in,
ничего не покидает устройство): к стандартным счётчикам (объекты/действия/завершения +

### #66 срез 4 — приложения устройства как первоклассные узлы графа

### #115 срез 1 — drag-to-connect: объект соединяется с возможностью
Идея владельца: «не выбрал действие, а соединил объект с возможностью». Реализовано как
long-press-drag (жест переноса иконок лаунчера — уже в моторике пользователя): долгое нажатие
«поднимает» объект (хаптика + сжатие 0.92), он следует за пальцем; ближайший «вероятный» пузырёк

отпускание над ним запускает действие, в пустоте — объект пружинит на место. Tap не тронут —
drag это второй, физичный путь к тому же действию. Почему после long-press, а не сразу: первый
экран скроллится (#114), и вертикальный drag без удержания обязан остаться скроллом — Compose
отдаёт такой жест `verticalScroll`, и это правильно. Геометрия магнита — pure `magnetTarget`
(:core:ui, JVM-тесты); жестовый слой только кормит её позициями (`onGloballyPositioned` центры
пузырьков — тот же канал, что M2-вектор рождения). Вторая часть идеи #115 (пузырьки сами находят
место: вероятные ближе, AI дальше, локальные/облачные по сторонам) — отдельный срез радиальной
раскладки, не начат.

### #147 срез A — Point для ПК: ядро окупилось буквально

(инвариант Android-free сыграл дословно: та же модель объекта, те же контракты

### #116 — скан: страница ищется как яркая масса, не как рёбра
Жалоба владельца: «Скан» возвращал фото со скошенными углами и срезанным верхом. Корень — старый
детектор (Canny с константными порогами + `RETR_LIST` по полному кадру): тень от листа клеилась к
его контуру, внутренние линейки чека конкурировали с внешним контуром, а почти-полнокадровый quad
не отбраковывался. Новый `detectDocument` (всё — на копии ≤720px, углы масштабируются обратно):
**Pass 1 — бумага как ЯРКАЯ масса**: освещение выравнивается делением кадра на его же размытую
оценку (`GaussianBlur σ=90` → `Core.divide`, гасит градиент лампы/тени стола), затем Otsu +
`MORPH_OPEN` — тень темнее бумаги и приклеиться к странице не может в принципе. **Pass 2
(fallback)** — классическая карта рёбер (Canny с порогами от медианы яркости + `MORPH_CLOSE`),
для столов, сливающихся с бумагой по яркости. Оба паса → `RETR_EXTERNAL`, топ-6 контуров по
