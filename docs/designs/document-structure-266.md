# Структура документа и арифметическая улика: срез #266

Документ собирает разведку по коду и корпусу (31.07–01.08.2026) и решения, которые из неё
следуют. Он опирается на движок документов v3 (`docs/designs/document-engine-v3.md`) и ничего в
нём не отменяет: адрес значения, правила-свидетели, полнота по действию и корпусная метрика
остаются как есть. Здесь — две связанные вещи, которых у движка ещё нет.

Сначала о названии. **«Идеальный Excel» — формулировка без стоп-условия**, и именно она тянет
задачу в редактор таблиц. Приёмка переписывается фальсифицируемо:

> **Ничего видимого на странице не ушло в файл молча.**

Всё, что ниже, служит этой одной фразе.

## Две вещи и почему они одна задача

1. **Адресованный блок.** Документ читается не в сетку, а в набор адресованных областей: шапка,
   реквизиты, сетка, итоги, примечание, подписной блок, хром приложения, непрочитанное. Блок —
   это `набор атомов + роль`, разрешаемый **тем же резолвером**, что и ячейка. Никакой новой
   подсистемы «понимание раскладки» — просто больше адресованных областей, ровно как выделение
   области не стало новой подсистемой (v3 §9).
2. **Арифметическая улика.** `EvidenceClass.ARITHMETIC` объявлен в `core/flow/Candidates.kt:44`
   и не выдаётся никем. Таблица — первый её настоящий заказчик, а на рукописи она вообще
   единственный класс улик, который доживает до значения.

Связь не риторическая, а несущая. Структура даёт ячейке **адрес** (класс `STRUCTURAL`),
арифметика — **подтверждение** (класс `ARITHMETIC`). Порознь ни одна не поднимает таблицу выше
предположения: `CONFIRMED_CLASSES = 2`, а сегодня у ячейки таблицы ноль классов. Вместе они
впервые дают правилу двух классов работать на таблицах — самом частом действии корпуса
(7 кадров из 22, 32%).

## Диагноз: шапка не теряется — её не просят и её некуда положить

Пять узких горл, каждое проверяется по коду. Ни одно не про качество распознавания.

| # | Где | Что происходит |
|---|---|---|
| 1 | `ExcelAction.kt:192-206` (`PROMPT`) | Единственная допустимая форма ответа — «массив строк из строк-ячеек». Слов «шапка», «итог», «примечание», «подпись», «единицы» в промпте нет. Модели **некуда положить** остальное. Для сравнения, «В Word+» имеет структурный контракт `T=/H=/B=/P=` (`WordPlusAction.kt:28-32`) — словарь структуры в проекте есть, он просто не заведён в Excel-путь. |
| 2 | `ExcelAction.kt:197-205` | Промпт требует строгий прямоугольник («не добавляй, не повторяй столбцы») и прямо велит **терять строки** («не удаётся прочитать всю строку — пропусти её целиком»). Строка-итог и строка-примечание читаются хуже табличных — выбрасываются первыми. |
| 3 | `ExcelAction.kt:252` и `:330` | `if (!cleaned.startsWith("[")) return null`. Естественный ответ «вся структура» — объект `{...}` — отвергается **обоими** парсерами и уезжает в TSV-фолбэк (`:236-239`), который кладёт фигурные скобки в ячейки как данные и считается успехом (`:118`). Сегодня любой более богатый ответ **хуже** плоского. |
| 4 | `AddressedTable.kt:28-31`, `TableConsensus.kt:8-11`, `SideEffects.kt:88` | Тип таблицы на всех этажах — `List<List<String>>`. Признака роли нет ни у ячейки, ни у строки, ни у таблицы. Потерять структуру негде — её не существует как значения. |
| 5 | `OoxmlSpreadsheetWriter.kt:62-87, 105-111, 138` | Лист один, имя «Таблица», имя файла всегда «таблица.xlsx». `<mergeCells>` в репозитории ноль вхождений, `<cols>` нет, каждая ячейка — `t="inlineStr"`, все `cellXfs` с `numFmtId="0"`, а стиль шапки назначается по **позиции** (`row == 0`). |

Отсюда две вещи, которые надо понимать до чтения решения. Первая: **это дефект контракта
запроса, а не разбора** — чинится там, где формулируется вопрос. Вторая: **писателю сегодня
нечего дать**, даже если модель пришлёт всё.

Плюс два дефекта, которые срабатывают до всякого качества чтения и гарантируют правки на
трёх кадрах из семи: шапка по индексу 0 (на кадре 18 шапки нет физически — заголовком станет
первая товарная строка) и все числа текстом (на 06, 04, 18 первое действие человека — конвертация
колонки, то есть кадр уже не «без правок»).

## Контракт 1. Блок документа поверх атомов

Новый файл `core/flow/DocumentLayout.kt`, чистый Kotlin.

```kotlin
/**
 * Роль блока — СВИДЕТЕЛЬСТВО, не переключатель пайплайна (v3 §4). Её называет модель,
 * видевшая страницу; код её не переопределяет и по ней не роутит. Роль влияет ровно на
 * две вещи: куда блок ляжет в представлении и кто вправе заявить претензию на итог.
 */
enum class BlockRole {
    TITLE,     // «Технологічна карта №…», «Сводная таблица к счету № …»
    FIELD,     // реквизит: метка → значение («Клиент: Терминал Пр. 117»)
    TABLE,     // сетка
    TOTALS,    // блок итогов — строками (04) ИЛИ колонками внутри шапки (10)
    NOTE,      // примечание, сноска, дисклеймер («кладовщик не имеет права отпускать товар»)
    SIGN,      // подписной блок
    CHROME,    // видно, но это НЕ документ: статус-бар, тулбар, соседняя карточка доски
    UNREAD,    // модель видит слова, но не берётся их присвоить
}

/** Ответ модели про блок: тот же адресный контракт, что у ячейки ([CellAnswer]). */
sealed interface BlockContent {
    data class Text(val cell: CellAnswer) : BlockContent
    data class Grid(val cells: List<List<CellAnswer>>, val headerRows: Int) : BlockContent
}

data class BlockAnswer(
    val role: BlockRole,
    /** Метка блока-реквизита («Клиент»); null — метки на странице нет. */
    val label: CellAnswer? = null,
    val content: BlockContent,
)

/** Заявленный охват — факт, а не догадка: за кадром бывает и лист, и прокрутка. */
enum class DocScope { FULL, VIEWPORT, CROPPED }

data class DocumentBlock(
    val role: BlockRole,
    val label: String,
    val text: String,
    val grid: GroundedTable?,
    val headerRows: Int,
    /** Метки, которые блок присвоил (после резолва — только настоящие). */
    val ids: Set<String>,
    val flagged: Boolean,
)

data class DocumentLayout(
    val blocks: List<DocumentBlock>,
    val scope: DocScope?,
    /** Именованные атомы, которых нет ни в одном адресе блока. Пусто ⇔ страница присвоена. */
    val uncovered: List<Atom>,
    /** Доля именованных атомов в СОДЕРЖАТЕЛЬНЫХ блоках (без CHROME/UNREAD).
     *  `null` — атомов нет (рукопись): покрытие не считается и не выдумывается. */
    val coverage: Float?,
)

fun AtomLayer.resolveLayout(answer: LayoutAnswer): DocumentLayout
```

### Инварианты

- **Один разбор, один вызов.** Блоки и сетка приходят в том же ответе, что и ячейки. Второй
  вызов «а теперь шапку» — стадия пайплайна, а стадии пайплайна в этом репозитории уже вылезали
  в UI тремя AI-кнопками (#260, #26). Плюс бюджет: действие уже `PAID/SLOW`, две сильные модели,
  15–25 с на плотной таблице; удвоение на ежедневном действии — регрессия, а не полнота.
- **У блока нет собственного пути чтения.** Текст блока собирается `resolve(ByIds)` из атомов,
  как текст ячейки. Диктовка мимо страницы получает ⚠ по той же ветке, что в `resolveCells`.
- **Роль ничего не решает.** Ошиблась в роли — блок встал не туда в файле; значения это не
  меняет, страница по-прежнему выигрывает символы.
- **Непокрытое не молчит.** Атомы вне блоков едут в файл видимым блоком «непрочитанное».
  Это дословная приёмка #266 и единственный способ не соврать, не притворяясь всезнающим.
- **`CHROME` — не мусор и не содержание.** Он существует, потому что на 4 кадрах из 7 хром
  занимает заметную долю страницы (диалог и полосы прокрутки на 06, тулбар на 21, соседние
  карточки доски на 16, клавиатура и чужой документ на 10). Без явной корзины «не документ»
  покрытие было бы недостижимо честным путём.
- **Обратная совместимость двусторонняя.** Массив верхнего уровня → один блок `TABLE`;
  TSV → он же. Ни один сегодняшний ответ не становится хуже. Это чинит дефект №3 прямо.
- **Слоя нет — контракт тот же.** На рукописи/PDF/тексте ячейки и блоки приходят
  `CellAnswer.Literal`. Структура читается всегда, заземление — только там, где есть атомы.

### Форма ответа модели

```json
{"scope":"viewport",
 "blocks":[
   {"role":"title","ids":["w3","w4"]},
   {"role":"field","label":{"ids":["w10"]},"ids":["w11","w12"]},
   {"role":"table","header":1,"rows":[[{"ids":["w20"]},{"ids":["w21"]}]]},
   {"role":"totals","rows":[[{"ids":["w80"]},{"ids":["w81"]}]]},
   {"role":"note","ids":["w90","w91"]},
   {"role":"chrome","ids":["w1","w2"]},
   {"role":"unread","ids":["w77"]}]}
```

`"header": 0` — **шапки нет физически** (кадр 18), `2` — двухуровневая (04, 10). Это не
косметика: сегодня «первая строка — заголовки, если они есть» вообще не имеет способа сказать
«их нет», и молчание разрешается в пользу «есть».

## Контракт 2. Схема действия «Извлечь таблицу»

`ACTION_SCHEMAS` сознательно не содержит табличного действия — комментарий
`ActionSchema.kt:124-127` объясняет почему: «у объекта пока не бывает честного факта „в документе
есть таблица“». Блоки этот факт создают.

```kotlin
const val META_TABLE_GRID     = "table.grid"      // «16×7»
const val META_TABLE_HEADER   = "table.header"    // «нет» | «1» | «2»
const val META_TABLE_COVERED  = "table.covered"   // «да» — и только тогда, когда правда
const val META_TABLE_SCOPE    = "table.scope"     // full | viewport | cropped
const val META_TABLE_UNREAD   = "table.unread"    // сколько слов уехало «непрочитанным»
const val META_TABLE_FLAGGED  = "table.flagged"
const val META_TABLE_READY    = "table.ready"     // арифметика: есть Holds и нет Breaks
const val META_TABLE_RESIDUAL = "table.residual"  // «расходится на 1 200»

ActionSchema(
    id = "extract-table",
    label = "Извлечь таблицу",
    fields = listOf(
        FieldSpec(META_TABLE_GRID, "таблица", critical = true),                    // critical ⇒ anchor
        FieldSpec(META_TABLE_HEADER, "шапка", critical = true, anchor = false),
        FieldSpec(META_TABLE_COVERED, "ничего не потеряно", critical = true, anchor = false),
        FieldSpec(META_TABLE_SCOPE, "охват"),
        FieldSpec(META_TABLE_RESIDUAL, "расхождение итога"),
    ),
)
```

### Что критично, а что обязательно

Правило разделения: **критично то, без чего человек берётся за клавиатуру; некритично, но
обязательно к переносу — то, без чего он теряет доверие.**

- `table.grid` — якорь и только он. Дата, сумма и число есть почти на каждом кадре корпуса;
  якорь по ним повторил бы ошибку, которую #260 уже ловил на «Отследить отправление» для любого
  чата. Про таблицу говорит таблица.
- `table.header` — критично, потому что нерешённый вопрос о шапке = ручная переделка первой
  строки (18) или всей шапки (04, 10). Критична **решённость**, а не наличие.
- `table.covered` — критично, потому что потерянные реквизиты и примечание человек допечатывает
  руками. Пишется двумя путями, по режиму чтения:
  - `PRINTED`: `layout.uncovered.isEmpty()` — каждое прочитанное слово присвоено: ячейке, блоку
    вокруг, хрому или «непрочитанному»;
  - `HANDWRITTEN`: атомов нет, покрытие недостижимо по построению — ключ пишется, когда
    `uncertainInExport` применён ко всем блокам, то есть **ни одна цифра не выдана за
    прочитанное**. Цена названа вслух: на рукописи гарантия слабее — не «всё на месте»,
    а «ничто не притворяется прочитанным».
- Некритичны, но обязательны к переносу: заголовок и реквизиты (04, 18), блок итогов (04, 10),
  примечание (18), подписной блок (10, 19), охват (06, 10, 16, 21).

### Инвариант: эта схема судит результат, а не предсказывает его

`track-parcel` читает факты, полученные бесплатно и офлайн. У `extract-table` фактов до тапа
не бывает и быть не должно: **LLM никогда не на первом экране**. Поэтому факты пишет само
действие в метаданные результата, и карточка готовности появляется на экране готового .xlsx —
«таблица 16×7, ничего не потеряно» либо «не хватает: ничего не потеряно». Новой навигации ноль,
`ReadinessSection` уже существует.

Следствие для `ExcelCapability.accepts`: **в этом срезе не трогаем.** Сегодня он принимает любой
IMAGE|PDF|TEXT, и «В Excel» одинаково предлагается водомеру и шестнадцати строкам договоров. Это
реальный дефект, но сузить его нечем: признак «в документе есть таблица» должен приходить от
энричера (офлайн, ≤300 мс), а не от платного действия. Отдельный шаг, названный явно.

## Контракт 3. Арифметическая улика

Новый файл `core/flow/TableArithmetic.kt`. Не в `fieldEvidence` — все классы там расширения слоя
(`resolve`, `lines`, `cellRuns`, боксы), а сумма считается по значениям сетки, где атомов уже нет.
Не в `TableValidation.kt` — тот объявлен «model-free safety net» и отдаёт `Set<Pair<Int,Int>>`;
вторая несовместимая форма выхода сломала бы его контракт.

```kotlin
data class Amount(val minor: Long, val scale: Int, val percent: Boolean = false)
data class NumberStyle(val decimal: Char?, val group: Char?)

fun parseAmount(cell: String, style: NumberStyle): Amount?
fun columnNumberStyle(column: List<String>): NumberStyle?

enum class TotalClaim { ARITHMETIC, LABELLED, HEADED }

sealed interface TableRelation {
    val terms: List<Pair<Int, Int>>; val total: Pair<Int, Int>; val claim: TotalClaim
    data class ColumnTotal(…) : TableRelation
    data class RowTotal(…) : TableRelation
    data class RowProduct(val a: Pair<Int, Int>, val b: Pair<Int, Int>, …) : TableRelation
    data class PercentOfTotal(val whole: Pair<Int, Int>, …) : TableRelation
}

sealed interface Blame {
    data class Candidate(val cell: Pair<Int, Int>, val reading: String, val grounded: Boolean) : Blame
    data class Cell(val cell: Pair<Int, Int>) : Blame
    data object Unattributed : Blame
}

sealed interface RelationVerdict {
    data class Holds(val exact: Boolean) : RelationVerdict
    data class Breaks(val residual: Amount, val blame: Blame) : RelationVerdict
    data class Incomplete(val unread: List<Pair<Int, Int>>) : RelationVerdict
}

data class TableArithmetic(
    val relations: List<JudgedRelation>,
    val repairs: Map<Pair<Int, Int>, String>,    // значение действительно меняется
    val preferred: Map<Pair<Int, Int>, String>,  // значение НЕ меняется — меняется порядок выбора
    val flags: Set<Pair<Int, Int>>,
    val confirmed: Set<Pair<Int, Int>>,
    val crossFooted: Boolean,
)

fun tableArithmetic(
    rows: List<List<String>>,
    candidates: Map<Pair<Int, Int>, List<CellReading>> = emptyMap(),
): TableArithmetic

fun TableArithmetic.cellEvidence(cell: Pair<Int, Int>): Set<EvidenceClass>
```

### Решения, а не детали

**Отношение находит арифметика, словарь только создаёт претензию.** Сошедшееся отношение —
улика; несошедшееся — ничто, пока кто-то не заявил, что оно должно сойтись. Любые N чисел не дают
в сумме случайное (N+1)-е, и флагать это — шум, топящий сигнал. `Σ(c[r0..rk-1]) == c[rk]` найдено
— строка и есть «Итого», на любом языке. Словарь (`итого/усього/разом/total/сума…`) и заголовок
столбца дают `TotalClaim.LABELLED`/`HEADED` — право поднять ⚠, когда **заявленное** не сошлось.
То же рассуждение, что в v3 про идентификаторы: у слова нет универсального языка, у суммы есть
универсальная арифметика.

**Фиксированная точка, не `Double`.** `0.1 + 0.2 ≠ 0.3` в двоичной плавающей: невязка на 1e-15
либо родит фантомное расхождение, либо заставит ввести эпсилон, под которым спрячется настоящая
ошибка в копейку. Всё в `Long`, приведение к `scale = max(scales)`. Допуск — накопленное
округление записи: `tolerance(terms, scale) = (terms + 1) / 2` единиц последнего разряда. Ни
процента, ни относительной погрешности: относительный допуск на большой сумме прячет ошибку в
разряд. Цена названа: ошибка меньше границы округления невидима, и граница схлопывается в ноль,
как только документ печатает копейки. Во всех 32 файлах `core/flow` сегодня нет ни одного
`toDoubleOrNull`/`BigDecimal` — выбор представления делается здесь один раз.

**Парсер отказывается, а не гадает.** Разделитель решается **столбцом**, а не ячейкой: «1.234»
среди «2.500 / 3.750» — дробь, среди «12.500 / 1.100.000» — разряды; столбец с обеими трактовками
вперемешку не типизируется и не даёт ни одного отношения. `null` (не ноль и не догадка), когда:
группы цифр после первого разделителя не по три («20 4514 9154 9395» — четвёрки, то есть не
число); после снятия закрытого списка единиц (грн ₴ руб $ € % шт кг г л) остались буквы;
`scale > 4`; `|minor| > 1e12`. Тире — **пусто, а не ноль**: подставить ноль значит изменить сумму
догадкой, а пустой терм даёт `Incomplete`, не `Breaks`. Скобки `(1 200)` и хвостовой минус —
отрицательное. Активное значение берётся ровно одним способом — `styleCell(raw).value`.
Трек-номер и id-колонка лежат в тех же таблицах: `Identifiers.WAYBILL_SHAPED` — это «число с
пробелами», и `RuleEvidence` уже один раз лечил ровно эту ложь.

**`normConsensus` внутри арифметики запрещён.** Он сворачивает `[\s\-–—.,]+`, то есть стирает
ровно те символы, что несут величину: «12,50» и «1250» сегодня считаются согласными, ⚠ не
поднимается, потерянная запятая уходит в файл как бесспорное значение. Это не баг голосования (для
сравнения текста свёртка правильна) — это слепое пятно целого этажа, у которого до сих пор не было
ни одного контролёра. Арифметика — единственный, кто его видит.

**Hard-block из v3 §4 не прикладывается к таблице и переезжает в «действие не готово».** Причина
не вкусовая: checksum — свойство одного значения, поэтому S10 законно блокирует; «Σ строк ≠ итог»
— нарушение ограничения над N+1 числом, и виновного оно не называет. Блокировка удалила бы
правильное значение с вероятностью N/(N+1) — тот же грех, что `isPlausible()`, в котором умер
14-значный трек. Реальные ведомости не сходятся законно (округление, рукописная правка,
потерянная строка скидки), и отказ срабатывал бы чаще всего на самом трудном документе. §4
исполняется буквально, но в другом слое: hard-block = «действие не готово без человека»,
а не «файл не выдан». Единственный существующий отказ выдачи остаётся один — `torn`.

**Арбитраж: невязка, закрывающаяся ровно одной подстановкой, — сильнейшая офлайн-улика в
системе.** Порядок жёсткий: (1) одна и только одна подстановка чтения из `candidates` закрывает
невязку **в ноль точно** (не в допуске) — виноват он; две закрывающие — совпадение, а не улика,
сразу `Unattributed`; (2) ровно одна подозрительная ячейка в отношении — виновата она; (3) иначе
`Unattributed`, и ⚠ идёт на ячейку-итог, потому что провалилось утверждение «это итог», а не 16
значений. Точное закрытие на разряде — совпадение порядка 1/10^k.

**Заземлённое чтение остаётся значением.** Атомы говорят 8 500, модель диктует 3 500, и ровно
3 500 закрывает столбец. Автоподмена сломала бы инвариант #258/#236 — цифру модель изменить не
может по построению. Поэтому выход раздваивается: `repairs` (значение меняется) — только когда
**оба** конкурирующих чтения заземлены в атомы; `preferred` (значение не меняется, ⚠ остаётся,
арифметически предпочтённое чтение встаёт первым в дропдауне) — когда победитель продиктован.
Человек чинит одним тапом, страница выигрывает значение, арифметика выигрывает порядок выбора.

**⚠ снимать чужое нельзя.** Столбец сошёлся, а у терма были `droppedIds` — значение
подтверждено, происхождение нет; это разные утверждения. ARITHMETIC добавляет класс улики, но
снимает ⚠ только у пометки «спор чтений» и только разрешив спор. Для этого — две аддитивные
правки выше: `GroundedTable` получает `structural: Set<Pair<Int,Int>>` (ячейки, чьи метки
разрешились чисто), а `candidates` меняет тип на `Map<Pair<Int,Int>, List<CellReading>>`, где
`CellReading(text, source)` берёт значения из существующего словаря `SOURCE_OCR`/`SOURCE_MODEL`.
Без происхождения арбитраж пришлось бы строить на догадке «первый кандидат — атомный», а это
ровно то допущение, которое уже ломалось и потребовало `anchorCandidates`.

**На рукописи арифметика — единственный класс, и шестой изобретать нельзя.** После #263 у
рукописи нет атомов → недостижимы STRUCTURAL/GEOMETRIC/LEXICAL, `semanticFits` для ячейки не
определён → нет SEMANTIC. Ноль классов при пороге 2. Арифметика считается по значениям, режим
чтения ей безразличен. Соблазн добавить `REPLICATED` (согласие двух моделей) шестым классом
отклоняется: две зрячие модели коррелируют в ошибках на одном и том же неоднозначном глифе, и
назвать их согласие независимым доказательством — воспроизвести самоподтверждение v3 §7 на новом
уровне. Потолок честности на рукописи — «подтверждено арифметикой» одним названным классом,
никогда не «подтверждено».

**Границы (каждое «не» дороже соответствующего «да»).** Не дописывает отсутствующий итог
(вычисленный итог в ячейке — это ВЫВЕДЕНО под видом ПРОЧИТАНО, v3 §8). Не пишет `=SUM()` в ячейку
значения. Не воскрешает зачёркнутое: сумма сошлась с `~~53~~` — это ⚠, а не подмена. Не судит
таблицы до голосования (иначе становится отборщиком таблиц, то есть решателем) — один этаж, после
`reconcile`. Не обвиняет обрезанную таблицу: термы, упирающиеся в первую/последнюю строку сетки,
дают `Incomplete`. Не флагает неполные отношения целиком: непрочитанный терм → ⚠ на нём.
Потолки: `MIN_RELATION_TERMS = 2`, `MIN_PRODUCT_ROWS = 3`, произведения отключаются при
`cols > 12`, вся арифметика при `rows > 500`; остальное — префиксные суммы, O(rows×cols).
Стоимость нулевая: офлайн, без сети, без модели — самый дешёвый класс улик в системе и
единственный, который невозможно подделать.

## Чего сознательно НЕ делаем

Граница проходит **не по богатству файла, а по тому, где живёт правка**. Обогащать xlsx можно
сколь угодно — это по-прежнему ответ на «что я могу сделать с этим объектом прямо сейчас»: один
тап, один файл, флоу закончился. Point становится редактором таблиц ровно в тот момент, когда
исправление результата переезжает внутрь Point. Рабочий тест к каждому пункту: **«после этого
файла человек возвращается в Point или уходит в Excel?»** Ответ «возвращается» — стоп.

1. **Экран правки таблицы перед экспортом — не делать.** Самый естественный следующий шаг после
   ⚠ и кандидатов, и это ровно фича-редактор. Механизм исправления уже отгружен и стоит в
   правильном месте — внутри самого xlsx: спорная ячейка несёт дропдаун чтений, человек чинит
   одним тапом там, где будет работать дальше. Зеркало этого экрана в Point — Excel на один
   процент плюс новая навигация и новое состояние.
2. **Формулы, сводные, диаграммы, «умное форматирование» — не делать.** Как только итог посчитал
   Point, документ тихо врёт: число выглядит прочитанным, а оно выведено, и в словаре
   происхождения ему нет честного имени.
3. **Библиотека шаблонов («запомни этот бланк») — не делать.** Соблазн максимален из-за
   ежедневности, и это ровно корневой роутер по типу документа, дважды отменённый (v3 §5,
   ADR-0001), плюс собственное состояние и своя навигация.
4. **Книга из листов «Шапка / Таблица / Подписи / Улики» — не делать.** Выглядит как полнота, на
   деле Point придумывает документу информационную архитектуру, которой в нём нет, и заводит
   навигацию: человек открывает файл и выбирает, на каком листе ответ. Скрытый `_варіанти`
   остаётся прецедентом для механики, а не для контента.
5. **Round-trip «поправил в Excel — вернул в Point — Point выучил» — не делать.** Маскируется под
   инвариант «правка человека не переписывается моделью», но `source=human` — про значение внутри
   флоу, а не про диффы двух файлов. Импорт правленого xlsx требует сопоставления документов,
   политики слияния и владения документом во времени — это менеджер документов, несовместимый с
   неизменяемым `PointObject`.
6. **Настройки экспорта и профили — не делать.** «С шапкой / без», «стиль», «разделитель» — это
   меню, которого у Point нет по замыслу. Законная форма выбора одна: второе действие с другой
   подписью (готовый паттерн «В Word» / «В Word+»).
7. **Структура вторым вызовом — не делать.** См. инвариант «один разбор, один вызов».

И одно ограничение охвата: **не расширять #266 до «любой структуры»**. Из семи «табличных»
кадров сетчатых пять. Кадр 16 (канбан-чек-лист) и 21 (дерево файлов) таблицами не являются;
накрыть их тем же «идеальным Excel» — это либо зоопарк структур, либо чек-лист внутри Point, то
есть менеджер задач. У списка нет колонок и единиц, зато есть состояние пункта и уровень/родитель
— чего нет у таблицы. Вторая схема `extract-list` (критические `list.items` (якорь),
`list.container`, `list.scope`, плюс `list.state`/`list.level`) — **отдельный issue**; до тех пор
16 и 21 остаются в `CorpusScore.unscored` поимённо, а не получают фальшивую готовность. Честный
охват #266 — сетка плюс то, что вокруг неё на той же странице.

## Как это измеряется на корпусе

Знаменатель растёт с **2 из 22** до **7 из 22**: два кадра `track-parcel` плюс пять сетчатых
кадров `extract-table` (04, 06, 10, 18, 19). Кадры 16 и 21 остаются в `unscored` поимённо —
они не таблицы. `CorpusMetric.kt` не меняется ни строкой.

«Без правок» для `extract-table` — дословно: сетка найдена и её размер заявлен; вопрос о шапке
решён (имена прочитаны, либо «шапки нет», либо «уровней два»); ничего видимого не ушло молча
(на печати — каждое прочитанное слово присвоено; на рукописи — ни одна цифра не выдана за
прочитанное).

Прогноз по кадрам, с ценой:

- **06** (16×7, договоры) — вероятнее всего «готов». Чистая одноуровневая шапка, хром явный
  (диалог, фильтр, кнопка, две полосы прокрутки), `scope = viewport`. Условия: «Ціна» приезжает
  числом, четыре обрезанных названия поставщиков помечены как обрезанные, а не достроены.
- **18** (счёт, 2×7 без шапки) — дословный случай #266. Готовность требует `header = 0`, четырёх
  реквизитов блоками `FIELD` и примечания «кладовщик не имеет права отпускать товар» блоком
  `NOTE`. Без него «идеальный Excel» юридически противоположен оригиналу.
- **04** (техкарта) — самый тяжёлый: три сетки, двухуровневая шапка, объединения, множитель ×100.
  Первый настоящий заказчик ARITHMETIC: колонка «на 1 порцію» ровно в 100 раз меньше «на 100
  порцій» на всех одиннадцати парах, проверяется без модели. Осторожность зафиксирована: сумма
  нетто (9 300+300+500+5+30 = 10 135) **не** равна «Вихід страви 10 000» — это технологические
  потери, а не ошибка чтения; сходится отношение колонок, а не сумма столбца.
- **10** (бланк, трёхэтажная шапка) — ожидаем «не готов», и это правда, а не дефект метрики:
  левая половина листа не в кадре (`scope = cropped`), под шапкой служебная строка нумерации
  граф 3…23, идеально похожая на данные.
- **19** (военный билет) — рукопись: `covered` через пометку. Печатная шапка читается атомами,
  девять строк — моделью. Цена названа: режим сегодня ставится на объект целиком, поэтому
  печатная шапка будет помечена вместе с рукописью — избыточно, но безопасно. Режим на значение
  — следующий срез.

**Ship-критерий: семь табличных кадров вошли в знаменатель и число опубликовано, даже если это
2 из 7.** Публикация невыгодного числа — и есть работа метрики.

**PR-3 — «Арифметическая улика»**
`TableArithmetic.kt`; `CellReading` в `GroundedTable`/`Consensus`; врезка в `ExcelRealizer`;

решается столбцом; точная сумма → `Holds(exact=true)`; округлённый столбец → `Holds(exact=false)`;
один закрывающий кандидат → `Blame.Candidate`, два → `Unattributed`; зачёркнутое не воскрешается;
таблица без числовых столбцов — ноль отношений, ноль флагов, `table.ready` отсутствует;
`repairs` пуст, когда победитель продиктован.

нечем арбитрировать (нет происхождения кандидатов).

## Риски и что может опровергнуть замысел

- **Готовность судит структуру, а не значения.** Кадр может пройти три критических поля и всё
  равно потребовать правок, если ⚠ стоит на важной ячейке. Это известная слабость proxy-метрики,
  и она лечится не формулой, а одним ручным проходом владельца по семи кадрам: расхождение
  «готово» ↔ «не правил» правит **схему**, а не число. Если расхождение окажется системным,
  критическим полем придётся сделать `table.flagged == 0`, и это будет решением, а не подкруткой.
- **`unread` как отмычка.** Модель может ссыпать половину документа в «непрочитанное» и формально
  выполнить `covered`. Смягчение — не порог (порог = выдуманное число), а публикация:
  `table.unread` едет в метаданные и в файл видимой строкой, и первый же прогон это покажет.
- **Потолок индекса.** `MAX_PROMPT_ATOMS = 600` закрывает индекс на плотной странице — а это ровно
  кадры 06 и 10. Без индекса блоки приходят дословными, покрытие не считается, `covered` не
  пишется, кадр «не готов». Честно, но означает, что потолок придётся поднимать или дробить
  страницу. Открытый вопрос среза.
- **Слой существует только у картинок** (`OcrEnricher.appliesTo == IMAGE`), а «В Excel» принимает
  ещё PDF и TEXT. Договорная таблица на 16 строк в PDF идёт по дословному пути со всеми
  последствиями. Тоже открытый вопрос — и он же аргумент за PDF-ветку слоя следующим срезом.
- **Многостраничность.** `Atom.page` объявлен, но `lines()` группирует только по вертикали кадра
  — на PDF страницы перемешаются. В этом срезе не чиним, но `DocumentLayout` обязан пережить
  добавление страницы без смены контракта (блок знает свои метки, метка знает свою страницу).
- **Латентность.** Ответ становится длиннее (блоки + сетка), вход не меняется. Второго вызова
  нет по инварианту; если выход начнёт упираться в лимит — резать надо блоки-хром, не содержание.
- **Числа числами против дословности.** «11 625» приезжает как 11625: исходная запись остаётся
  в подсказке ячейки. Если владелец скажет, что дословная форма важнее автосуммы, — решение
  переворачивается, и это развилка вкуса, а не архитектуры.

## Что дальше (и почему не сейчас)

`DocumentLayout` — это **единое чтение**, а xlsx и docx — два его рендера. Word-ветка сегодня
беднее по всем швам: `DocBlock` не имеет адреса, «В Word+» кормится плоской строкой распознавания
вместо слоя атомов (на печатной странице он диктует, пока «В Excel» указывает), а
`OoxmlDocxWriter` не умеет таблиц вовсе — рукописная ведомость в Word теряет сетку целиком.
Свести их в один контракт — ровно то, чего требует поправка «формат — представление, а не объект»
(#265), и после этого среза это становится дешёвой работой: второй рендер поверх готового
`DocumentLayout`, без нового контракта чтения.

Во второй заход также: `<mergeCells>` и настоящая двухуровневая шапка; режим чтения **на
значение**, а не на объект (кадр 19 — два режима на одной странице); схема `extract-list` для
кадров 16 и 21; сужение `ExcelCapability.accepts` по офлайн-признаку «в документе есть таблица».
Каждое из них берётся, только если число покажет, что правки держит именно оно.
