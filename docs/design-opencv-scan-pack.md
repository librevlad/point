# Design: OpenCV скан-пак (предпочтительный realizer к `ScanCapability`)

Сгенерировано `/office-hours` — 2026-07-23. Ветка: `main`. Статус: **DRAFT (за гейтом валидации)**. Режим: Startup.

> Это форвард-дизайн для отложенного пункта роадмапа («OpenCV-скан-пак»). **Не
> реализация** — реализацию открывает только пройденный гейт (см. «Задание»).
> Механизм уже готов: `ScanCapability` + `RealizerMeta priority` + фолбэк-цепочка
> `Resolver` (срез «OCR: два реализатора»). Вопрос дока — *стоит ли строить и как
> доставлять*, а не *как встроить*.

## Проблема

Скан документа в Point сейчас — чистый `ScanFilter` (grayscale + Otsu), без
геометрии. Пользователь, которому нужен ровный, обрезанный по границам документ,
не получает его в Point.

## Свидетельство спроса

Прямое, поведенческое: когда нужен чистый скан, пользователь **уходит в спец-приложение**
(CamScanner / Adobe Scan / Genius Scan / Microsoft Lens). Это реальное поведение
(не «интересно бы»), значит спрос на чистый скан существует. Но это же и определяет
конкурента: не «кривое фото», а зрелые бесплатные сканеры с авто-границами.

## Статус-кво

Уход в спец-сканер. Следствие: побить эти приложения по качеству CV — не наша игра.
Единственное оправдание нашего скана — **континуити** (Северная звезда Point: минус
переключения): «ты уже в Point с этой картинкой, не прыгай в другой app и обратно».

## Целевой пользователь и вердж

Пользователь, который уже расшарил фото документа в Point и не хочет уходить.
**Планка — «достаточно хорошо, чтобы остаться», а не «превзойти CamScanner».** Вердж
(выбран владельцем): полный OpenCV-realizer (авто-границы + перспектива), но
доставленный **on-demand**, чтобы вес не бил тех, кто скан не трогает.

## Ограничения

- Качество детекции проверяемо **только на устройстве** — юнит-тестами не берётся.
- Нативный OpenCV тяжёлый (~40 МБ), ABI-ограничение как у Tesseract (`arm64-v8a` +
  `armeabi-v7a`).
- Point — share-first: работаем с уже расшаренным изображением, не с флоу камеры
  (поэтому ML Kit Document Scanner отвергнут ранее — это камера-флоу).
- Офлайн-инвариант: скан не должен требовать сети (в отличие от отвергнутого cloud-варианта).

## Премисы (подтверждены в сессии)

1. Ценность = континуити, а не превзойти CamScanner по CV.
2. Надёжный авто-кроп/deskew обязателен для планки, и лёгкая/самописная CV его надёжно
   НЕ даёт (мажет на низком контрасте/пёстром фоне) → OpenCV = прагматичный known-good путь.
3. Доставка — по-настоящему on-demand (dynamic feature module), **НЕ «пока встроенный»**.
   Иначе 40 МБ в базовом APK для всех топят кейс.
4. On-demand модуль тянется только из Play → нужен фолбэк для sideload/enterprise
   (забандлить пак в тех сборках). `Resolver` уже падает на фильтр — деградация мягкая.
5. Риск №1 — качество детекции на реальных фото — сейчас НЕ проверен → проверить дёшево
   на desktop **до** постройки пака. Это гейт.

## Рассмотренные подходы

### Approach A — Валидация → OpenCV on-demand пак *(выбран)*
Сначала desktop-OpenCV проба на реальных фото; клирит порог → OpenCV как настоящий
dynamic feature module, realizer за `isAvailable()`, `Resolver` падает на фильтр.
Effort L (проба S, пак L). Risk Med (качество ретайрится пробой; остаётся нативная +
delivery-сложность). Переиспользует шов мульти-realizer, только что сделанный нагруженным.

### Approach B — Не строить пак *(minimal viable, фолбэк)*
Фильтр = «быстрый скан» для частого кейса (чеки/заметки/скрины) + one-tap ручной
кроп/поворот для «страница под углом». «Идеальный скан» остаётся спец-приложениям.
Effort S, Risk Low. Ноль веса, шип сейчас. Теряет «авто-магию», DLC-шов не валидирует.
**Это честный исход, если проба разочарует.**

### Approach C — Облачный скан-realizer *(creative/lateral, отклонён)*
Cloud-realizer выравнивает/кропает (vision-модель → координаты → warp на устройстве),
фильтр — офлайн-фолбэк; зеркалит OCR device/cloud сплит. Ноль нативщины/веса.
Отклонён: возвращает онлайн-зависимость, которую Point только что убрал из OCR
(срез «OCR: два реализатора»); цена за скан; **приватность документов** (B2B-блокер).

## Рекомендация

**Approach A, строго через гейт.** Тезис континуити верен *если* детект работает, а
проба — самый дешёвый способ снять единственный риск, который топит кейс, до самой
дорогой стройки. Валидировать раньше, чем строить.

## Открытые вопросы

- Можно ли обрезать OpenCV до нужных модулей (imgproc: contour + warp), чтобы пак был
  <40 МБ? Уменьшает и download-friction, и порог оправданности.
- Нужен ли ручной override кропа, когда авто мажет (safety net, чтобы промах не гнал
  юзера в CamScanner)?
- Download-friction UX: что видит пользователь при первом «Скан», пока пак качается —
  прогресс? тихий фолбэк на фильтр с последующим апгрейдом?

## Критерии успеха

- **Гейт:** ≥~90% реальных мятых фото дают корректный авто-кроп в desktop-пробе без
  ручной правки.
- Базовый APK не растёт (пак on-demand); 40 МБ качают только scan-юзеры.
- Scan-юзер получает выровненный документ, **не выходя из Point**.
- `Resolver` мягко падает на фильтр, когда пак недоступен (офлайн / не установлен /
  sideload / OpenCV не загрузился).

## План доставки

- **Play Feature Delivery** — OpenCV в отдельном dynamic feature module; `SplitInstallManager`
  тянет его при первом использовании «Скан». Базовый `.aab` остаётся лёгким.
- **Realizer за `isAvailable()`** — проверяет, установлен ли модуль; `RealizerMeta.priority`
  ниже фильтра (предпочтительный); `Resolver` уже выбирает лучший доступный и падает на
  фильтр-realizer автоматически.
- **Фолбэк для sideload/enterprise** — эти сборки бандлят пак install-time (on-demand
  недоступен вне Play). Либо документируем, что вне Play скан = только фильтр.
- **CI** — сборка app bundle (`.aab`) для Play; тест дин-модуля через `bundletool` /
  internal-app-sharing (не `installDebug`).

## Зависимости

- Play App Bundle + тестовый контур `bundletool`/internal-app-sharing (дин-модуль не
  ставится через обычный `installDebug`).
- Нативный OpenCV (ABI `arm64-v8a` + `armeabi-v7a`).
- **Устройство** для проверки качества (нативный вызов — тонкая обвязка; логику
  device→фильтр покрывают фейки, как в OCR).

## Задание (следующее действие — до единой строки пак-кода)

Собрать **15–20 реальных мятых фото документов** (под углом; разный фон/свет; чек +
полная страница + рукопись) и прогнать desktop-скриптом OpenCV (Python:
`grayscale → GaussianBlur → Canny → findContours → approxPolyDP` до 4 точек `→
getPerspectiveTransform → warpPerspective`). Глазами оценить кроп.

- **≥~90% корректных кропов** → пак оправдан → идти в `/plan-eng-review` по реализации
  dynamic feature module.
- **<~90%** → либо чинить пайплайн (адаптивный порог / иная сегментация), либо
  Approach B (не строить пак).

Это отвечает на единственный вопрос, который отсюда не виден: **работает ли детект на
реальных данных.** Стоит полдня, не требует устройства, снимает главный риск.

  большинство избегает.
- Когда я переформулировал ценность как континуити, а не превосходство по CV, ты всё
  равно выбрал полный OpenCV — и **принял гейт валидации**. Убеждённость плюс готовность
  проверить её дёшево до стройки — та самая комбинация, которая доводит до шипа.
- Ты не защищал 40 МБ — ты переформулировал их в on-demand-доставку. Это решать
  возражение, а не спорить с ним.
