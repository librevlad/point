# ADR-0001 — Object Graph Runtime

**Статус:** Accepted

## Решение

Point строится вокруг одного графового runtime:

PointObject
→ PointObject Graph
→ Planner
→ Capability
→ Resolver
→ Realizer
→ PointObject Graph

Цикл повторяется произвольное число раз.

Planner отвечает за предложение и порядок действий.

Resolver выбирает допустимый способ исполнения Capability.

Realizer выполняет.

Отдельного механизма извлечения знания в модели нет. Исследование — тоже Capability и проходит тот же путь. Отличается только результат: знание в Graph вместо нового объекта или внешнего эффекта.

Названия конкретных классов не являются архитектурным контрактом.

---

## 1. PointObject

PointObject — самостоятельный объект, над которым может существовать пользовательски осмысленное действие.

У объекта есть:
- identity;
- kind;
- metadata;
- relations;
- provenance/evidence;
- ObjectRef на payload, если он существует.

`kind` — открытый словарь.

Runtime не содержит отдельного типа для каждого предмета мира.

Не вводятся специальные фундаментальные типы вроде:

Car
Cat
Stamp
Passport
Receipt

если для работы с ними достаточно существующих примитивов.

---

## 2. Object Graph

Graph выражает:
- самостоятельные объекты;
- свойства объектов;
- отношения;
- происхождение;
- локализацию;
- вложенность;
- альтернативные результаты;
- результаты transformations.

Atom не является Graph node.

Atom — внутренний адресуемый слой исходного объекта:
- текстовый span;
- polygon/bounding geometry;
- OCR evidence;
- другие низкоуровневые данные.

Например:

Photo
└── OCR / evidence layer
    ├── Atom
    ├── Atom
    └── ...

Graph не обязан знать об отдельных атомах как об объектах.

---

## 3. Принадлежность Graph

Сущность становится PointObject, если она сама по себе полезна пользователю:

- её можно увидеть;
- выбрать;
- применить к ней Capability.

Внутренние технические элементы не становятся объектами Graph.

Это позволяет одному изображению содержать множество самостоятельных сущностей без создания специального типа для каждой.

---

## 4. Enrichment

Enrichment добавляет знание существующему объекту.

Enrichment НЕ:
- создаёт новую версию;
- заменяет исходный объект;
- уничтожает старое знание.

Пример:

Photo
→ Photo + QR + Phone + Person + Evidence

Это тот же `Photo`.

Если найденное значение также имеет самостоятельную пользовательскую семантику, оно может быть одновременно:

1. узлом Graph;
2. фактом об исходном объекте.

Это одно значение с двумя ролями, а не две копии.

Связь с источником обязательна.

---

## 5. Transformation

Transformation создаёт новый самостоятельный результат.

Например:

ZIP → File A + File B

Document → TextObject

Document → TableObject

Transformation сохраняет связь результата с источником.

---

## 6. Representation

Representation — способ представить существующий semantic object.

Например:

Table
→ XLSX
→ CSV
→ HTML

Representation не является новым semantic node.

Экспорт — Capability, результат которой может быть representation.

Representation может быть ленивой и временной.

---

## 7. Relations

Связи Graph выражают обычные семантические отношения между объектами.

Не требуется специальная архитектура для каждой предметной области.

Например:

Chat
→ contains → Image
Image
→ depicts → Vehicle A
Image
→ depicts → Vehicle B
Vehicle A
→ has → Plate

Два автомобиля на одном изображении остаются двумя объектами.

Graph не обязан автоматически их сливать.

Если пользователю требуется объединение/сопоставление — это отдельное пользовательское действие или UX-механизм.

---

## 8. Provenance и Evidence

Происхождение результата сохраняется внутри Graph.

Возможные источники:
- OCR;
- model;
- rule;
- human;
- другие допустимые реализации.

Evidence хранит основания результата.

Alternatives позволяют сохранить конкурирующие прочтения.

Provenance не является confidence score.

Runtime не должен сводить все источники к одному числу confidence.

Пользовательский UI не обязан показывать внутреннюю provenance.

---

## 9. Неопределённость

Investigation State описывает состояние знания.

Состояние принадлежит паре:

(ObjectId, Investigation/CapabilityId)

Оно отвечает на один вопрос: исследовался ли этот вопрос для этого объекта.

Investigation State не является состоянием операции и не является свойством найденного факта. Факт может отсутствовать, а состояние всё равно существует — именно это отличает «не искали» от «искали и не нашли».

Graph должен уметь различать:

FOUND
NOT_FOUND
NOT_INVESTIGATED
INSUFFICIENTLY_INVESTIGATED
CONTRADICTORY

Это необходимо, потому что:

«не найдено» не означает «отсутствует».

### Состояние операции

Идёт ли исследование, завершилось ли оно, сорвалось ли — состояние операции, а не знания.

Оно живёт вне Investigation State и не хранится как знание об объекте.

Сорванное или прерванное исследование не переводит знание в `NOT_FOUND`. Знание остаётся `NOT_INVESTIGATED` или `INSUFFICIENTLY_INVESTIGATED`, а неудача выражается результатом операции (§18).

«Дальше исследовать не оправдано» — вывод ranking на текущем состоянии, а не состояние знания. При изменении Graph он пересчитывается.

---

## 10. Focus

Focus — внешний пользовательский сигнал для механизма понимания.

Он может адресовать:
- область изображения;
- конкретный объект;
- часть документа;
- часть текста;
- другой аспект текущего состояния.

Focus не является Object type.

Focus не является Intent.

Focus не изменяет значение вручную.

Focus увеличивает приоритет исследования указанной области/аспекта.

---

## 11. Capability

Capability — декларация действия:

что принимается;
что потенциально получается;
какие ограничения существуют;
можно ли действие вывести наружу.

Capability не содержит реализацию.

Capability не знает, на каком устройстве фактически будет исполнена.

### Исследование — тоже Capability

Capability различаются результатом, а не механизмом:

- исследовательская Capability возвращает знание в Graph;
- пользовательская Capability возвращает новый объект или внешний эффект.

Обе объявляются одинаково, обе проходят через Resolver и Realizer, обе подчиняются одной политике исполнения.

Разница видна Planner: исследовательская Capability расширяет знание, пользовательская — завершает шаг.

Отдельного реестра исследований не существует. Выделенный слой обогащения допустим как реализация той же схемы, но не как второй механизм со своими правилами.

---

## 12. Realizer

Realizer — конкретный способ выполнения Capability.

Одна Capability может иметь несколько Realizer.

Например:

ExtractText
├── local OCR
├── computer OCR
└── remote OCR

Человек выбирает `ExtractText`, а не конкретный Realizer.

---

## 13. Resolver

Resolver выбирает Realizer для:

Capability + Object Graph + Context.

Не существует универсального закона:

LOCAL > CLOUD > REMOTE

Выбор зависит от:
- допустимости;
- доступности;
- качества;
- границ приватности;
- других свойств конкретного исполнения.

Внешний Realizer не выбирается молча (§19).

---

## 14. Planner

Planner работает с текущим состоянием Graph.

Он:

1. получает состояние;
2. определяет применимые Capability;
3. учитывает Intent;
4. учитывает Focus;
5. учитывает пользовательское использование;
6. формирует порядок действий.

Таблица переходов не хранится.

Добавление Capability расширяет пространство действий автоматически.

Planner не должен быть отдельным каталогом всех возможных состояний мира.

### Два разных ranking

Порядок действий для человека и выбор следующего исследования — разные задачи над одним Graph:

- Action ranking — задача Planner: что предложить человеку и в каком порядке;
- Discovery ranking — задача Progressive Understanding (§15): какое исследование выполнить следующим.

Ни одна не выводится из другой.

Дорогое исследование может быть лучшим следующим шагом и при этом не показываться действием. Уместное действие может не быть следующим исследованием.

Формулы обоих ranking этот ADR не фиксирует. Discovery ranking описан в RFC Progressive Object Understanding. Action ranking остаётся за Planner при обязательном условии Конституции: Intent влияет на порядок, но не уничтожает полезные действия.

### Intent

Intent — семантический смысл действия, уместного для текущего состояния объекта.

Intent выводится из Graph, контекста и Focus.

Intent не является пользовательским вводом, типом объекта и свойством, которое хранится у объекта навсегда.

Новое знание может изменить уместный Intent.

Intent влияет на порядок действий и не является основанием убрать действие из списка.

---

## 15. Progressive Understanding

Graph является состоянием постепенно приобретаемого знания.

Механизм может выполнять:

State
→ candidate discoveries
→ ranking
→ допустимое исследование
→ validation
→ merge
→ updated Graph
→ новые candidates

Discovery может порождать новые Discovery.

Например:

Image
→ Document discovered
→ Document structure discovered
→ regions discovered
→ handwritten region discovered
→ text/entities discovered
→ new actions.

Механизм не должен быть конечным набором pipeline.

### Validation

Validation проверяет пригодность результата до merge:

- та ли это форма результата;
- отвечает ли результат тому, что заявляла Capability;
- можно ли вообще положить его в Graph.

Validation не разрешает противоречия.

Она не выбирает между конкурирующими результатами, не отбрасывает более слабый и не сводит источники к одному значению.

Конфликт сохраняется в Graph вместе с provenance и alternatives и разрешается отдельным шагом понимания или человеком.

Непригодный результат не становится знанием об отсутствии: Investigation State остаётся прежним, а шаг завершается неудачей операции (§18).

---

## 16. Лестница понимания

UX может позволять пользователю углублять понимание:

Понять
→ Понять сильнее
→ Понять ещё сильнее
→ ...

Каждый следующий результат обогащает текущее состояние.

Это не создание версий одного объекта.

Это накопление знания о том же объекте.

---

## 17. Глубина Graph

Нет фиксированной максимальной глубины.

Например:

Document
→ Screenshot
→ Chat
→ Image
→ Vehicle
→ Plate

или:

Audio
→ Transcript
→ Date
→ Place

или:

Image
→ Document
→ Region
→ Entity

Все эти случаи используют один Graph runtime.

Не требуется отдельный pipeline для каждой глубины.

---

## 18. ActionResult

ActionResult описывает операцию, а не знание об объекте.

Терминальных исходов три:

- **новый объект** — появился самостоятельный объект;
- **выполнено** — шаг состоялся без нового объекта: внешний side-effect либо новое знание в Graph;
- **не вышло** — выполнение не состоялось, с причиной.

Незавершённый шаг терминальным исходом не является. Запрос ввода или изображения означает, что шаг ждёт продолжения, а не закончился.

Имена вариантов в коде могут отличаться. Контракт — набор ролей и то, что ожидание продолжения не считается исходом.

Исход «не вышло» принадлежит операции. Он не переводит знание в `NOT_FOUND` (§9) и не скрывается от человека.

---

## 19. Execution Boundary

Point может автоматически выполнять внутреннее исследование в пределах разрешённой политики.

Объект покидает устройства пользователя только с явного согласия человека.

Согласие может быть дано заранее — выбранным режимом работы, — но никогда не подразумевается по умолчанию.

### Автоматическое исследование

Автоматический Discovery не пересекает внешнюю границу без заранее данного явного согласия.

Пока согласия нет, Resolver не выбирает внешний Realizer для автоматического исследования — даже если внешний даёт лучший результат и других Realizer нет. Такое исследование остаётся кандидатом с названной причиной недоступности.

### Пользовательское действие

Отсутствие согласия не делает Capability невидимой.

Действие, для которого потребуется согласие, показывается человеку как доступное для выбора: иначе согласие негде дать.

Порядок:

1. Planner показывает действие;
2. человек выбирает его;
3. Point показывает запрос согласия с указанием, куда уйдёт объект;
4. после явного согласия Resolver выбирает внешний Realizer;
5. без согласия действие не выполняется, и объект никуда не уходит.

Показ действия не является согласием. Подразумеваемого согласия не существует.

Resolver/ExecutionPolicy не должен превращать внешний сервис в скрытый автоматический fallback.

Стоимость, latency и availability — параметры исполнения, а не семантика объекта.

---

## 20. Payload

Graph не является файловым хранилищем.

Graph хранит semantic state и ссылки на payload, но не обязан хранить сами байты.

ObjectRef — адрес payload, а не контейнер для произвольных данных.

Рабочие payload могут находиться в scratch и удаляться после завершения работы.

Semantic knowledge может переживать удаление payload.

### Перенос между устройствами

Graph не синхронизируется между устройствами пользователя. Единый распределённый Graph не является архитектурным контрактом.

При продолжении работы на другом устройстве передаётся то, что нужно для продолжения:

- сам объект;
- его известное состояние;
- перечень Capability, доступных на той стороне;
- результат выполнения и полученное знание.

Принимающая сторона работает с тем же объектом, а не заводит новый.

Знание, полученное на другом устройстве, возвращается в состояние исходного объекта.

Потеря знания при переносе — дефект, а не следствие отсутствия синхронизации.

Форма передачи — деталь транспорта. Контракт — сохранение объекта и его знания, а не структура Graph на проводе.

---

## 21. Что ADR фиксирует

Этот ADR фиксирует фундаментальные примитивы:

- PointObject;
- Object Graph;
- Atom;
- Enrichment;
- Transformation;
- Representation;
- Relation;
- Evidence / Provenance;
- Investigation State;
- Focus;
- Intent;
- Capability;
- Realizer;
- Resolver;
- Planner;
- Progressive Understanding;
- Validation;
- ActionResult;
- перенос между устройствами.

Он НЕ фиксирует:
- конкретный UI;
- конкретную AI-модель;
- конкретный OCR;
- формулу Action ranking;
- формулу Discovery ranking;
- конкретный набор `kind`;
- конкретную реализацию Graph storage;
- конкретный транспорт между устройствами и формат передачи.

Эти вещи могут меняться без изменения фундаментальной модели.

Отдельного примитива `Extractor` в модели нет: исследование выражается Capability.

---

## 22. Критерий корректности

Runtime корректен, если любой новый кейс можно выразить через существующие примитивы, не добавляя специальную архитектуру под предметный мир.

Если для:

Car
Cat
Stamp
Passport
Receipt
Map
Chat

нужно вводить отдельные фундаментальные runtime-типы, сначала следует проверить, не отсутствует ли более фундаментальная Object/Property/Relation/Evidence/Focus модель.

Новый примитив добавляется только если существующих действительно недостаточно.
