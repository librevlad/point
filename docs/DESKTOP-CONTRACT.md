# Контракт: Point на компьютере

**Статус:** принято владельцем 06.08.2026. Основание — продуктовый аудит
(`docs/DESKTOP-PRODUCT-AUDIT.md`) и разбор его выводов владельцем.
**Отношение к ADR-0001:** этот документ **ничего в нём не меняет**. Он говорит, куда в уже
замороженную цепочку встаёт второе устройство.

---

## Аксиома

> **Point Desktop не является второй копией Point Phone и не является файловым менеджером. Это
> физическое расширение пространства исполнителей Point.**
>
> Пользователь работает с единым потоком объектов. Он выбирает **намерение, а не устройство**.
> Point самостоятельно выбирает лучший доступный `Realizer` среди Phone, Desktop и других
> разрешённых исполнителей. Если для выполнения намерения объект должен временно перейти на другое
> устройство, это происходит под капотом. Результат возвращается в контекст, из которого было
> запрошено действие, — если это не конечная доставка.
>
> **Устройство — свойство исполнения. Объект и намерение — свойства пользовательского действия.**

**Проверка контракта:**

> Если человек может пройти сценарий, **не зная, на каком устройстве работал `Realizer`**, Point
> устроен правильно.

**Критерий работы, которая этот контракт исполняет:**

> Мы не добавили новую систему. Мы наконец заставили существующую систему действительно выбирать
> `Realizer`.

## Четыре инварианта

### И1. `Capability` никогда не принадлежит устройству

Не бывает `PhoneCapability`, `DesktopCapability`, `RemotePhoneCapability`, `RemoteDesktopCapability`.

```
Capability:  ExtractText          ← что человек хочет сделать
Realizers:   PhoneOcrRealizer     ← как и где это может быть исполнено
             DesktopOcrRealizer
             CloudOcrRealizer
```

Именно этот инвариант не даёт архитектуре снова скатиться в удалённые кнопки. Признак нарушения
простой: как только у способности в имени появилось устройство — она перестала быть способностью.

### И2. Пользователь не видит `Realizer`

В обычном сценарии на экране **нет** ни «На компьютере», ни «На телефоне», ни «Отправить на ПК»,
ни приписки «· телефон». Есть:

```
объект → действие → выполнение → результат
```

Устройство появляется в интерфейсе **только** когда:
- оно действительно меняет ожидание («это займёт дольше — идёт на компьютер»);
- требуется действие человека;
- произошёл отказ;
- это чужой сервис и нужно согласие.

Куда Point отправил объект — это состояние исполнения, а не решение, которое принимает человек.

### И3. `Resolver` выбирает под задачу, а не по глобальному закону

Никакого архитектурного `LOCAL > CLOUD > REMOTE`. Выбор делается для конкретной пары
**`Capability` + `PointObject` + контекст**: доступность реализации, её характеристики, размер
объекта, состояние связи.

```
PPTX → ExportPdf                 Фото → ExtractText
  Phone    нет реализации          Phone    LOCAL
  Desktop  LibreOffice/Office      Desktop  LOCAL
  Cloud    есть                    Cloud    CLOUD
        ↓                                ↓
     Desktop                      лучший доступный
```

`priority` — свойство **конкретной реализации**, а не философия Point. Эвристики допустимы; законом
они не становятся.

Это не новая сущность: ADR-0001 уже назвал её — **`ExecutionPolicy`**, «цена — свойство запуска…
живёт там, где делается выбор исполнителя, то есть у `Resolver`».

### И4. `Realizer` не становится распределённым `Planner`

Point выбирает исполнителя **текущего** намерения и **никогда не выбирает следующее**.

Многошаговый сценарий — это последовательность **явных действий человека**, каждое из которых может
исполниться на другом устройстве. Автоматически генерируемым конвейером он не становится:

```
ХОРОШО                             ПЛОХО
фото → ExtractTable                фото → «сделай красиво»
   (Resolver выбрал исполнителя)      → OCR → таблица → PDF → на телефон → карта
→ человек выбрал следующее             (Point додумал четыре шага за человека)
```

Следствие, названное отдельно: **Point не платит за человека.** Он превращает номер карты в
доступное значение и кладёт его в буфер того устройства, где человек сидит. Платёж человек
совершает сам, в своём банковском приложении. То же для любого внешнего действия: Point доводит
объект до пригодного вида и останавливается.

Это тот же старый инвариант «Point не строит автоматических цепочек» — контракт его не отменяет, а
уточняет: **выбор исполнителя ≠ выбор шага.**

## Граница молчаливого выбора

Молчаливый выбор действует **только внутри круга устройств человека**.

| | Молча | По тапу, с именем |
|---|---|---|
| свой телефон, свой компьютер | ✅ объект не покидает круг, спрашивать нечего | |
| чужой сервис (OCR, модель, расшифровка) | ❌ никогда | ✅ действие выбрал человек, и он видит, куда уходит объект |

Без этой границы контракт съел бы инвариант приватности: карты, платежи, переписка и военная
ведомость уехали бы наружу «под капотом». Это же — уровень 2 `ExecutionPolicy` из ADR-0001:
«дорогой или сетевой — не запускается никогда без явного тапа по Action».

## Доставка — тоже намерение

«На компьютер» остаётся законным действием: человек хочет **продолжить работу на большом экране**.
Это его намерение, а не выбор исполнителя.

| | Намерение-преобразование | Намерение-доставка |
|---|---|---|
| пример | «Распознать», «В PDF» | «На компьютер», «На телефон» |
| кто выбирает устройство | **Point** | человек, потому что место и есть цель |
| результат | объект возвращается в контекст запроса | `ActionResult.Done` |

ADR-0001, поправка 3, прямо называет «продолжить на ПК» законным пользователем `Done`.

## Куда это встаёт в замороженный фундамент

ADR-0001, менять только новым ADR:

```
PointObject → Extractor → PointObject Graph → Planner → Action → Executor → PointObject Graph
```

Карта имён — из самого ADR-0001:

| Манифест | Код |
|---|---|
| Action | `Capability` |
| Executor | `Realizer` за `Resolver`, включая `FallbackRealizer` |
| Planner | `BubblePolicy` / `LearningBubblePolicy` |
| рёбра графа | `PointObject.sourceObjects` + `creatorAction` |

**Второе устройство — это ещё одно место исполнения существующего графа.** Оно не вводит модели
поверх фундамента.

| Desktop добавляет | Desktop НЕ добавляет |
|---|---|
| `Realizer`'ы под уже существующие `Capability` | второй реестр способностей |
| один вход в `ExecutionPolicy`: доступность соседа | второй `Planner` |
| `RemoteRealizer` с `meta.kind = REMOTE` | второй граф, вторую модель объекта |
| место исполнения | новую семантику `Action` |

**Изобретать нечего.** ADR-0001 назвал оба недостающих шва и оставил их нулём: `ExecutionPolicy`
(в коде отсутствует) и `RealizerKind.REMOTE` (`core/flow/RealizerMeta.kt`, «reserved for the future
ICG»). Другое устройство и есть REMOTE.

## Архитектурные ворота

Проходятся письменно **перед каждым срезом**, до первой строки кода:

1. Найти существующий frozen contract / ADR, которого касается изменение.
2. Показать используемый шов: `PointObject` / `Extractor` / `Graph` / `Planner` / `Action` /
   `Realizer` / `Executor`.
3. Доказать, что изменение **расширяет** шов, а не меняет его смысл.
4. Не создавать новую абстракцию, если существующая способна выразить требование.
5. Не переносить ответственность между слоями только ради Desktop.
6. Не дублировать `PointObject`, граф, `Capability`, `Planner` или `Resolver` для Desktop.
7. Не менять ADR-0001 без отдельного ADR.
8. Если реализация требует изменить фундаментальную цепочку — **STOP**: не кодировать обходной путь
   и не «улучшать» архитектуру молча, а сформулировать конфликт и вернуть владельцу.
9. После среза прогнать тесты замороженной архитектуры и кросс-устройственные.
10. Любое изменение протокола — только дописыванием, обратно совместимо.

### Журнал ворот

#### Срез 1 — один словарь намерений · пройдено 06.08.2026

1. **Затронутый контракт.** ADR-0001 (карта имён Action = `Capability`), правило модулей из
   `CLAUDE.md`, инвариант «`:core:model` и `:core:flow` без Android».
2. **Используемый шов.** `Action` (`Capability`) — и только он. `PointObject`, граф, `Planner`,
   `Executor` не трогаются.
3. **Расширение, а не изменение смысла.** ADR-0001 говорит «Action доступен всем подходящим
   объектам через `accepts`». Сегодня это неправда на второй поверхности: у компьютера **свои 20
   идентификаторов**, 16 из которых повторяют намерение телефона. Срез не меняет смысл `Action` —
   он убирает второй экземпляр одного и того же Action.
4. **Новых абстракций нет.** Ни одной. Убираются существующие дубли.
5. **Ответственность не переносится ради Desktop.** Декларация Action переезжает в слой, который по
   собственной роли держит `Capability`, `CapabilityRegistry` и `BubblePolicy`, — это исправление
   слоя, а не услуга компьютеру. Реализации остаются там, где были.
6. **Дублей не заводится** — наоборот, 16 удаляются.
7. **ADR-0001 не меняется.**
8. **STOP не сработал:** фундаментальная цепочка не затронута.
9. **Проверка:** существующие тесты + `CapabilityInventory` как сторож «словарь один».
10. **Протокол не меняется** в этом срезе вовсе.

**Решение по способу переноса, принятое воротами 4.** `:core:flow` сегодня не имеет ни одной
сторонней зависимости, кроме корутин, — и не получит. Из 49 деклараций телефона 37 имеют пустой
конструктор, у остальных зависимости — контракты, которые уже живут в `:core:flow`. Поэтому
переезжающие декларации **теряют аннотацию `@Inject`**, а Hilt связывает их через `@Provides
@IntoSet` в `CapabilityModule`. Ядро остаётся без `javax.inject`; Hilt-привязки правятся
механически.

**Объём первого шага.** Не 49 деклараций разом, а те, что нужны слиянию 16 идентификаторов и
сквозному сценарию. Остальные переезжают по мере надобности.

## Роли устройств

Это описание **реализаций**, а не развилка, которую показывают человеку.

| | Чем силён |
|---|---|
| **Телефон** | камера, микрофон, системное «Поделиться», мобильный контекст, локальное бесплатное чтение снимков |
| **Компьютер** | большой экран, клавиатура и мышь, настоящий конвертер офиса, файловая система, принтер, системный буфер, тяжёлые реализации |
| **Сервер** | доставка, адресация, Drop — и ничего больше |

Мозг один — модель Point, а не три независимых продукта.

## Приёмка

Сквозной сценарий владельца. **Нигде человек не выбирает устройство.**

```
фото таблицы → Point понимает Table → извлекает таблицу
      (Resolver сам выбирает реализацию)                        → TableObject
→ человек отправляет результат на компьютер          [доставка — его намерение]
→ компьютер открывает таблицу → человек редактирует → «В PDF»
      (Resolver сам выбирает компьютер: у телефона реализации нет)
→ человек отправляет PDF на телефон
→ телефон извлекает номер карты → «Скопировать» → значение в буфере компьютера
→ ЧЕЛОВЕК САМ платит в банковском приложении                   ← Point за него не платит (И4)
→ снимок экрана компьютера → понят номер квитанции → значение в буфере телефона
```

Каждая стрелка — явное действие человека. Point выбирает только исполнителя.

**Т1 — выбор без выбора.** Дано: PDF; и телефон, и компьютер умеют `ExtractText`; компьютер
подходит лучше. Когда: человек нажал «Распознать». Тогда: исполняет компьютер · результат в
**исходном** контексте · человек компьютер не выбирал и нигде его не видел.

**Т2 — единственный исполнитель.** Дано: PPTX; телефон не умеет `ExportPdf`, компьютер умеет.
Когда: человек нажал «В PDF». Тогда: исполняет компьютер · выбора устройства человек не видит ·
готовый результат в исходном контексте.

Т1 и Т2 важнее теста самого `RemoteRealizer`: они судят контракт, а не деталь реализации.

## Чего не строим

Второй граф · второй `Planner` · второй реестр способностей · вторую модель объекта ·
синхронизируемую папку · зеркалирование экрана телефона и управление им · файловый менеджер ·
AI-чат на компьютере · раздел «История» на компьютере · автоматический выбор следующего намерения ·
платёж за человека.

Контракт не расширяется новыми продуктовыми идеями.

## Столкновения с ADR-0001 — решено 06.08.2026

Вынесены владельцу воротами 8, отданы на усмотрение исполнителя. Оба решения читают ADR-0001, а не
меняют его.

### С1. Представление или новый объект

**Решение: результат — представление, если несёт ТО ЖЕ значение в другой форме; новый объект, если
несёт ДРУГОЕ значение.**

| | Что это | Почему |
|---|---|---|
| таблица → xlsx · csv · **pdf** | представление | одно значение, разные способы его выдать |
| картинка → та же картинка легче | представление | то же изображение, другая передача |
| снимок → текст | **новый объект** | текст — не снимок |
| PDF → номер карты | **новый объект** | номер — не документ |

Отсюда сквозной сценарий читается так: «таблица → В PDF» даёт **представление `TableObject`**, а не
узел `PDFObject`. Через границу устройств едет это представление **вместе с личностью и пониманием
таблицы**, поэтому найденный на телефоне номер карты происходит от таблицы, а не от безымянного
PDF, — происхождение не рвётся.

Довод ADR прямой: «одно и то же значение не может существовать в графе трижды под разными
расширениями». Исправленная таблица иначе рождала бы второй PDF, и ни один из двух не был бы
объявлен текущим.

**Следствие, которое надо будет разобрать в срезе 4:** «Сделать легче» сегодня порождает второй
объект на конвейере (#595). По этому правилу это представление, а не объект, и облачное чтение
должно само брать подходящее представление вместо того, чтобы советовать человеку сжать вручную.
Разбирается там, не здесь.

### С2. Восстановимость `ObjectRef` через границу устройств

**Решение: `ObjectRef` остаётся локальным адресом и только адресом. Второго адреса не заводится.**

ADR требует восстановимости словами «объект помнит, откуда он взялся, и умеет перечитать себя».
Через границу устройств «перечитать» — это **попросить у того, кто держит оригинал**. Устройство
происхождения — факт происхождения, а происхождение уже одно из пяти полей графа; в `ObjectRef` не
добавляется ничего.

Почему не иначе: два адреса в одном `ObjectRef` — это второй источник правды о том, где лежат
байты, ровно та свалка, от которой ADR и защищает формулировкой «и ничего, кроме ссылки».
Адресация по содержимому решала бы задачу, но это новая механика при живой старой — ворота 4.

**Побочный выигрыш:** уборка на ПК (#602) перестаёт спорить с памятью. Убранный объект, открытый
заново из «БЫЛО РАНЬШЕ», не упирается в «файла больше нет» — компьютер просит его у телефона.
