# ADR-0001 — Object Graph Runtime

Status: Accepted
Date: 2026-08-07

## Context

Point должен работать с произвольными входами, не имея заранее полного набора типов и сценариев.

Один вход может содержать много независимых или вложенных объектов:

- фотография визитки содержит QR, телефон, человека и организацию;
- скриншот карты содержит карту, область и координаты;
- фотография документа содержит текст, даты, людей, числа, печати и другие элементы;
- скриншот переписки может содержать фотографию автомобиля, внутри которой можно обнаружить номер;
- голосовое может содержать несколько дат, мест и других значений.

Невозможно заранее определить конечную глубину понимания.

Поэтому Point не строится вокруг одноразового классификатора:

Object → Type → Fixed Extractors → Actions.

Point использует накапливающееся состояние понимания.

---

## Decision

Point использует Object Graph Runtime.

Основной цикл:

    Input Object
        ↓
    Graph State
        ↓
    Discovery
        ↓
    Knowledge / Objects / Relations
        ↓
    Graph State
        ↓
    Planner
        ↓
    Action
        ↓
    Executor
        ↓
    Graph State

Цикл может повторяться произвольное количество раз.

Каждый новый результат становится частью состояния, на основании которого могут появиться новые направления Discovery и новые действия.

---

## 1. Graph

Graph — это рабочая структура состояния понимания.

Он содержит:

- Objects;
- значения и признаки объектов;
- Relations;
- Evidence / Provenance;
- Focus;
- Context;
- состояние того, что уже было исследовано.

Graph не является:

- базой знаний обо всём мире;
- каталогом сущностей;
- пользовательской историей;
- отдельной семантической онтологией.

---

## 2. Object

Object — универсальная единица, с которой runtime может продолжить работу.

Фундаментальные типы объектов должны оставаться небольшими и определяться потребностями runtime.

Нельзя вводить отдельный архитектурный тип для каждого предмета мира.

Например, `Cat`, `Car`, `Stamp`, `Dish` и `Medicine` не являются обязательными фундаментальными типами.

Их семантика может быть представлена:

- значением;
- признаком;
- Evidence;
- отношением;
- Focus;
- результатом Discovery.

---

## 3. Object identity

Object ID означает конкретный объект в Graph, а не уникальный объект реального мира.

Runtime не обязан автоматически объединять:

- две фотографии одной машины;
- двух людей, которые могут оказаться одним человеком;
- два обнаружения одного предмета.

Entity resolution может быть предложен пользователю через UX.

Это не обязанность Graph Runtime.

---

## 4. Enrichment

Enrichment добавляет знание существующему объекту.

Enrichment:

- не создаёт новую версию пользовательского объекта;
- не удаляет ранее найденное знание;
- может добавить новые значения;
- может добавить Evidence;
- может обнаружить новые Objects;
- может добавить Relations;
- может изменить доступные Actions.

Обогащение исходного объекта и появление обнаруженного дочернего объекта — совместимые события.

Например:

    Photo
      ├── Phone
      └── QR

`Photo` остаётся тем же объектом, одновременно получая новое знание.

`Phone` и `QR` могут быть объектами Graph и самостоятельными точками дальнейшего Discovery.

---

## 5. Transformation

Transformation — выполнение действия, результатом которого является новый самостоятельный Object.

Исходный Object не заменяется.

Пример:

    Photo
      ↓ Transform
    CleanPhoto

Representation не является самостоятельным semantic Object только из-за формата.

---

## 6. Discovery

Discovery — получение нового знания о текущем Graph.

Discovery не обязан выполнять полную классификацию объекта.

Он отвечает на вопрос:

> Что ещё сейчас можно узнать, что потенциально изменит пространство полезных действий?

Discovery может использовать:

- локальные алгоритмы;
- OCR;
- CV;
- модели;
- внешние исполнители;
- уже имеющиеся объекты;
- Relations;
- Focus;
- Context;
- ранее полученное Evidence.

Discovery может быть применён:

- к исходному объекту;
- к обнаруженному объекту;
- к области;
- к вложенному объекту;
- к совокупности объектов.

---

## 7. Recursive understanding

Любой объект, обнаруженный в Graph, может стать входом следующего Discovery.

Поэтому:

    Object
      ↓
    Understand
      ↓
    Object / Knowledge
      ↓
    Understand
      ↓
    Object / Knowledge
      ↓
    ...

не является специальной цепочкой типов.

Это один и тот же runtime, применённый к новому состоянию Graph.

Пользователь может явно углублять понимание через UI.

---

## 8. Focus

Focus — пользовательское указание, какую часть состояния следует исследовать.

Focus не является обязательным и не является значением, которое пользователь редактирует.

Focus может резко изменить приоритет Discovery.

Например:

    Conversation
      → Photo
         → Focus(region)
            → обнаружить автомобиль
               → обнаружить номер

Без Focus Point может самостоятельно выбрать наиболее перспективную область.

---

## 9. Evidence и Provenance

Каждое знание может иметь Evidence и источник происхождения.

Источники могут включать:

- OCR;
- RULE;
- MODEL;
- HUMAN;
- другие определённые runtime источники.

Несколько источников могут дать разные результаты.

Runtime не должен молча уничтожать конфликтующие знания.

Хранение происхождения не означает обязательного показа внутренней структуры пользователю.

---

## 10. Investigated state

Runtime должен отличать как минимум:

- ещё не исследовано;
- исследовано, но не найдено;
- найдено;
- обнаружено противоречие;
- исследование завершилось отказом.

Это необходимо, чтобы `not found` не превращалось в `not exists`.

---

## 11. Planner

Planner получает текущее состояние Graph и доступные Actions.

Planner не обязан сначала определить «полный тип» входного объекта.

Он выбирает наиболее уместные направления действий и дальнейшего исследования на основании текущего состояния.

Конкретный алгоритм ранжирования определяется RFC.

---

## 12. Execution

Executor выбирает способ исполнения в соответствии с архитектурной политикой Point.

Устройство исполнения не является пользовательским выбором само по себе.

Внешняя передача объекта требует соответствующего согласия.

Внутреннее Discovery и пользовательское Action не должны смешиваться.

---

## 13. Pause

Discovery или Action может ожидать действия пользователя.

Это пауза внутри шага, а не новый тип результата Graph.

---

## 14. Relationship to other documents

CONSTITUTION определяет продуктовые законы.

ADR-0001 определяет фундаментальный архитектурный механизм, реализующий эти законы.

RFC Progressive Object Understanding определяет алгоритм выбора и выполнения дальнейшего Discovery внутри этого механизма.

RFC не переопределяет Object, Graph, Enrichment или Transformation.

Если алгоритмическое решение требует изменения архитектурного контракта ADR, это сначала становится изменением ADR.

---

## Consequences

Положительные:

- Point не требует полной онтологии мира;
- глубина понимания не ограничена архитектурой;
- любой найденный объект может стать новым входом;
- новое знание не уничтожает старое;
- Focus позволяет пользователю направлять дорогой анализ;
- локальное и облачное понимание могут дополнять друг друга;
- один runtime работает для документов, изображений, аудио, переписки, ссылок и других входов.

Цена:

- Graph должен хранить больше состояния;
- Discovery должен учитывать уже исследованные направления;
- Planner должен работать с графовым состоянием, а не только с одним объектом;
- необходимо явно моделировать Evidence и состояние исследования;
- стоимость и латентность Discovery становятся частью алгоритма Planner.

---

## Rejected alternatives

### Полная классификация входа перед работой

Отклонено.

Невозможно заранее определить все возможные типы входа и их комбинации.

### Онтология всех сущностей мира

Отклонено.

Point не должен превращаться в систему с тысячами фундаментальных типов `Car`, `Cat`, `Stamp`, `Dish` и т.п.

### Новая версия Object при каждом enrichment

Отклонено.

Enrichment сохраняет идентичность исходного Object.

### Автоматическое объединение сущностей реального мира

Отклонено.

Entity resolution является отдельной UX-задачей.
