# RFC — Progressive Object Understanding

**Status:** Proposed

## 1. Назначение

RFC описывает алгоритм, который позволяет Point постепенно понимать произвольный объект.

RFC не определяет продуктовую идентичность Point.

RFC реализует Graph Runtime из ADR-0001.

---

## 2. Проблема

Point может получить что угодно:

- текст;
- clipboard;
- URL;
- изображение;
- PDF;
- документ;
- аудио;
- музыку;
- архив;
- композицию из нескольких объектов.

Объект может содержать другие объекты.

Например:

Document
→ Screenshot
→ Chat
→ Image
→ Vehicle
→ Cat

или:

Audio
→ Transcript
→ Dates
→ Places

или:

Image
→ Document
→ Handwriting
→ Stamp
→ Person
→ Money
→ Date
→ Relations

Невозможно заранее иметь один pipeline для всех комбинаций.

Невозможно гарантировать полное понимание одним проходом.

---

## 3. Основная идея

Point не пытается сначала ответить:

> Что это целиком?

Он отвечает на другой вопрос:

> Какое следующее исследование сейчас наиболее полезно?

Состояние постепенно расширяется:

Graph₀
→ Graph₁
→ Graph₂
→ Graph₃
→ ...

Каждое новое знание может породить новые возможности исследования и новые действия.

---

## 4. State

Минимальная модель:

State = Graph + Context + Focus + InvestigationState

### Graph

Текущее знание об объектах и отношениях.

### Context

Связанные объекты и обстоятельства текущего исследования.

### Focus

Явно указанная человеком область/часть/аспект, если он существует.

### InvestigationState

Investigation State описывает состояние знания (ADR-0001 §9) и принадлежит паре:

(ObjectId, Investigation/CapabilityId)

Состояния:

- не исследовано;
- найдено;
- не найдено;
- исследовано недостаточно;
- противоречиво.

Это позволяет отличить:

QR не найден

от:

QR ещё не искали.

Состояние выполнения хранится отдельно и знанием не является.

Идёт ли исследование прямо сейчас и не сорвалось ли оно — свойства операции. Сорвавшееся исследование оставляет знание в «не исследовано» или «исследовано недостаточно» и никогда не переводит его в «не найдено».

«Дальше исследовать не оправдано» — вывод ranking на текущем состоянии (§22), а не состояние знания. При изменении Graph он пересчитывается.

---

## 5. Discovery

Discovery — кандидат на получение нового знания.

Discovery может:
- уточнить объект;
- найти структуру;
- найти сущность;
- получить атрибут;
- получить текст;
- получить геометрию;
- найти QR;
- найти координаты;
- распознать речь;
- определить музыку;
- найти подписи;
- найти печати;
- установить отношение;
- раскрыть вложенный объект;
- открыть новую ветвь исследования.

Discovery не обязан соответствовать одному `kind`.

Discovery может породить новые Discovery.

---

## 6. Discovery не является pipeline

Нельзя строить механизм:

IMAGE → OCR → DOCUMENT → TABLE → ...

как обязательную последовательность.

Правильная модель:

current Graph
→ какие исследования теперь возможны?
→ какие из них наиболее полезны?
→ выполнить одно/несколько допустимых
→ обновить Graph
→ пересчитать возможности.

Поэтому фотография автомобиля может одновременно породить:

Vehicle
→ Plate
→ Brand
→ Model

а изображение документа:

Document
→ Text
→ Person
→ Date
→ Money
→ Stamp
→ Relations

без необходимости вводить отдельный pipeline для документа.

---

## 7. Candidate Generation

Candidate Discovery формируется из:

1. текущих объектов;
2. их свойств;
3. relations;
4. evidence;
5. representations;
6. Context;
7. Focus;
8. доступных Capability;
9. уже исследованных ветвей.

Candidate generator должен быть открытым.

Добавление новой Capability может создать новые Discovery без изменения основного алгоритма.

Отдельного механизма извлечения знания нет: исследование объявляется Capability и выполняется через Resolver и Realizer (ADR-0001 §11).

---

## 8. Discovery ranking

Здесь ранжируются исследования, а не действия.

Discovery ranking и Action ranking — две разные задачи над одним Graph (ADR-0001 §14). Action ranking остаётся за Planner, и этот RFC его не определяет.

Выбирается не самый вероятный тип объекта.

Выбирается наиболее полезное следующее исследование.

Концептуально:

Priority =
    Expected usefulness
    × Probability of useful result
    × Actionability
    ÷ Cost

Формула является моделью принятия решения, а не обязательной математической реализацией.

Дополнительно могут учитываться:
- Focus;
- Context;
- latency;
- privacy;
- availability;
- уже полученное знание;
- необходимость внешнего сервиса;
- необходимость согласия.

---

## 9. Что означает usefulness

Исследование полезно, если его результат способен:

- создать новое полезное действие;
- улучшить существующее действие;
- раскрыть новую ветвь объекта;
- уточнить уже известное;
- дать пользователю доступ к самостоятельному объекту;
- сделать возможным следующий шаг.

Полное описание объекта само по себе не является целью.

---

## 10. Focus

Если пользователь выделил конкретную область, это сильный сигнал.

Например:

Photo
→ Focus = синяя точка на карте
→ Discovery = координаты

или:

Photo
→ Focus = госномер
→ Discovery = plate recognition.

Если Focus отсутствует, механизм продолжает работать глобально.

Focus не должен быть обязательным для универсальности.

---

## 11. Progressive Loop

Основной цикл:

State
→ generate candidates
→ rank
→ select permitted discovery
→ execute
→ validate
→ merge into Graph
→ update InvestigationState
→ recompute candidates
→ re-rank

Цикл может повторяться произвольное число раз.

Новая глубина не требует нового алгоритма.

Шаг `validate` проверяет пригодность результата: та ли форма, отвечает ли он заявленному, можно ли положить его в Graph.

Validation не разрешает противоречия (ADR-0001 §15). Она не выбирает между конкурирующими результатами и не отбрасывает более слабый — конфликт попадает в Graph и разрешается отдельным шагом.

Непригодный результат не становится знанием об отсутствии: он оставляет Investigation State нетронутым и завершается неудачей операции.

---

## 12. Вложенные объекты

После обнаружения самостоятельного объекта Point может продолжить исследование уже его.

Например:

Chat
→ Image
→ Vehicle A
→ Plate

При этом исходные связи сохраняются.

Пользователь может «зайти» в обнаруженный объект через UX и продолжить его понимание.

Таким образом, пользовательский Focus и вложенность образуют единый механизм навигации по Graph.

---

## 13. Пример: составной документ

Вход:

фотография кривой полурукописной ведомости с печатями.

Не предполагается, что это «таблица».

Возможное развитие:

Image
→ document structure
→ geometry
→ regions
→ handwriting
→ printed text
→ stamps
→ signatures
→ dates
→ persons
→ numbers
→ relations

Затем Point может обнаружить, что некоторый набор данных образует TableObject.

Только после этого появляется смысл:

TableObject
→ XLSX

Но другой документ может привести совсем к другому результату.

---

## 14. Пример: переписка

Вход:

скриншот переписки.

Исследование может обнаружить:

Chat
→ Image
→ Vehicle A
→ Vehicle B

Пользователь может выбрать Vehicle A.

Это создаёт Focus на конкретном объекте:

Vehicle A
→ Plate

Второй автомобиль остаётся отдельным объектом.

---

## 15. Пример: карта

Вход:

скриншот карты.

Без Focus:

Image
→ map-like structure
→ marker
→ location candidates.

С Focus:

Image
→ Focus(marker)
→ precise coordinate extraction
→ address / POI.

Не требуется заранее классифицировать изображение как «MapObject».

---

## 16. Пример: визитка

Photo

→ QR
→ Phone
→ Email
→ Person
→ Address

QR и Phone могут быть получены разными Realizer.

Они не заменяют друг друга.

Полученное знание увеличивает пространство действий.

---

## 17. Пример: голосовое

Audio

→ speech
→ transcript
→ dates
→ places
→ people
→ relations

Если в голосовом перечислены даты и места, Point не обязан сначала классифицировать весь файл как «аудио с календарными данными».

Каждый следующий результат становится новым источником Discovery.

---

## 18. Пример: произвольный мультимедиа-вход

Для:

- кота;
- автомобиля;
- еды;
- инструкции;
- техпаспорта;
- YouTube URL;
- clipboard;
- PDF;
- ZIP;
- музыки;

алгоритм один и тот же.

Различаются только доступные кандидаты Discovery и Capability.

---

## 19. Parallel Realizers

Один Discovery может иметь несколько Realizer.

Например:

ExtractText
├── local OCR
├── computer OCR
└── remote OCR

Результаты разных Realizer не должны молча уничтожать друг друга.

При конфликте сохраняются:
- результаты;
- provenance;
- evidence;
- alternatives;
- InvestigationState.

Разрешение конфликта является отдельным шагом понимания и не выполняется validation (§11).

---

## 20. Автоматизм

Progressive Understanding не означает обязательного автоматического полного анализа.

Point может автоматически выполнять допустимые исследования внутри устройств пользователя.

Исследование, требующее выхода объекта за границу устройств пользователя, не запускается без явного согласия человека.

Согласие может быть дано заранее — выбранным режимом работы, — но никогда не подразумевается по умолчанию и не следует из того, что снаружи результат будет лучше.

Пока согласия нет, такое исследование остаётся кандидатом с названной причиной недоступности, а не выполняется скрытно.

Внешний AI — не обязательная часть каждого цикла.

---

## 21. Стоимость

Point не должен запускать все возможные исследования сразу.

В первую очередь выбираются исследования с высокой ожидаемой ценностью относительно стоимости.

Стоимость включает не только деньги:

- latency;
- network;
- privacy;
- computational cost;
- user attention;
- необходимость дополнительного ввода.

---

## 22. Остановка

Цикл останавливается, если:

- хорошие действия уже доступны;
- следующие Discovery имеют низкую ожидаемую ценность;
- стоимость слишком высока;
- результат не изменит пространство действий;
- требуется Focus;
- требуется согласие;
- дальнейшее исследование сейчас не оправдано.

Остановка означает:

> сейчас дальнейшее понимание не оправдано.

Она НЕ означает:

> объект полностью понят.

---

## 23. Ошибочная классификация

Любая классификация является гипотезой.

Раннее предположение не должно закрывать другие ветви.

Например, объект, предположительно являющийся документом, всё ещё может содержать:
- QR;
- фотографию;
- карту;
- переписку;
- автомобиль;
- человека;
- рукописную область.

Более позднее знание может изменить гипотезу.

---

## 24. Действия

После каждого существенного изменения Graph Point пересматривает Capability.

Graph₁ → Actions₁

Graph₂ → Actions₂

Graph₃ → Actions₃

Новые знания могут:
- добавить действие;
- сделать действие более уместным;
- сделать действие неприменимым;
- открыть новый объект и его действия.

Цель Progressive Understanding — не максимизировать количество знаний.

Цель — максимизировать полезное пространство действий при разумной стоимости понимания.

Что именно показать человеку и в каком порядке — решает Planner. Этот RFC определяет, какое исследование выполнить следующим, и не определяет порядок действий.

---

## 25. Пользовательская лестница

UX может экспонировать Progressive Understanding как:

Понять
→ Понять сильнее
→ Понять ещё сильнее
→ ...

Но внутренний механизм не обязан представлять это как фиксированную последовательность уровней.

Каждый следующий шаг выбирается из текущего Graph.

---

## 26. Не цели

RFC не требует:

- полного semantic graph;
- полной классификации;
- отдельного типа для каждого предмета мира;
- полного анализа каждого входа;
- автоматической длинной цепочки пользовательских действий;
- AI на каждом входе;
- превращения каждой сущности в Object;
- фиксированного pipeline;
- одной конкретной модели AI;
- одной конкретной OCR-системы.

---

## 27. Критерий универсальности

Механизм считается универсальным, если новый реальный кейс можно обработать тем же циклом:

Graph
→ Discovery
→ Ranking
→ Execution
→ Validation
→ Merge
→ Graph

без добавления специальной архитектурной ветки для предметной области.

Наличие нового предмета мира само по себе не является основанием для нового runtime-типа.

---

## 28. Связь с ADR-0001

ADR определяет:

- что такое Object;
- что такое Graph;
- что такое Atom;
- что такое Enrichment;
- что такое Transformation;
- что такое Representation;
- что такое Relation;
- что такое Evidence;
- что такое Investigation State;
- что такое Focus;
- что такое Intent;
- что такое Capability;
- что такое Realizer;
- что такое Resolver;
- что такое Planner;
- что такое Progressive Understanding;
- что такое Validation;
- что такое ActionResult;
- что переносится между устройствами.

RFC определяет только:

> как из текущего Graph выбирать следующее наиболее полезное исследование и как повторять этот процесс.

RFC не определяет Action ranking: порядок действий для человека остаётся за Planner.

Если RFC требует нового фундаментального примитива Graph Runtime — сначала пересматривается ADR.

Это относится и к состояниям: новое состояние знания добавляется в ADR §9, а не в этот RFC.

Если изменение затрагивает продуктовую семантику Point — сначала пересматривается Конституция.
