# /live-review — живая охота на дефекты

Второй контур тестирования Point: автотесты защищают известное — **эта охота ищет
неизвестное**. Ты не исполнитель тест-кейсов, а adversarial-исследователь: запускаешь
настоящий Point, смотришь глазами человека, ломаешь намеренно, расследуешь странное.
Заранее известного оракула нет — его появление в момент наблюдения и есть ценность.

## Роль и настрой
- Не пытайся «закрыть сценарий», получить зелёное или доказать, что Point работает.
  Задача — найти, где он НЕ работает, особенно то, о чём мы ещё не знаем.
- Здоровая поверхность не объявляется здоровой — меняй объект, состояние, порядок,
  способ взаимодействия.
- Discovery ≠ preservation: не превращай прогон в чеклист и не пиши автотест на каждый
  баг. Сначала: «что я узнал о продукте, чего не знал?»

## Пять способностей, которыми человек находит то, что тесты пропускают
1. **Параллельный оракул из мира** — ДО прогона знай истину объекта глазами (открой кадр,
   прочитай его сам). Сверяй вывод Point с реальностью, не с ожиданием кода.
2. **Чтение пользы** — после каждого шага: «что человек теперь МОЖЕТ, чего не мог?»
   Ответ «ничего» при зелёном экране — находка. Абсурд («Отследить „нет номера“»),
   тупик без выхода, «прочитал всё» с пустыми руками — категории пользы.
3. **Чувствительность к отсутствию** — «чего я ждал и НЕ увидел?»: нет двери, нет
   результата, нет следа, нет реакции. Ассерты видят только присутствие.
4. **Симметрии** — одна сущность = один узел; «отправлено» = появилось там; обе стороны
   живы = письмо доходит; умеет = предлагает. Нарушение симметрии видно без спецификации.
5. **Адаптивность** — странность на шаге B отменяет шаг C. Копай B до дна.

## Правило остановки (ядро охоты)
Увидел хоть что-то подозрительное — СТОП основному ходу. Минимальный набор пыток на месте:
повтори · сделай дважды · сделай наоборот · измени вход · назад посреди · убей процесс
и вернись · offline/online посреди · тот же объект ещё раз · другой объект · та же
операция на второй стороне (Phone ↔ PC). Новая странность — новое направление.

## Стартовая карта (не программа!)
Выбор поверхности: самый свежий срез кода (вчерашний фикс — сегодняшняя дыра) · самая
злая область (связка, process death, повторы, время) · самый грязный объект корпуса ·
самая застоявшаяся область (давно не копали). Каждой сессии — своя злость: день
повторов / день обрывов / день второй стороны / день плохой сети. Не начинай с «кадр 01».

## Журналы — продолжение экрана, не замена глазам
После значимого шага читай то, чего не видно: llm-log (сырые обмены с моделью — на
устройстве `run-as com.point cat files/llm-log/...`), mailbox-лог компакта, журнал ПК
(`~/.point-pc/journal`, base64-строки), знание объекта, связи, provenance. UI «выглядит
правильно» — не доказательство.

## Стенд (без этого охота калечит себя и владельца)
- Скрин ПЕРЕД каждым тапом; на экране не Point → тапы запрещены (если владелец не отдал
  устройство явно). Телефон в руках владельца — не трогать.
- A34: шаринг файлов только `/sdcard/Android/data/com.point/files/` + `file://`;
  `input text` кириллицу не умеет; координаты скринов ×1.17.
- Компакт на ПК запускать из собранного jar, НЕ из `:desktop:run` — пересборка убьёт
  процесс под ногами. Мышь владельца не трогать.
- Правки кода во время бегущего гейта запрещены; гейт и commit — раздельные вызовы.

## Находка → доска СРАЗУ (по ходу, не в конце)
Каждый подтверждённый дефект — issue немедленно (механика /todo: Inbox, Project #3),
title императивом, body: симптом · репро · ожидание · факт · вероятная причина ·
задетая аксиома/гарантия · классификация. Известной карточке — комментарий-подтверждение
вместо дубля. Журнал сессии (scratchpad/bughunt-*.md) ведётся параллельно — доска не
заменяет расследование.

## Классификация каждой находки
- **BUG** — дефект продукта → расследуй причину до класса отказов, потом чини/фиксируй.
- **MISSING GUARANTEE** — класс поведения ничем не защищён → сначала решение продукта,
  тест писать не по чему.
- **AUTOMATABLE REGRESSION** — оракул ясен и стабилен → регрессия, сформулированная как
  обещание человеку (решение владельца дословно в тексте теста), не как снимок реализации.
- **LIVE-ONLY** — недетерминизм модели/сети/времени → периодическая живая проверка.

Чинить найденное — только по слову владельца; фикс — с живой верификацией на устройстве
(баг найден живьём → и починка подтверждается живьём, не только гейтом).

## Отчёт сессии (короткий, в конце)
LIVE BUG HUNT: Surface · Objects used · Experiments performed · Findings ·
Newly discovered defect classes · Regression candidates · Live-only findings ·
Next surface to attack.

## Чего не делать
Не гонять корпус конвейером без остановок · не объявлять «всё зелено» · не писать
методологию вместо охоты · не сжигать облако на подтверждение уже известного ·
не превращать карту рисков в сценарий A→B→C→D.
