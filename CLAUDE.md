# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Что это

**Point** — приложение (Kotlin/Compose), встроенное в системный Share. Пользователь передаёт Point произвольный объект: image, text, pdf, zip, url, audio, screenshot, clipboard и т.д.

Point не обязан сначала полностью классифицировать объект.

Фундаментальная модель:

    Graph State → Discovery → ranking → выполнение → validate → merge → Graph State → reconsider

После существенного обогащения пространство действий пересматривается заново.

Понимание прогрессивное:

    Понять → Понять сильнее → Понять ещё сильнее → ...

Это один механизм, а не фиксированные стадии.

Point не является AI-чатом, менеджером файлов или каталогом заранее известных функций.

## Как здесь работать

- Работать максимально автономно: принимать разумные решения самому, а не засыпать вопросами.
- Перед изменением продуктовой семантики или архитектуры читать:
  1. `docs/CONSTITUTION.md`
  2. `docs/0001-object-graph-runtime.md` — ADR-0001 Object Graph Runtime.
  3. `docs/pou-rfc.md` — RFC Progressive Object Understanding.
- Конституция — источник продуктовых инвариантов; ADR — архитектурных решений; RFC — модели/направления двигателя.
- Код и тесты показывают текущую реализацию, но не являются автоматически источником продуктовой семантики.
- Не возвращать удалённые решения только потому, что они ещё присутствуют в коде.
- Не добавлять новую архитектуру только ради удобства текущей реализации.
- Временные файлы, черновики, логи и эксперименты — в system temp/scratch, не в корне.

## Модули

```text
:core:model ← :core:flow ← { :data, :executors, :core:ui } ← :app
```

Стрелки только вниз.

- `:core:model` — чистый Kotlin, Android-free.
- `:core:flow` — Graph/Flow и контракты Capability, Realizer, Resolver, Registry, BubblePolicy.
- `:core:ui` — Compose UI и дизайн-система, без бизнес-логики.
- `:data` — ObjectStore, LlmClient и внешние реализации.
- `:executors` — Capability + Realizer и их регистрация.
- `:app` — Android entry points, navigation, DI.
- `:desktop` — Compose Desktop поверх `:core:model` и `:core:flow`.

## Graph — фундамент Point

Graph — текущее понимание объекта и основа принятия следующих решений.

Не пытаться сначала свести произвольный объект к одному классу.

Не вводить runtime-типы вроде `Car`, `Cat`, `Stamp`, `BusinessCard`, `LicensePlate` или `Prescription` только потому, что такие сущности встретились.

Использовать фундаментальные object primitives, свойства, отношения, локализацию и Evidence.

Один объект может содержать множество сущностей и отношений. Они не обязаны автоматически сливаться в один объект.

Например:

    переписка
      → фотография
        → автомобиль
          → госномер

Пользователь может войти в найденный объект и продолжить его понимание. Тот же механизм должен работать для визитки, карты, документа с рукописью и печатями, фотографии еды, техпаспорта, голосового сообщения, текста, URL и составных документов.

Не создавать отдельную архитектурную ветку под каждый новый кейс.

## Enrichment и Transformation

**Enrichment** добавляет знание к существующему объекту. Исходный объект сохраняется.

Примеры: найден QR, распознан текст, найдены координаты, локализована область, обнаружены сущности или отношения.

**Transformation** создаёт самостоятельный объект.

Не путать новое знание об объекте с новым объектом.

Representation — форма представления результата, а не semantic object.

## Discovery

Discovery ищет не обязательно ответ на вопрос «что это?», а то, **что полезного можно узнать дальше**.

Discovery — про знание. Что предложить человеку и в каком порядке — задача Planner. Это два разных ranking над одним Graph, и один не выводится из другого.

Отдельного механизма исследования нет: Discovery объявляется Capability и выполняется через Resolver и Realizer, как любое действие. Отличается результат — знание в Graph.

Примеры:

- карта → точные координаты;
- визитка → QR / телефон / email;
- фото → автомобиль → госномер;
- документ → даты / люди / суммы / печати / рукопись;
- голосовое → даты / места;
- переписка → фотография → автомобиль → госномер.

Не требовать полного понимания объекта перед первым полезным действием.

## Progressive Understanding

Не запускать дорогую полную цепочку понимания для каждого объекта.

Начинать с дешёвого и потенциально полезного исследования. Полученное знание изменяет Graph и тем самым изменяет пространство следующих возможностей.

Учитывать Graph State, Focus, уже проведённые исследования, ожидаемую полезность, стоимость, latency, privacy и доступных исполнителей.

`Понять сильнее` — не отдельная ветка архитектуры и не специальный тип объекта: это следующий виток того же Discovery над текущим Graph State.

Формула Discovery ranking и механизм Candidate Discovery определяются RFC и implementation. Формулу Action ranking RFC не задаёт — она остаётся за Planner.

`validate` перед merge проверяет пригодность результата и **не разрешает противоречия**: конфликтующие результаты сохраняются вместе с provenance.

## Focus

Пользователь может дать Focus:

- выделить область;
- обрезать;
- войти в найденный объект;
- указать конкретную часть объекта.

Focus — сильный сигнал для Discovery и ranking, но необязателен.

Focus не является Intent.

## Investigation State

Investigation State — состояние **знания** для пары `(ObjectId, CapabilityId)`: исследовался ли этот вопрос для этого объекта.

- не исследовано;
- исследовано, не найдено;
- найдено;
- исследовано недостаточно;
- противоречиво.

`not investigated` ≠ `not found`.

Состояние выполнения (идёт / завершилось / сорвалось) и ошибка — свойства **операции**, хранятся отдельно и знанием не являются.

Сорвавшееся исследование оставляет знание в `not investigated` или «исследовано недостаточно» и никогда не переводит его в `not found`.

Не уничтожать конфликтующие результаты молчаливой заменой.

Evidence должен позволять понять происхождение и основания знания.

Provenance — внутренняя информация и не должна показываться пользователю просто потому, что существует.

## Intent

`Intent` — семантическое описание человеческого смысла действия.

Это не обязательный вход в систему, не устройство, не результат и не классификатор объекта.

Intent выводится из Graph, контекста и Focus и меняется вместе с состоянием.

Intent влияет на порядок действий и не является основанием убрать действие из списка.

Не строить архитектуру вокруг обязательного предварительного определения пользовательского намерения.

## Capability / Realizer

**Capability = что можно сделать.**

**Realizer = как это выполнить.**

UI / FlowGraph / BubblePolicy работают с Capability, а не с реализацией.

Исследование — тоже Capability. Отдельного реестра исследований не заводить; выделенный слой обогащения допустим только как реализация той же схемы.

Устройство — свойство исполнения, пока результат для человека один и тот же: не создавать `PhoneCapability`, `DesktopCapability`, `RemoteCapability` ради самого исполнителя.

Устройство входит в Capability, только когда от него зависит внешний результат: печать на телефоне и печать на компьютере — разные действия, потому что бумага выходит в разных местах.

`Resolver` выбирает подходящий способ исполнения для capability + Graph State + context.

## Устройства и внешние сервисы

Пользователь выбирает действие, а не устройство.

Телефон, компьютер и remote service — исполнители.

Среди собственных устройств выбор может быть автоматическим.

Объект покидает устройства пользователя только с явного согласия человека. Согласие может быть дано заранее — выбранным режимом, — но никогда не подразумевается по умолчанию.

Для **автоматического** исследования: пока согласия нет, `Resolver` не выбирает внешний Realizer, даже если он единственный и лучший — исследование остаётся кандидатом с названной причиной.

Для **пользовательского действия** наоборот: действие видно и доступно для выбора, по тапу показывается запрос согласия, и только после явного «да» Resolver берёт внешний Realizer. Прятать действие, ради которого и спрашивают согласие, нельзя.

Внутри разрешённого пространства внешний сервис допустим, если он лучше решает задачу. Собственная реализация не имеет приоритета сама по себе.

Внешние сервисы подключаются через существующие архитектурные швы, а не обходят их.

Приватность важнее удобства.

### Продолжение на компьютере

Graph между устройствами не синхронизируется — это не контракт.

Передаются объект, его известное состояние, список доступных на той стороне capability и результат с полученным знанием.

На той стороне это тот же объект, а не новый. Потеря уже полученного знания при переносе — дефект.

## Первый экран

Первый экран ≤ 300 мс и без I/O.

На нём допустимы только нулевые сигналы: MIME / расширение / размер и уже доступное состояние.

Обогащение выполняется асинхронно и может расширять пространство действий.

LLM не вызывается для первого экрана.

## Capability / ActionResult

`ActionResult` описывает операцию, а не знание об объекте.

Терминальных исхода три: `Success` — появился объект, `Done` — шаг состоялся без нового объекта (внешний side-effect либо новое знание), `Failure(recoverable)` — не вышло.

`NeedsInput` / `NeedsImage` — незавершённый шаг, ожидающий продолжения, а не исход.

`Failure` принадлежит операции: он не переводит знание в `not found`.

Ошибки не должны исчезать в молчаливых цепочках.

## ObjectStore

Объект немедленно копируется в scratch при приёме.

Работать с копией, а не с временным `content://` grant.

После завершения flow — `ObjectStore.clear()`, включая process death.

`:core:model` и `:core:flow` не знают об Android `Uri`.

## Side effects

File IO, сеть, Android framework, PDF rendering и другие side effects — только за интерфейсами.

Pure-логику тестировать напрямую.

Не использовать глобальные/static singleton-объекты. App-scoped Hilt bindings допустимы.

## Что Point НЕ становится

Point не превращается в:

- браузер;
- task manager;
- CRM;
- заметки;
- AI-chat как основную модель;
- чужую предметную область со своим независимым состоянием и навигацией.

Настройки самого Point — исключение: это конфигурация приложения.

## Секреты

Gemini key — только в `local.properties` (`GEMINI_API_KEY`), никогда не хардкодить и не коммитить.

Release-артефакты не должны содержать секреты.

Провайдеры и OCR-цепочка остаются за соответствующими контрактами (`LlmClient`, `CloudTextReader` и т.д.).

## Главный инженерный тест

Перед добавлением abstraction спроси:

1. Это действительно новый фундаментальный primitive?
2. Или это можно выразить существующими объектами, свойствами, отношениями, Evidence и Focus?
3. Проблема находится в Graph, Discovery, ranking, Capability, Realizer или UI?
4. Работает ли решение для произвольного объекта, а не только для текущего примера?

**Не добавляй новый semantic type только потому, что встретился новый noun.**

Главная цель:

> Point должен уметь встретить неизвестный объект, получить полезное знание, использовать это знание для поиска следующего полезного шага и продолжать этот процесс без заранее заданной классификации мира.
